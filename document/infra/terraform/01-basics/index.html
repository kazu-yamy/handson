Terraform の基本操作

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: Terraform を初めて使う人
  • 📋 前提: ターミナルでの基本的なコマンド操作（cd / ls / cat など）ができること。クラウドのアカウントは不要（ローカルにファイルを作るだけ）。Terraform がインストール済みであること
  • 🔗 前提となる項目: なし（トラック最初の項目）

🎯 このレッスンで学ぶこと

  • terraform init でプロバイダーを取得し、lock ファイルの役割を知る
  • fmt / validate / plan / apply の流れでリソースを作る
  • state（terraform.tfstate）に何が記録されているかを確かめる
  • 設定の変更が「置換」になる場合と、リソース間の暗黙の依存を plan の出力から読み取る
  • Terraform の外で実物を消したとき、plan がどう検出するかを確かめる
  • destroy で片付け、Git にコミットするファイルとしないファイルを分ける

概要

Infra トラックの最初の項目です。Terraform の設定ファイル（.tf）を書き、init → plan → apply の流れでリソースを作ってから、destroy で片付けるまでを一通り体験します。

クラウドのリソースは使いません。手元にテキストファイルを作る local_file と、ランダムな名前を作る random_pet だけを扱うので、アカウントの登録や料金の心配なしに試せます。 ここで覚える操作と state の考え方は、以降の各クラウドの項目でもそのまま使います。

ℹ️

使用バージョン

Terraform v1.16.2（darwin_arm64）/ hashicorp/local v2.9.1 / hashicorp/random v3.9.1 で動作を確認しています。 バージョンは執筆時点（2026年10月）のものです。terraform init はその時点の最新版のプロバイダーを選ぶため、実行する時期によっては新しいバージョンが入り、出力の内容も多少変わります。 掲載している出力は色なし（-no-color 相当）で取得したものです。

手順

1

作業ディレクトリを作り、init の前に plan してみる

まず Terraform が使えることを確かめます。terraform version でバージョンを表示します。

Terminal 
$ terraform versionTerraform v1.16.2on darwin_arm64Your version of Terraform is out of date! The latest versionis 1.16.5. You can update by downloading from https://developer.hashicorp.com/terraform/install

最後の 3 行は、より新しい版が出ているときだけ表示される案内です。表示されなくても問題ありません。 terraform コマンドが見つからない場合は、公式のインストールページの手順でインストールしてください。

作業ディレクトリ 01-basics を作り、その中に移動します。

Terminal 
$ mkdir 01-basics$ cd 01-basics

main.tf を作り、次の内容を書きます。terraform ブロックには、Terraform 本体の対応バージョンと、使うプロバイダー（Terraform から操作対象を扱うためのプラグイン）を書きます。 今回は、ローカルにファイルを作る hashicorp/local と、ランダムな値を作る hashicorp/random を使います。プロバイダーのバージョンは、この時点ではまだ書きません。

HCL main.tf 
terraform {
  required_version = ">= 1.9"

  required_providers {
    local = {
      source = "hashicorp/local"
    }
    random = {
      source = "hashicorp/random"
    }
  }
}

この状態で、init をせずに terraform plan を実行してみます。

Terminal 
$ terraform planError: Inconsistent dependency lock fileThe following dependency selections recorded in the lock file areinconsistent with the current configuration:  - provider registry.terraform.io/hashicorp/local: required by this configuration but no version is selected  - provider registry.terraform.io/hashicorp/random: required by this configuration but no version is selectedTo make the initial dependency selections that will initialize the dependencylock file, run:  terraform init

エラーになりました。文言は「依存関係の lock ファイルが設定と一致しない（Inconsistent dependency lock file）」というもので、「init していない」とは書かれていません。 設定にはプロバイダーが書かれているのに、どの版を使うかがまだ決まっていない、という意味です。対処として、最後の行で terraform init を実行するよう案内されています。

✅ 確認ポイント

terraform version で Terraform v1.16.2（またはそれ以降）が表示され、init 前の terraform plan が Error: Inconsistent dependency lock file で止まることを確認してください。

2

terraform init を実行します。main.tf に書いたプロバイダーを Terraform Registry からダウンロードし、作業ディレクトリを使える状態にします。

2 つのものが増えています。.terraform/ にはダウンロードしたプロバイダーの実行ファイルが入ります（.terraform/providers/registry.terraform.io/hashicorp/ の下）。 .terraform.lock.hcl は、選ばれたプロバイダーの版とハッシュを記録する lock ファイルです。次に init したときも同じ版が選ばれるようにするためのもので、出力にあるとおり Git などで管理することが推奨されています。

    …

  version = "3.9.1"
  hashes = [
    …

}

hashes の行は環境によって変わるため、ここでは省略しています。

次に、選ばれた版をもとに、プロバイダーのバージョン制約を main.tf に書き足します。 ~> 2.9 は「2.9 以上、3.0 未満」という意味で、互換性のある範囲の更新だけを許します。

Diff main.tf 
     local = {-      source = "hashicorp/local"+      source  = "hashicorp/local"+      version = "~> 2.9"     }     random = {-      source = "hashicorp/random"+      source  = "hashicorp/random"+      version = "~> 3.9"     }

source の後ろの空白が 1 つ増えているのは、= の位置をそろえるためです。後で使う terraform fmt が、この形に整えます。 設定を変えたので、もう一度 init し、terraform validate で、設定の文法と、参照や型などの整合性を検査します（プロバイダーの API やクラウドには接続しません）。

Terminal 
$ terraform initInitializing the backend...Initializing provider plugins...- Reusing previous version of hashicorp/random from the dependency lock file- Reusing previous version of hashicorp/local from the dependency lock file- Using previously-installed hashicorp/random v3.9.1- Using previously-installed hashicorp/local v2.9.1…$ terraform validateSuccess! The configuration is valid.

2 回目の init は、lock ファイルに記録された版を再利用しています（出力の後半は 1 回目と同じなので省略しています）。

✅ 確認ポイント

.terraform/ と .terraform.lock.hcl ができ、terraform validate が Success! The configuration is valid. を表示することを確認してください。

3

最初のリソースを書き、plan と apply で作る

いよいよ、Terraform で管理する対象（リソース）を書きます。main.tf の末尾に、テキストファイルを作る local_file リソースを追加します。 resource "種類" "名前" の形で書き、Terraform の中では local_file.hello という名前で指します。

Diff main.tf 
       version = "~> 3.9"     }   } }++resource "local_file" "hello" {+  filename = "${path.module}/output/hello.txt"+  content  = "Hello, Terraform!\n"+}

${path.module} は、この .tf ファイルがあるディレクトリを表します。filename に書いた場所へ、content の内容でファイルが作られます。

書いたら、terraform fmt で書式を整え、terraform validate で検査します。fmt は直す箇所が無ければ何も表示しません。

Terminal 
$ terraform fmt$ terraform validateSuccess! The configuration is valid.

続いて terraform plan で、これから何が起きるか（実行計画）を確認します。plan は確認するだけで、実際には何も変更しません。

Terminal 
$ terraform planTerraform used the selected providers to generate the following executionplan. 先頭の + は「作成する」という意味です。(known after apply) の項目は、実際に作るまで値が決まりません。 最後の行の Plan: 1 to add, 0 to change, 0 to destroy. が、追加・変更・削除の件数の要約です。

では terraform apply で実際に作ります。apply は実行計画をもう一度表示してから確認を求めるので、内容を確かめたうえで yes と入力して Enter を押します。yes 以外を入力すると中止されます。

途中の実行計画は plan と同じなので省略しています。また、plan の最後に出ていた Note: You didn't use the -out option ... は、apply では表示されません。 ファイルができたか確かめます。

Terminal 
$ cat output/hello.txtHello, Terraform!$ ls -la outputtotal 8drwxr-xr-x@ 3 yourname  staff   96 10月  4 12:34 .drwxr-xr-x@ 7 yourname  staff  224 10月  4 12:34 ..-rwxr-xr-x@ 1 yourname  staff   18 10月  4 12:34 hello.txt

output/ ディレクトリは事前に作っていませんが、local_file が作ってくれました。 なお、plan では file_permission = "0777"（既定値）と表示されましたが、実際のファイルの権限は -rwxr-xr-x になっています。手元の umask の設定によって、表示とは違う権限で作られます。

💡

filename の表示が ./output/hello.txt になる理由

main.tf には ${path.module}/output/hello.txt と書きましたが、実行計画では ./output/hello.txt と表示されます。terraform を実行しているディレクトリ自体がモジュールのルートなので、path.module が . になるためです。

✅ 確認ポイント

Apply complete! Resources: 1 added, 0 changed, 0 destroyed. が表示され、cat output/hello.txt で Hello, Terraform! が表示されることを確認してください。

4

state を見る

Terraform は、自分が作ったリソースを state（状態）に記録しています。apply の後、作業ディレクトリに terraform.tfstate というファイルが増えています。 まず、コマンドで state の中身を確認します。

Terminal 
$ terraform state listlocal_file.hello$ terraform state show local_file.hello# local_file.hello:resource "local_file" "hello" {    content              = <<-EOT        Hello, Terraform! terraform state list は、state に記録されているリソースの一覧です。terraform state show <名前> は、1 つのリソースの属性をすべて表示します。 作る前は (known after apply) だった id やハッシュ値が、ここでは確定しています。 terraform show を実行すると、state 全体を同じ形式で表示します（いまはリソースが 1 つなので、出力は state show と同じです）。

何も変えずに、もう一度 plan を実行してみます。

Terminal 
$ terraform planlocal_file.hello: Refreshing state... [id=ae9c7cc6581fe6b7a01af3ee5fa123a4afc9bac1]No changes. Your infrastructure matches the configuration.Terraform has compared your real infrastructure against your configurationand found no differences, so no changes are needed.

1 行目の Refreshing state... は、state に記録された id をもとに実物を読み直している表示です。 Terraform は「設定（main.tf）」「state」「実物」の 3 つを比べて実行計画を作ります。今回は 3 つが一致しているので、No changes. になりました。

⚠️

state は手で編集しない

terraform.tfstate は Terraform が読み書きするファイルです。手で書き換えると、設定や実物との対応が崩れる場合もあります。中身の確認には terraform state list / terraform state show を使いましょう。

✅ 確認ポイント

terraform state list で local_file.hello が表示され、変更なしの plan が No changes. Your infrastructure matches the configuration. を表示することを確認してください。

5

設定を変えて、置換（-/+）を観察する

設定を変えると、Terraform は state と比べて差分を出します。local_file.hello の content を変えてみます。

Diff main.tf 
-  content  = "Hello, Terraform!\n"+  content  = "Hello again, Terraform!\n"
Terminal 
$ terraform planlocal_file.hello: Refreshing state... [id=ae9c7cc6581fe6b7a01af3ee5fa123a4afc9bac1]Terraform used the selected providers to generate the following executionplan. Resource actions are indicated with the following symbols:-/+ destroy and then create replacementTerraform will perform the following actions:  # local_file.hello must be replaced-/+ resource "local_file" "hello" {      ~ content              = <<-EOT # forces replacement          - Hello, Terraform!          + Hello again, Terraform!        EOT      ~ content_base64sha256 = "6wKS0JLRbqCUNW2dBDS6ihyRntb8v6POQLyDI/NZqBY=" -> (known after apply)      …      ~ id                   = "ae9c7cc6581fe6b7a01af3ee5fa123a4afc9bac1" -> (known after apply)        # (3 unchanged attributes hidden)    }Plan: 1 to add, 0 to change, 1 to destroy.…

今度は記号が -/+（destroy and then create replacement）になりました。リソース行には must be replaced、content の行には # forces replacement と付いています。 local_file は content を書き換えて更新する（~ の update）のではなく、いったん削除して作り直す「置換」になります。 どの属性の変更が置換になるかはリソースの種類ごとに決まっていて、# forces replacement がその目印です。 実際のクラウドのリソースでは、置換は「作り直し」を意味するので、plan でこの表示を見落とさないことが大切です。

中ほどの「…」は、ハッシュ値の行（content_md5 など）を省略した箇所です。最後の「…」は、ステップ 3 と同じ Note: の部分です。 apply して確かめます（以降、apply の出力は実行計画の部分を「…」で省略します）。

Terminal 
$ terraform apply…Plan: 1 to add, 0 to change, 1 to destroy.Do you want to perform these actions?  Terraform will perform the actions described above.  Only 'yes' will be accepted to approve.  Enter a value: yeslocal_file.hello: Destroying... [id=ae9c7cc6581fe6b7a01af3ee5fa123a4afc9bac1]local_file.hello: Destruction complete after 0slocal_file.hello: Creating...local_file.hello: Creation complete after 0s [id=5ef8bf606a7ddb96430e62dd3cd11c5cc546b4f8]Apply complete! Resources: 1 added, 0 changed, 1 destroyed.$ cat output/hello.txtHello again, Terraform!$ ls -la terraform.tfstate*-rw-r--r--@ 1 yourname  staff  1645 10月  4 12:34 terraform.tfstate-rw-r--r--@ 1 yourname  staff  1639 10月  4 12:34 terraform.tfstate.backup

Destroying... の後に Creating... が続き、計画どおりに置換されました。 2 回目の apply から、1 つ前の state が terraform.tfstate.backup として残るようになります。

state の serial も増えています（grep serial terraform.tfstate で確かめられます）。serial は state の新旧を見分けるための番号で、state の内容が変わると増えます。1 回の apply で増える数は 1 とは限らず、内容が変わらなければ増えません。

✅ 確認ポイント

plan で -/+ と # forces replacement が表示されること、apply 後の output/hello.txt が Hello again, Terraform! になり、terraform.tfstate.backup ができていることを確認してください。

6

random_pet で依存を作り、手で消したファイルを戻す

2 つ目のリソースとして、ランダムなペットの名前を作る random_pet を追加します。length = 2 で、2 語をつないだ名前になります。 さらに、local_file.hello の content で、その名前（random_pet.greeter.id）を参照します。

Diff main.tf 
+resource "random_pet" "greeter" {+  length = 2+}+ resource "local_file" "hello" {   filename = "${path.module}/output/hello.txt"-  content  = "Hello again, Terraform!\n"+  content  = "Hello, ${random_pet.greeter.id}!\n" }

これで main.tf は完成です。全文は次のとおりです。

HCL main.tf 
terraform {
  required_version = ">= 1.9"

  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.9"
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.9"
    }
  }
}

resource "random_pet" "greeter" {
  length = 2
}

resource "local_file" "hello" {
  filename = "${path.module}/output/hello.txt"
  content  = "Hello, ${random_pet.greeter.id}!\n"
}

出力の順番に注目してください。random_pet.greeter の作成が終わってから、local_file.hello の作成が始まっています。 main.tf では local_file の方を後ろに書いていますが、順番を決めているのは書いた位置ではなく参照です。 random_pet.greeter.id を参照したことで、Terraform は「local_file.hello は random_pet.greeter に依存する」と判断し、依存される側を先に作ります（暗黙の依存）。

ℹ️

ペットの名前は実行ごとに変わる

living-werewolf は執筆時の出力例です。random_pet の値は作成のたびランダムで決まるので、みなさんの環境では別の名前になります。hello.txt の中身や、id のハッシュ値も同様に変わります。一度作った後は state に記録されるので、この後の plan / apply でも同じ名前のまま使われます。

lock ファイル .terraform.lock.hcl は .gitignore に書きません。init の出力でも、バージョン管理に含めるよう案内されていました。

ℹ️

state を共有したいときは

state をコミットしない代わりに、チームで共有するときはリモートのバックエンド（クラウドのストレージなど）に state を置きます。このトラックの 04「リモートステート管理」で扱います。

ℹ️

この教材リポジトリの完成コードについて

完成コードを置いているブランチ infra/terraform/01-basics では、リポジトリのルートの .gitignore が **/.terraform.lock.hcl を無視する設定になっているため、lock ファイルは含まれていません。自分のプロジェクトでは、上のとおり lock ファイルをコミットしてください。

✅ 確認ポイント

terraform destroy が Destroy complete! Resources: 2 destroyed. で終わり、terraform state list が何も表示しないこと、.gitignore に state と .terraform/ が入っていて lock ファイルは入っていないことを確認してください。

つまずきポイント

💡

plan や apply が Inconsistent dependency lock file で止まる

まだ terraform init を実行していないか、別のディレクトリで実行しています。main.tf があるディレクトリで terraform init を実行してください。エラー文には「init していない」とは書かれないので注意しましょう。

💡

apply が Apply cancelled. で終わる

確認プロンプト Enter a value: には yes と入力する必要があります。y や Yes など yes 以外を入力すると、Apply cancelled. と表示され、何も変更されずに終わります。

💡

内容を変えただけなのに「置換」になる

local_file は、content を変えると更新ではなく置換（-/+）になります。故障ではありません。plan で # forces replacement の付いた属性が、置換の原因です。

まとめ

init でプロバイダーを取得し、plan で実行計画を確かめてから apply で反映する、という Terraform の基本の流れを体験しました。 Terraform は設定・state・実物の 3 つを比べて計画を作ること、設定の変更が置換になる場合があること、参照から作成の順番が決まることも確かめました。 次の項目では、変数（variables）とアウトプット（outputs）を使って、設定に値を渡したり結果を取り出したりできるようにします。
