リモートステート管理

  • ⏱ 所要時間: 60分
  • 📊 難易度: 入門
  • 👤 対象: モジュールを使った Terraform の設定を書けるようになり、state をチームで共有する方法を知りたい人
  • 📋 前提: 03 で作った 03-modules ディレクトリが手元にあること。Docker が使えること（Docker Desktop や Rancher Desktop など）。クラウドのアカウントは不要
  • 🔗 前提となる項目: 03: モジュール化

🎯 このレッスンで学ぶこと

  • backend "s3" を書き、terraform init -migrate-state でローカルの state をリモートへ移す
  • リモートの state で plan / apply し、terraform state pull で中身を確かめる
  • use_lockfile によるロックで同時実行が止まることを確かめ、-lock-timeout と force-unlock の使いどころを知る
  • 別の作業ディレクトリから同じ state を共有する
  • -backend-config で環境ごとの設定を分け、鍵はファイルに書かず環境変数で渡す

概要

01〜03 では、state を作業ディレクトリの terraform.tfstate に保存してきました。1 人で試すにはこれで十分ですが、チームで同じインフラを管理するには困ります。 state が各自の PC にあると、互いの変更が見えません。2 人が同時に apply すると、state が食い違ったり壊れたりします。

そこで実務では、state を Amazon S3 や Google Cloud Storage などの共有ストレージに置き、全員が同じ state を読み書きします。state の保存先を決める仕組みをバックエンドと呼び、ストレージに置く方式をリモートバックエンド（リモートステート）と呼びます。

この項目では、クラウドのアカウントを使わずに同じ流れを体験します。S3 互換のストレージ SeaweedFS を手元の Docker で動かし、Terraform の s3 バックエンドで接続します。 s3 バックエンドの設定のうち、endpoints や skip_* は、接続先を AWS から手元の S3 互換サーバーに向けるためのものです。本物の S3 を使うときは書きません。

設定役割本物の S3 では
bucket / keystate を置くバケットと、バケット内のパス書く（必須）
regionバケットのリージョン書く
use_lockfileバケットに .tflock を置いてロックする書く
endpoints（s3）接続先を AWS ではなく http://localhost:8333 に変える不要
use_path_styleバケット名をホスト名（tfstate.localhost）ではなく URL のパスに入れる不要
skip_credentials_validation鍵が有効かを AWS の STS に問い合わせない不要
skip_requesting_account_idAWS のアカウント ID を STS や IAM に問い合わせない不要
skip_metadata_api_checkEC2 のメタデータ API を確認しない不要
skip_region_validationリージョン名が AWS に実在するかを検証しない不要

つまり、上の 4 行（bucket・key・region・use_lockfile）が実務でもそのまま使う部分です。なお、HashiCorp は S3 互換のストレージへの対応を「best effort」（できる範囲での対応）としています。詳しくは s3 backend の Support for "S3 Compatible" Storage Providers を参照してください。 SeaweedFS で動くことは執筆時の版で確かめていますが、学習用の置き場所と考えてください。

管理するリソースは、これまでと同じく hashicorp/local と hashicorp/random だけです。

ℹ️

使用バージョン

動作を確認したのは Terraform v1.16.2（darwin_arm64）、hashicorp/local v2.9.1、hashicorp/random v3.9.1 です。S3 互換ストレージには SeaweedFS の chrislusf/seaweedfs:4.48 を使いました。Docker は Rancher Desktop（Docker Engine 29.5.3）を使いました。バージョンは執筆時点（2026年10月）のものです。 確認した環境は macOS（zsh）です。コマンドは macOS のシェルで書いています。 掲載している出力は色なし（-no-color 相当）で取得したものです。

2

SeaweedFS を起動してバケットを用意する

state の置き場所になる S3 互換ストレージ SeaweedFS を、Docker で起動します。SeaweedFS の weed mini は、1 つのコンテナで S3 互換の API を提供するモードです。 オプションの変更に備えて、イメージのタグは 4.48 に固定します。

まず、SeaweedFS の S3 API が使うポート 8333 の空きを確かめます。何も表示されなければ空いています。

Terminal 
$ lsof -nP -iTCP:8333 -sTCP:LISTEN

次に、この端末に認証情報を設定します。値は SeaweedFS 用に決めたダミーの鍵です。本物の AWS の鍵は使わないでください。 この後のコマンドはすべて、この設定をした端末で実行します（ステップ 5 で開く 2 つ目の端末でも、同じ設定をします）。

Terminal 
$ unset AWS_PROFILE AWS_SESSION_TOKEN$ export AWS_ACCESS_KEY_ID=tf04access AWS_SECRET_ACCESS_KEY=tf04secret123456 AWS_EC2_METADATA_DISABLED=true
  • AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY: Terraform の s3 バックエンドが使う鍵です。同じ値を SeaweedFS の起動時にも渡し、管理者の鍵として登録させます
  • unset AWS_PROFILE AWS_SESSION_TOKEN: AWS_PROFILE で ~/.aws の名前付きプロファイルを使う設定を外します。AWS_SESSION_TOKEN は、一時的な認証情報のトークンが残っていれば外します
  • AWS_EC2_METADATA_DISABLED=true: AWS の SDK が EC2 のインスタンスメタデータサービス（IMDS）へ認証情報を取りにいくのを止めます。backend の skip_metadata_api_check と同じ目的の保険です
⚠️

本物の AWS へ接続しないために

この項目の backend "s3" には、skip_credentials_validation と skip_requesting_account_id を書きます。どちらも、AWS の STS（認証の窓口）へ問い合わせないための設定です。 これらを外すと、Terraform は手元の SeaweedFS ではなく本物の AWS（STS）へ問い合わせにいきます。ダミーの鍵なので 403 InvalidClientTokenId などで失敗しますが、アクセスキー ID と署名付きのリクエストが本物の AWS に届きます。

教材のとおりに書けば、接続先は手元の SeaweedFS だけです。本物の AWS の認証情報を環境変数や ~/.aws に設定している人は、上の unset と export を省かないでください。

SeaweedFS を起動します。最後の -bucket=tfstate で、起動と同時にバケット tfstate も作られます。

3

backend "s3" を書いて state を移す

main.tf の terraform ブロックに、backend "s3" ブロックを追加します。あわせて required_version を >= 1.10 に上げます。ロックの設定 use_lockfile が Terraform 1.10 で追加された機能だからです（1.11 で正式版になり、従来の DynamoDB によるロックは非推奨になりました）。

2 つの端末でロックを確かめる

force-unlock は最後の手段

エラー文にもあるとおり、force-unlock は危険な操作です。ロックを持っている操作がまだ動いているときに外すと、2 人が同時に state を書き換えられる状態になります。Lock Info の Who と Created を見て、その操作が本当に終わっている（異常終了した）ことを確かめてから使ってください。-lock=false でロックを無効にすることも勧められません。

演習

以下のチェックリストを使って、このレッスンの内容を振り返りましょう。

つまずきポイント

💡

Error: Backend initialization required で止まる

backend ブロックを追加・変更したのに、init し直していません。ローカルの state を移すなら terraform init -migrate-state を実行してください。state を移さず設定だけを切り替えるなら terraform init -reconfigure です。

💡

移したはずなのに plan が全リソースを「+ create」と言う

use_path_style = true が抜けていないか確かめてください。抜けていると、Terraform はバケット名をホスト名に入れた tfstate.localhost:8333 へ接続します。SeaweedFS はこれを別のバケット（パスの先頭の handson）への要求として扱うので、state が見つからず、エラーにならないまま空の state として扱われます。この状態で apply すると、同じリソースをもう一度作ろうとします。

💡

Error: Error acquiring the state lock で止まる

別の端末や別の人の操作がロックを持っています。Lock Info の Who と Created で誰の操作かを確かめ、終わるのを待つか、-lock-timeout=60s のように待ち時間を付けて実行してください。持ち主の操作が異常終了していると確かめられた場合に限り、terraform force-unlock <ID> でロックを外します。

💡

操作の最後に Error: Error releasing the state lock が出る

実行中に、別の端末から force-unlock でロックを外された場合に出ます。ロックのファイル（.tflock）が既に無いので、解放に失敗したという意味です。force-unlock した覚えがない場合は、誰かが外していないかをチームで確かめてください。

💡

別のディレクトリで plan すると local_file が作り直しになる

state は共有されていますが、local_file が作るファイルは最初に apply した人のディスクにしかないためです。この教材の題材に特有の挙動で、クラウド上のリソースを管理する場合は起きません。

💡

Error: Missing Required Value（The attribute "bucket" is required）で止まる

partial configuration にした backend ブロックに対して、-backend-config を付けずに init しています。terraform init -reconfigure -backend-config=backend.hcl のように、値を書いたファイルを渡してください。-input=false を付けずに実行すると、エラーの代わりに Enter a value: で bucket の入力を求められます。

まとめ

backend "s3" を書いて init -migrate-state するだけで、state の置き場所をローカルのファイルからリモートのストレージに移せました。リモートの state は、別のディレクトリ（別の人）からも init するだけで共有できます。 use_lockfile = true により、同時の操作はロックで止まります。force-unlock は、持ち主の操作が終わっていると確かめたうえで使う最後の手段です。 環境ごとに変わる値は -backend-config で分けます。鍵は設定ファイルに書かず、環境変数などで渡します。

実務で使う主なバックエンドは次のとおりです。設定項目は公式ドキュメントを参照してください。

  • s3: Amazon S3 に置きます。この項目で使った bucket・key・region・use_lockfile をそのまま使います
  • gcs: Google Cloud Storage に置きます
  • azurerm: Azure Blob Storage に置きます
  • HCP Terraform: HashiCorp のサービスに state を置き、実行やチームの権限もまとめて管理します。backend ブロックではなく cloud ブロックで設定します

これで Terraform サブトラックは終わりです。01 で init / plan / apply の流れと state の役割を学びました。02 では入力変数と出力値で値をやり取りし、03 ではモジュールで設定を部品にしました。04 では state をリモートで共有管理しました。 この 4 つは、どのクラウドを相手にしても変わらない Terraform の基本です。次は各クラウドのサブトラック（Google Cloud / AWS / Azure / Cloudflare）に進み、本物のクラウドのリソースを Terraform で構築します。
