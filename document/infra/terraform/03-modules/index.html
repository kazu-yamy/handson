モジュール化

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: 入力変数・出力値・ローカル値を使って Terraform の設定を書けるようになった人
  • 📋 前提: 02 で作った 02-variables-outputs ディレクトリ（main.tf・variables.tf・outputs.tf・terraform.tfvars・.gitignore）が手元にあること。クラウドのアカウントは不要
  • 🔗 前提となる項目: 02: 変数とアウトプット

🎯 このレッスンで学ぶこと

  • 設定の一部を子モジュール（modules/greeting/）に切り出し、module ブロックで呼び出す
  • モジュールを追加したら init が必要なこと、モジュールの中を編集しただけなら不要なことを確かめる
  • モジュールに移すとリソースのアドレスが変わることを知り、moved ブロックで作り直しを避ける
  • モジュールの出力値を module.<名前>.<出力名> で受け取る
  • for_each で同じモジュールを複数回呼び出し、結果を for 式でまとめる

概要

02 では、入力変数で値を受け取り、出力値で結果を返せるようにしました。この項目では、その設定の一部をモジュールとして切り出し、部品として呼び出せるようにします。 02 で作った入力変数と出力値は、そのままモジュールの「入口」と「出口」になります。

すでに apply 済みのリソースをモジュールへ移すと、Terraform はそのリソースを別物とみなし、作り直そうとします。これを moved ブロックで避ける方法も、実際に作り直しの計画を見ながら確かめます。 使うのはこれまでと同じく hashicorp/local と hashicorp/random だけで、クラウドのアカウントや料金の心配はありません。

ℹ️

使用バージョン

Terraform v1.16.2（darwin_arm64）/ hashicorp/local v2.9.1 / hashicorp/random v3.9.1 で動作を確認しています。バージョンは執筆時点（2026年10月）のものです。 掲載している出力は色なし（-no-color 相当）で取得したものです。

ℹ️

ペットの名前は実行ごとに変わる

helped-killdeer は執筆時の出力例です。random_pet の値は作成のたびにランダムで決まるので、みなさんの環境では別の名前になります。id のハッシュ値も同様です。以降の出力に出てくる helped-killdeer（ステップ 6 で作る splendid-seasnail も）は、自分の環境の名前に読み替えてください。

state の中でリソースを指す名前を「アドレス」と呼びます。いま state に入っているアドレスは、random_pet.greeter・local_file.hello・local_sensitive_file.token の 3 つです。この後、モジュールに移すとアドレスがどう変わるかに注目します。

2

あいさつ文の部分をモジュールに切り出す

Terraform のモジュールは、.tf ファイルを置いたディレクトリのことです。これまで作業してきた 03-modules 自身も「ルートモジュール」と呼ばれるモジュールです。 ルートモジュールから別のディレクトリを module ブロックで呼び出すと、そのディレクトリの中身を部品として使えます。呼び出される側を「子モジュール」と呼びます。

あいさつ文を作る部分（random_pet・local_file・関連するローカル値）を、子モジュール modules/greeting/ に移します。ダミーのトークン（local_sensitive_file.token と変数 api_token）はルートに残します。

Terminal 
$ mkdir -p modules/greeting

モジュールの中身は、ルートと同じく main.tf・variables.tf・outputs.tf に分けて書きます。まず modules/greeting/main.tf です。

HCL modules/greeting/main.tf 
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = ">= 2.0"
    }
    random = {
      source  = "hashicorp/random"
      version = ">= 3.0"
    }
  }
}

locals {
  greeting_text = var.shout ? upper(var.greeting) : var.greeting
  message       = "${local.greeting_text}, ${random_pet.greeter.id}! (by ${var.owner})\n"
}

resource "random_pet" "greeter" {
  length = var.pet_length
}

resource "local_file" "hello" {
  filename = "${var.output_dir}/hello.txt"
  content  = local.message
}

リソースとローカル値は、ルートの main.tf から移したものです。違いは local_file の filename です。02 ではルートで "${path.module}/output" と書いていました。 path.module は「その式が書かれているモジュールのディレクトリ」を表します。ルートでは . でしたが、子モジュールの中に書くと modules/greeting を指します。 そのままモジュールに移すと、ファイルの出力先が modules/greeting/output/ に変わってしまいます。そこで、出力先のディレクトリは変数 output_dir として呼び出し側から受け取ります。

先頭の terraform ブロックでは、モジュールが使うプロバイダーを required_providers で宣言しています。モジュール側では source と緩い下限（>= 2.0 / >= 3.0）だけを書きます。 実際に使うバージョンの範囲（~> 2.9 / ~> 3.9）を決めるのはルートです。ルートとモジュールの制約は、両方を満たすバージョンが選ばれます。モジュールには provider ブロックは書きません（プロバイダーの設定はルートから引き継がれます）。この項目では、モジュール側の required_version も省略しています。

次に、モジュールの入力変数を modules/greeting/variables.tf に書きます。モジュールの変数は、呼び出し側から値を受け取る「入口」です。

HCL modules/greeting/variables.tf 
variable "greeting" {
  type        = string
  description = "ファイルに書くあいさつ文"
  default     = "Hello"
}

variable "owner" {
  type        = string
  description = "ファイルの作成者名"
}

variable "pet_length" {
  type        = number
  description = "random_pet の名前を構成する単語の数（1〜5）"
  default     = 2

  validation {
    condition     = var.pet_length >= 1 && var.pet_length <= 5
    error_message = "pet_length は 1 以上 5 以下で指定してください。"
  }
}

variable "shout" {
  type        = bool
  description = "true にするとあいさつ文を大文字にする"
  default     = false
}

variable "output_dir" {
  type        = string
  description = "あいさつファイルを書き出すディレクトリ"
}

greeting・owner・pet_length・shout はルートの変数と同じ形です。pet_length の範囲を検査する validation も、値を実際に使うモジュール側へ移しました。最後の output_dir が新しく追加した変数です。

モジュールの出力値は modules/greeting/outputs.tf に書きます。こちらは呼び出し側へ値を返す「出口」です。

HCL modules/greeting/outputs.tf 
output "hello_path" {
  description = "生成したあいさつファイルのパス"
  value       = local_file.hello.filename
}

output "pet_name" {
  description = "random_pet が作った名前"
  value       = random_pet.greeter.id
}

ルートの main.tf は、移したリソースとローカル値を消し、代わりに module ブロックでモジュールを呼び出します。

4

moved ブロックで作り直しを避ける

リソースのアドレスが変わったことを Terraform に伝えるのが moved ブロックです。from に古いアドレス、to に新しいアドレスを書きます。 ルートに moved.tf を新しく作ります（ファイル名は自由です）。

HCL moved.tf 
moved {
  from = random_pet.greeter
  to   = module.greeting.random_pet.greeter
}

moved {
  from = local_file.hello
  to   = module.greeting.local_file.hello
}

つまずきポイント

💡

Error: Module not installed で止まる

💡

モジュールに移しただけなのに destroy と create が出る

リソースのアドレスが module.<名前>. 付き（for_each を付けた場合は module.<名前>["キー"]）に変わったためです。そのまま apply せず、古いアドレスから新しいアドレスへの moved ブロックを書いてから plan し直してください。has moved to と表示され、作り直しが消えれば成功です。

💡

Error: Unsupported attribute で止まる

モジュールが output で公開していない値を、module.<名前>.xxx で参照しています。エラー文の object with 2 attributes の数が、モジュールの出力値の数です。必要な値は、モジュールの outputs.tf に output として追加してください。

💡

Error: Invalid value for variable がモジュールを呼び出す行を指す

モジュールの入力変数の validation に違反しています。エラーの位置は呼び出し側（ルートの main.tf）の行ですが、ルールの場所はエラー文の末尾（This was checked by the validation rule at modules/greeting/variables.tf:17,3-13.）に表示されます。

💡

ファイルが modules/greeting/output/ にできてしまう

モジュールの中で path.module を使うと、モジュールのディレクトリ（modules/greeting）を指します。出力先はこの項目のように変数で受け取り、ルートから "${path.module}/output" を渡してください。

まとめ

設定の一部を子モジュールに切り出し、module ブロックで呼び出せるようになりました。モジュールの入力変数が「入口」、出力値が「出口」で、モジュールの中のローカル値やリソースは外から見えません。 既存のリソースをモジュールへ移したり for_each を付けたりするとアドレスが変わり、そのままでは作り直しになります。moved ブロックで移動を伝えれば、リソースを保ったまま構成を変えられます。

この項目ではローカルパスのモジュールだけを扱いました。source には、Terraform Registry で公開されているモジュールや Git リポジトリなども指定できます。詳しくは参考資料の module block reference（source）を参照してください。 次の項目では、これまで手元のファイルに置いていた state を、リモートのバックエンドで共有管理します。
