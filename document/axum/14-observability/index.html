可観測性と graceful shutdown

  • ⏱ 所要時間: 45分
  • 📊 難易度: 初級
  • 👤 対象: 13 までの API に、本番で調べやすいログ、ヘルスチェック、安全な停止を足したい人
  • 📋 前提: Rust の基本文法、04 のミドルウェア、08 の結合テスト、12 の layers::apply（層の順番）、13 の CORS とセキュリティヘッダー
  • 🔗 前提となる項目: 13: HTTP の防御層

🎯 このレッスンで学ぶこと

  • println! を tracing に置き換え、RUST_LOG で出力量を、LOG_FORMAT=json で形式を切り替える
  • tower-http の TraceLayer とリクエスト ID の層で、エラーやプリフライトを含む全ての応答に x-request-id を付け、ログと突き合わせる
  • 層の順番（ID の発行 → 応答への付与 → 機密ヘッダーの伏せ字 → ログ）を、実測を元に説明できる
  • /health（プロセスが生きているか）と /ready（DB に届くか）を使い分ける
  • SIGTERM と Ctrl + C で、処理中のリクエストを終えてから止まるようにする

概要

13 までのサーバーは、println! で 1 リクエスト 1 行のログを出していました。例えば POST /auth/login -> 500 Internal Server Error (67.292µs) のような行です。これでは、次のことができません。

  • 出力量を変える: 調査のときだけ詳しく出す、普段は警告だけにする、といった切り替えができない。
  • 機械で読む: ログ収集の基盤（Cloud Logging など）に渡しやすい JSON で出せない。
  • 1 件のリクエストを追う: 利用者から「さっきのリクエストが 500 になった」と言われても、どのログの行か特定できない。

また、サーバーを止める方法は Ctrl + C でプロセスを殺すことだけでした。処理中のリクエストがあっても、その場で打ち切られます。

このレッスンでは、ログ・リクエスト ID・ヘルスチェック・停止の 4 つを整えます。直す前と直した後は次のとおりです。

観点直す前（13 のまま）直した後ステップ
ログの出し方println! / eprintln!tracing。RUST_LOG で量、LOG_FORMAT=json で形式を切り替える2
リクエスト IDなし全ての応答に x-request-id。ログの request_id と同じ値3
ヘルスチェック/health だけ/health に加えて、DB に届くかを見る /ready4
SIGTERM を受けたときその場で終わる（終了コード 143）処理中のリクエストを終えてから終わる（終了コード 0）5

subscriber を初期化する

新しいファイル src/telemetry.rs を作ります。

Rust src/telemetry.rs 
use std::io::IsTerminal;
use tracing_subscriber::{EnvFilter, fmt, layer::SubscriberExt, util::SubscriberInitExt};

// ログの出力先（subscriber）を作って、プロセスに 1 つだけ登録する。
// 2 回呼ぶと panic するので、main からだけ呼ぶ（テストからは呼ばない）
pub fn init() {
    // RUST_LOG が無い、または書式が壊れているときは info 以上を出す
    let filter = EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"));
    let registry = tracing_subscriber::registry().with(filter);

    if std::env::var("LOG_FORMAT").is_ok_and(|value| value == "json") {
        // 1 行 1 JSON。ログ収集の基盤（Cloud Logging や Datadog など）に渡しやすい形
        registry.with(fmt::layer().json()).init();
    } else {
        // 色の escape sequence は、出力先が端末のときだけ付ける（ファイルにリダイレクトしたときに混ざらないように）
        registry
            .with(fmt::layer().with_ansi(std::io::stdout().is_terminal()))
            .init();
    }
}
  • EnvFilter::try_from_default_env() は、環境変数 RUST_LOG を読みます。無いときは info 以上を出します。ただし、空の値（RUST_LOG=）は「無い」扱いにならず、ログが 1 行も出なくなります。.env にも空の値で書かないでください（つまずきポイント）。
  • LOG_FORMAT=json のときだけ JSON で出します。それ以外は人が読むテキストです。
  • 色（ANSI の escape sequence）は、出力先が端末のときだけ付けます。ファイルにリダイレクトしたログに制御文字が混ざらないようにするためです。
  • init() は、プロセスに 1 つだけの subscriber を登録します。2 回呼ぶと panic するので、main からだけ呼びます（つまずきポイント）。

make_span は自作しています。tower-http の DefaultMakeSpan は、method・uri・version と（指定すれば）ヘッダー全部を span に入れる作りです。x-request-id だけを入れることはできません。自作の make_span では、次の 3 つだけを span に入れます。

  • method
  • path: パスだけで、クエリ文字列は入れません。13 の log_request はクエリ付きの URI を出していました。?token=... のような値をログに残さないために、パスだけにします。

RUST_LOG を変えたのに、出力が変わらない

RUST_LOG の書式が壊れていると、エラーや警告を出さずに、黙って既定の info に戻ります。これは tracing-subscriber の性質ではありません。src/telemetry.rs が try_from_default_env() の Err を unwrap_or_else で info のフィルターに置き換えているためです。執筆時に RUST_LOG='app::layers=bogus[[' で起動したところ、出力は既定と同じでした。対象の名前を間違えたときは、何も言われず出力が出ないだけです。このプロジェクトの名前は、lib クレートが app、bin が server、tower-http が tower_http です。

💡

ログが 1 行も出ない

RUST_LOG が空の値（RUST_LOG=）になっていないか確かめてください。空の値は書式の誤りとは扱われないので、既定の info に戻りません。何も指定しないフィルターになり、既定の ERROR だけが通るので、起動ログもリクエストのログも出ません。執筆時に RUST_LOG= で起動し、3 つのリクエストを送ったところ、ログは 0 バイトでした。.env に書くときも空にせず、使わないなら .env.example のように行ごとコメントにします。

💡

ログに request{...}: の部分が出ない

DefaultMakeSpan を使っている場合、span の既定のレベルは DEBUG なので、RUST_LOG=info では span が丸ごと出ません。.level(Level::INFO) を付けるか、このレッスンのように info_span! で作ってください（ステップ 3 の読み物）。

💡

プリフライトの応答にだけ x-request-id が付かない

PropagateRequestIdLayer が CORS より内側にあります。SetRequestIdLayer の直後（TraceLayer の外側）に置いてください（ステップ 3）。the_cors_preflight_response_also_has_a_request_id のテストが、この位置を守ります。

💡

ブラウザのアプリから x-request-id を読めない

CORS の access-control-expose-headers に x-request-id を入れていないからです（ステップ 3 の CORS の読み物）。expose するかは、このレッスンでは決めていません。

💡

SIGTERM を送ってもプロセスが終わらない

閉じていない接続が残っていないか確かめてください。with_graceful_shutdown は、全ての接続が終わるまで待ちます（ステップ 5 の注意）。

まだ残っていること

このレッスンで、ログを調べやすくし、安全に止められるようにしました。一方で、次の課題は残っています。執筆時に確かめていないことも含めて挙げます。

  • クライアントが送る x-request-id の検証: 送られた値をそのまま採用し、長さや文字種を確かめていません。信用できない相手からの値は捨てて振り直す、といった対策は実装していません。
  • ASCII 以外を含む x-request-id: ASCII 以外の文字を含む値を送ると、ログの request_id は "-" になり、応答には元の値が返るので、両者が一致しません。
  • ブラウザからの x-request-id: CORS で expose していないので、ブラウザの JavaScript からは読めません。
  • DB が応答しないときの /ready: 確かめたのは、プールを閉じて即座にエラーになる場合（503）だけです。DB が応答せずに待たされる場合の挙動は確かめていません。
  • 停止の待ち時間の上限: 閉じない接続があると、プロセスが終わりません。上限を付ける処理は実装していません（16 のコンテナ化で、停止の猶予時間に触れます）。
  • 401 などの理由: 500 系は tracing::error! で詳細をログに出しますが、401・403 などは、ログにステータスが出るだけで理由は出ません。
  • JSON ログの長さ: span の内容が span と spans の両方に出るので、1 行が長くなります。
