🎯 このレッスンで学ぶこと

  • tests/ ディレクトリに結合テストを書き、cargo test で実行する

  • http_body_util::BodyExt::collect でレスポンスの本文を読み、JSON として検査する

概要

07 までは、サーバーを起動して curl でリクエストを送り、応答を目で見て確かめていました。 コードを変えるたびに同じ確認を手で繰り返すのは手間がかかり、見落としも出ます。 このレッスンでは、その確認を cargo test で自動で実行できるようにします。

Axum の Router は tower の Service なので、サーバーを起動せず、ポートも使わずに、テストのコードから直接リクエストを渡せます。 DB は sqlx の #[sqlx::test] を使い、テストごとにマイグレーション済みの専用の DB を用意します。 09 以降の項目では、機能を足すたびにこの tests/ へテストを足し、最後に cargo test の全件成功を確かめながら進めます。

項目07（curl で確かめる）08（結合テスト）
サーバー起動する起動しない
ポート8080 で待ち受ける使わない（Router に直接リクエストを渡す）
DBapp.dbテストごとに作られる専用の DB
結果の判定出力を目で見るassert_eq! で自動で判定する
ℹ️

使用バージョン

Rust（rustc）1.99.0 / cargo 1.99.0（Rust edition 2024）で動作を確認しています。

クレートは 07 と同じです。axum 0.8.9 / tokio 1.53.1 / serde 1.0.229 / serde_json 1.0.151 / sqlx 0.9.0 / dotenvy 0.15.7 を使います。テスト用に tower 0.5.3（util feature）と http-body-util 0.1.5 を [dev-dependencies] に追加します。バージョンは執筆時点（2026年10月）のものです。

2

テスト用のクレートを追加し、/health を呼ぶテストを書く

テストだけで使うクレートを 2 つ追加します。--dev を付けると、[dependencies] ではなく [dev-dependencies] に追加されます。[dev-dependencies] のクレートはテストのビルドにだけ使われ、実行ファイル server には入りません。Features: の一覧は一部を省略しています。

Terminal

tokio・serde_json・sqlx は [dependencies] にあるので、テストからもそのまま使えます。tokio は macros feature 入りで追加済みなので、[dev-dependencies] に足す必要はありません。sqlx の既定の feature には macros と migrate が含まれているので、ステップ 3 で使う #[sqlx::test] も追加の設定なしで使えます。

最初のテストとして、07 で curl localhost:8080/health で確かめていた GET /health を、テストのコードから呼び出します。tests ディレクトリを作り、tests/health.rs を次の内容で作成します。

Terminal 
$ mkdir tests
Rust tests/health.rs 
use app::{build_app, config::Config, state::AppState};
use axum::{
    body::Body,
    http::{Request, StatusCode},
};
use http_body_util::BodyExt;
use sqlx::SqlitePool;
use std::sync::Arc;
use tower::ServiceExt;

#[tokio::test]
async fn health_returns_ok() {
    let pool = SqlitePool::connect("sqlite::memory:").await.unwrap();
    let config = Config {
        host: "127.0.0.1".to_string(),
        port: 0,
        database_url: "sqlite::memory:".to_string(),
        api_key: "test-api-key".to_string(),
    };
    let app = build_app(AppState {
        pool,
        config: Arc::new(config),
    });

    let response = app
        .oneshot(Request::get("/health").body(Body::empty()).unwrap())
        .await
        .unwrap();

    assert_eq!(response.status(), StatusCode::OK);
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let json: serde_json::Value = serde_json::from_slice(&bytes).unwrap();
    assert_eq!(json, serde_json::json!({ "status": "ok" }));
}
  • tests/ に置いたファイルは、それぞれが独立したテスト用のクレートとしてビルドされます。外から見たライブラリ app を使うので、use app::... で参照します。07 でコードを lib.rs に分けたのは、このためでもあります。
  • Config は Config::from_env を使わずに直接作ります。テストの結果が .env や環境変数に左右されないようにするためです。API キーには、本物ではない固定のダミー値 test-api-key を使います。host・port・database_url は main.rs でしか使わないので、テストでは使われません。
  • sqlite::memory: は、ファイルを作らないメモリ上の DB です。/health は DB を使わないので、ここでは空の DB で足ります。
  • app.oneshot(request): Router に 1 つのリクエストを渡し、レスポンスを受け取ります。HTTP サーバーを起動せず、ポートも使いません。oneshot は ServiceExt のメソッドなので、use tower::ServiceExt; が必要です。
  • oneshot(...).await の結果は Result<Response, Infallible> です。Router はエラーを返さない（エラーもレスポンスとして返す）ので、unwrap() は常に成功します。
  • oneshot は Router を消費します（引数の self を受け取ります）。同じ app で 2 回呼ぶ方法はステップ 3 で扱います。
  • response.into_body().collect().await で本文を最後まで読み、to_bytes() でバイト列にします。それを serde_json::Value に変換し、json! で書いた期待値と比べます。
  • #[tokio::test] は、非同期のテスト関数を tokio のランタイムで実行する属性です。

3

#[sqlx::test] でテスト専用の DB を使う

次は POST /users でユーザーを作り、GET /users/{id} で取り出せることを確かめます。ただし、ステップ 2 の sqlite::memory: の DB は空で、users テーブルがありません。テーブルを作るマイグレーションを、テストの中で毎回実行する必要があります。

そこで、sqlx の #[sqlx::test] を使います。#[sqlx::test] を付けたテスト関数は、migrations/ のマイグレーションを適用済みの DB を、引数の SqlitePool として受け取れます。DB はテスト関数ごとに別のものが作られます。tests/users.rs を次の内容で作成します。

Rust tests/users.rs 
use app::{build_app, config::Config, state::AppState};
use axum::{
    body::Body,
    http::{Request, StatusCode},
};
use http_body_util::BodyExt;
use sqlx::SqlitePool;
use std::sync::Arc;
use tower::ServiceExt;

fn test_app(pool: SqlitePool) -> axum::Router {
    let config = Config {
        host: "127.0.0.1".to_string(),
        port: 0,
        database_url: "unused".to_string(),
        api_key: "test-api-key".to_string(),
    };
    build_app(AppState {
        pool,
        config: Arc::new(config),
    })
}

#[sqlx::test]
async fn create_then_get_user(pool: SqlitePool) {
    let app = test_app(pool);

    let request = Request::post("/users")
        .header("x-api-key", "test-api-key")
        .header("content-type", "application/json")
        .body(Body::from(r#"{"name":"alice"}"#))
        .unwrap();
    let response = app.clone().oneshot(request).await.unwrap();
    assert_eq!(response.status(), StatusCode::CREATED);
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let created: serde_json::Value = serde_json::from_slice(&bytes).unwrap();
    assert_eq!(created["name"], "alice");
    let id = created["id"].as_i64().unwrap();

    let response = app
        .oneshot(
            Request::get(format!("/users/{id}"))
                .body(Body::empty())
                .unwrap(),
        )
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::OK);
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let fetched: serde_json::Value = serde_json::from_slice(&bytes).unwrap();
    assert_eq!(fetched, serde_json::json!({ "id": id, "name": "alice" }));
}
  • #[sqlx::test] は、テスト用の DB を作ってマイグレーションを適用し、非同期のテスト関数を実行するところまで受け持ちます。#[tokio::test] は付けません（両方を付けた場合の失敗はステップ 6 で見ます）。
  • test_app: テスト用の Config と受け取った pool から Router を作る関数です。database_url は使われないので "unused" にしています。
  • oneshot は Router を消費するので、1 回目は app.clone() を渡し、2 回目に app そのものを渡します。Router の clone は軽い処理です。
  • 1 回目のレスポンスから created["id"] を取り出し、2 回目の URL に使います。serde_json::Value は ["name"] のようにキーで中身を取り出せます。

テストを実行する前後で、本番用の DB ファイル app.db と、テスト用の DB の置き場所を確かめます。--test users を付けると、tests/users.rs のテストだけを実行します。

Terminal 
$ ls app.db* ; ls target/sqlxzsh: no matches found: app.db*ls: target/sqlx: No such file or directory$ cargo test --test users   Compiling integration-test v0.1.0 (/path/to/08-integration-test)    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.76s     Running tests/users.rs (target/debug/deps/users-a6ec1a5383ee42fd)running 1 testtest create_then_get_user ... oktest result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s$ ls app.db*; ls target/sqlx/test-dbszsh: no matches found: app.db*users

no matches found は zsh の表示で、該当するファイルが無いという意味です。

  • テスト用の DB は、target/sqlx/test-dbs/<テストのファイル名>/<テスト関数名>.sqlite に作られます。
  • テストが成功すると DB ファイルは削除され、target/sqlx/test-dbs/users/ は空のディレクトリだけが残ります。失敗したときは DB ファイルが残ります（ステップ 6 で確かめます）。
  • app.db はテストの前後とも作られません。.env の DATABASE_URL も使われません。テストを何度実行しても、開発用の DB の中身は変わりません。

✅ 確認ポイント

1 passed が表示され、target/sqlx/test-dbs/users ディレクトリができていれば OK です。app.db は作られません。

4

異常系のテストを足す

正しいリクエストだけでなく、間違ったリクエストに正しくエラーを返すことも確かめます。07 で curl を使って確かめた次の 4 つをテストにします。

リクエスト期待するステータスerror.code
x-api-key を付けずに POST /users401 Unauthorizedunauthorized
POST /users に空白だけの name422 Unprocessable Entityvalidation_failed（error.fields.name も付く）
存在しない id で GET /users/999404 Not Foundnot_found
POST /users に壊れた JSON400 Bad Requestbad_request

テストが増えると、リクエストを送って本文を JSON にする処理が何度も出てきます。そこで、ファイルの中に補助関数 send と post_user を作ります。tests/users.rs を次の内容に置き換えます。

Rust tests/users.rs 
use app::{build_app, config::Config, state::AppState};
use axum::{
    body::Body,
    http::{Request, StatusCode},
};
use http_body_util::BodyExt;
use sqlx::SqlitePool;
use std::sync::Arc;
use tower::ServiceExt;

fn test_app(pool: SqlitePool) -> axum::Router {
    let config = Config {
        host: "127.0.0.1".to_string(),
        port: 0,
        database_url: "unused".to_string(),
        api_key: "test-api-key".to_string(),
    };
    build_app(AppState {
        pool,
        config: Arc::new(config),
    })
}

async fn send(app: axum::Router, request: Request<Body>) -> (StatusCode, serde_json::Value) {
    let response = app.oneshot(request).await.unwrap();
    let status = response.status();
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let json = serde_json::from_slice(&bytes).unwrap();
    (status, json)
}

fn post_user(api_key: Option<&str>, body: &'static str) -> Request<Body> {
    let mut builder = Request::post("/users").header("content-type", "application/json");
    if let Some(key) = api_key {
        builder = builder.header("x-api-key", key);
    }
    builder.body(Body::from(body)).unwrap()
}

#[sqlx::test]
async fn create_then_get_user(pool: SqlitePool) {
    let app = test_app(pool);

    let (status, created) = send(
        app.clone(),
        post_user(Some("test-api-key"), r#"{"name":"alice"}"#),
    )
    .await;
    assert_eq!(status, StatusCode::CREATED);
    assert_eq!(created["name"], "alice");
    let id = created["id"].as_i64().unwrap();

    let (status, fetched) = send(
        app,
        Request::get(format!("/users/{id}"))
            .body(Body::empty())
            .unwrap(),
    )
    .await;
    assert_eq!(status, StatusCode::OK);
    assert_eq!(fetched, serde_json::json!({ "id": id, "name": "alice" }));
}

#[sqlx::test]
async fn create_without_api_key_is_unauthorized(pool: SqlitePool) {
    let (status, body) = send(test_app(pool), post_user(None, r#"{"name":"alice"}"#)).await;
    assert_eq!(status, StatusCode::UNAUTHORIZED);
    assert_eq!(body["error"]["code"], "unauthorized");
}

#[sqlx::test]
async fn create_with_empty_name_is_unprocessable(pool: SqlitePool) {
    let (status, body) = send(
        test_app(pool),
        post_user(Some("test-api-key"), r#"{"name":"   "}"#),
    )
    .await;
    assert_eq!(status, StatusCode::UNPROCESSABLE_ENTITY);
    assert_eq!(body["error"]["code"], "validation_failed");
    assert!(body["error"]["fields"]["name"].is_array());
}

#[sqlx::test]
async fn get_unknown_user_is_not_found(pool: SqlitePool) {
    let (status, body) = send(
        test_app(pool),
        Request::get("/users/999").body(Body::empty()).unwrap(),
    )
    .await;
    assert_eq!(status, StatusCode::NOT_FOUND);
    assert_eq!(body["error"]["code"], "not_found");
}

#[sqlx::test]
async fn create_with_broken_json_is_bad_request(pool: SqlitePool) {
    let (status, body) = send(
        test_app(pool),
        post_user(Some("test-api-key"), r#"{"name":"#),
    )
    .await;
    assert_eq!(status, StatusCode::BAD_REQUEST);
    assert_eq!(body["error"]["code"], "bad_request");
}
  • send: リクエストを送り、ステータスと本文の JSON を組にして返します。
  • post_user: POST /users のリクエストを作ります。api_key が None のときは x-api-key ヘッダーを付けません。
  • 422 のテストでは、error.code に加えて error.fields.name が配列であることも確かめます。文言そのものではなく形を確かめておくと、文言を直してもテストが壊れません。
  • 壊れた JSON には {"name": を送ります。r#"..."# は、" をエスケープせずに書ける Rust の文字列リテラルです。
Terminal 
$ cargo test --test users   Compiling integration-test v0.1.0 (/path/to/08-integration-test)    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.80s     Running tests/users.rs (target/debug/deps/users-a6ec1a5383ee42fd)running 5 teststest create_with_empty_name_is_unprocessable ... oktest create_without_api_key_is_unauthorized ... oktest create_with_broken_json_is_bad_request ... oktest get_unknown_user_is_not_found ... oktest create_then_get_user ... oktest result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.02s

テストは並列に実行されるので、test ... ok の行の順番は実行のたびに変わります。各テストが別々の DB を受け取るので、create_then_get_user が作った alice は、ほかのテストからは見えません。

💡

認可の失敗は必ずテストに含める

「API キーが無いと書き込めない」ことは、正しいリクエストのテストだけでは確かめられません。ミドルウェアの登録を誤って外しても、正常系のテストは通ってしまうからです。401 を返すテストを用意しておけば、保護が外れたときにすぐ気付けます。

テストで使う秘密の値は、test-api-key のような固定のダミーにします。本物の API キーをテストのコードに書かないでください。

✅ 確認ポイント

5 passed が表示されれば OK です。

5

共通の部品を tests/common/mod.rs にまとめる

test_app と send は、tests/health.rs でも使いたい部品です。tests/ の各ファイルは別々のクレートとしてビルドされるので、ファイル同士で関数を直接呼べません。共通の部品はモジュール common にまとめ、各ファイルから mod common; で取り込みます。

Terminal 
$ mkdir tests/common
Rust tests/common/mod.rs 
#![allow(dead_code)] // tests/ の各ファイルが別クレートとして common を取り込むため、使わない関数の警告を抑える

use app::{build_app, config::Config, state::AppState};
use axum::{Router, body::Body, http::Request, http::StatusCode};
use http_body_util::BodyExt;
use sqlx::SqlitePool;
use std::sync::Arc;
use tower::ServiceExt;

pub const TEST_API_KEY: &str = "test-api-key";

pub fn test_app(pool: SqlitePool) -> Router {
    let config = Config {
        host: "127.0.0.1".to_string(),
        port: 0,
        database_url: "unused".to_string(),
        api_key: TEST_API_KEY.to_string(),
    };
    build_app(AppState {
        pool,
        config: Arc::new(config),
    })
}

pub async fn send(app: Router, request: Request<Body>) -> (StatusCode, serde_json::Value) {
    let response = app.oneshot(request).await.unwrap();
    let status = response.status();
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let json = serde_json::from_slice(&bytes).unwrap();
    (status, json)
}

pub fn get(uri: &str) -> Request<Body> {
    Request::get(uri).body(Body::empty()).unwrap()
}

pub fn json_request(
    method: &str,
    uri: &str,
    api_key: Option<&str>,
    body: &'static str,
) -> Request<Body> {
    let mut builder = Request::builder()
        .method(method)
        .uri(uri)
        .header("content-type", "application/json");
    if let Some(key) = api_key {
        builder = builder.header("x-api-key", key);
    }
    builder.body(Body::from(body)).unwrap()
}
  • TEST_API_KEY: テスト用の API キーを定数にしました。test_app の Config と、リクエストのヘッダーの両方でこの定数を使います。
  • get: 本文の無い GET のリクエストを作ります。
  • json_request: メソッド・パス・API キー・JSON の本文からリクエストを作ります。ステップ 4 の post_user を、POST /users 以外にも使える形にしたものです。
  • 先頭の #![allow(dead_code)] は、使っていない関数の警告を、このファイル全体で出さないようにする指定です。理由はこのステップの最後で説明します。
ℹ️

tests/common.rs ではなく tests/common/mod.rs にする

tests/ の直下に置いた .rs ファイルは、全てテスト用のクレートとして扱われます。tests/common.rs にすると、それ自体もテストとして実行され、cargo test の出力に running 0 tests のブロックが 1 つ増えます。サブディレクトリの mod.rs にすれば、テストとしては実行されず、モジュールとしてだけ使われます。

tests/health.rs を次の内容に置き換えます。test_app が SqlitePool を受け取るので、/health のテストも #[sqlx::test] に切り替えます。

まとめ

tests/ ディレクトリに結合テストを書き、07 まで curl で確かめていた応答を cargo test で自動で確かめられるようにしました。 oneshot で Router に直接リクエストを渡すので、サーバーを起動せず、ポートも使いません。 #[sqlx::test] がテストごとにマイグレーション済みの DB を用意するので、テストは並列に実行してもぶつからず、開発用の app.db にも影響しません。 src/ は 1 行も変えずに、正常系と異常系の 7 件のテストを用意できました。

テストを書くときに押さえておく点は次のとおりです。

観点このレッスンでの扱い
リクエストの送り方tower::ServiceExt::oneshot で Router に直接渡す。サーバーもポートも使わない
本文の読み方http_body_util::BodyExt::collect で読み、serde_json::Value にして比べる
DB#[sqlx::test] がテストごとにマイグレーション済みの DB を用意する。成功すると削除、失敗すると残る
設定Config をテストの中で直接作る。API キーは固定のダミー test-api-key
