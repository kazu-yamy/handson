DB 接続と CRUD

  • ⏱ 所要時間: 60分
  • 📊 難易度: 入門
  • 👤 対象: 04 で共有状態を使った API を作り、次にサーバーを再起動してもデータが残るようにしたい人
  • 📋 前提: Rust の基本文法（構造体・Option / Result・クロージャー）、cargo run と curl の基本操作、SQL の基本（CREATE TABLE・SELECT・INSERT・UPDATE・DELETE）、sqlite3 コマンドが使えること
  • 🔗 前提となる項目: 04: 共有状態とミドルウェア

🎯 このレッスンで学ぶこと

  • sqlx の SqlitePool で SQLite に接続し、State でハンドラと共有する
  • sqlx::migrate! と migrations/ の SQL ファイルで、起動時にテーブルを作る
  • FromRow と query_as で、クエリの結果を構造体として受け取る
  • RETURNING と rows_affected() を使い、作成・取得・更新・削除（CRUD）の API を実装する
  • SQL の誤り（実行時の 500）と接続文字列の誤り（起動時のパニック）の現れ方を確かめる

概要

04 の API は、ユーザーの一覧をメモリー上の Vec に持っていたため、サーバーを止めるとデータが初期状態に戻りました。 このレッスンでは、sqlx を使って SQLite のデータベースファイル app.db に接続し、ユーザーを DB に保存します。 ハンドラを「読み取り → 作成 → 更新・削除」の順に 1 つずつ DB へ置き換え、最後にメモリー上の Vec と Mutex を取り除きます。

このレッスンの完成時には、サーバーが次のルートへ応答します。04 から変わったところを太字にしています。

メソッドパス返す内容ミドルウェア
GET/Hello from Handson Axumログ
GET/healthJSON {"status":"ok"}ログ
GET/usersDB に保存されているユーザーの JSON 配列ログ
POST/usersDB にユーザーを追加し、201 と作成したユーザーの JSONログ + API キー認証
GET/users/{id}DB から取得したユーザーの JSON（なければ 404）ログ
PUT/users/{id}DB のユーザーの名前を更新し、更新後の JSON（なければ 404）ログ + API キー認証
DELETE/users/{id}DB からユーザーを削除し、204（なければ 404）ログ + API キー認証

Rust（rustc）1.98.1 / cargo 1.98.1（Rust edition 2024）で動作を確認しています。クレートのバージョンは axum 0.8.9 / tokio 1.53.1 / serde 1.0.229 / serde_json 1.0.151 / sqlx 0.9.0 です。 バージョンは執筆時点（2026年9月）のものです。このレッスンで新たに追加するクレートは sqlx（機能 runtime-tokio・sqlite）だけです。DB の中身の確認には sqlite3 コマンド 3.51.0 を使います。

Rust src/main.rs 
use axum::{
    Extension, Json, Router,
    extract::{Path, Query, Request, State},
    http::StatusCode,
    middleware::{self, Next},
    response::{IntoResponse, Response},
    routing::{get, post, put},
};
use serde::{Deserialize, Serialize};
use serde_json::json;
use sqlx::SqlitePool;
use std::collections::HashMap;
use std::sync::{Arc, Mutex};
use std::time::Instant;

#[derive(Clone, Serialize)]
struct User {
    id: u32,
    name: String,
}

#[derive(Deserialize)]
struct CreateUser {
    name: String,
}

#[derive(Clone)]
struct AppState {
    users: Arc<Mutex<Vec<User>>>,
    pool: SqlitePool,
}

#[derive(Clone)]
struct AppConfig {
    app_name: String,
}

#[tokio::main]
async fn main() {
    let pool = SqlitePool::connect("sqlite://app.db?mode=rwc")
        .await
        .unwrap();

    let state = AppState {
        users: Arc::new(Mutex::new(vec![
            User {
                id: 1,
                name: "alice".to_string(),
            },
            User {
                id: 2,
                name: "bob".to_string(),
            },
        ])),
        pool,
    };

    let protected_users = Router::new()
        .route("/users", post(create_user))
        .route("/users/{id}", put(update_user))
        .route_layer(middleware::from_fn(require_api_key));

    let app = Router::new()
        .route("/", get(root))
        .route("/health", get(health))
        .route("/users", get(list_users))
        .route("/users/{id}", get(get_user))
        .merge(protected_users)
        .route("/users/{user_id}/posts/{post_id}", get(get_user_post))
        .route("/search", get(search))
        .fallback(not_found)
        .layer(Extension(AppConfig {
            app_name: "Handson Axum".to_string(),
        }))
        .layer(middleware::from_fn(log_request))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on {}", listener.local_addr().unwrap());
    axum::serve(listener, app).await.unwrap();
}

async fn log_request(req: Request, next: Next) -> Response {
    let method = req.method().clone();
    let uri = req.uri().clone();
    let start = Instant::now();

    let response = next.run(req).await;

    let elapsed = start.elapsed();
    println!("{method} {uri} -> {} ({elapsed:?})", response.status());
    response
}

async fn require_api_key(req: Request, next: Next) -> Response {
    let is_valid = req
        .headers()
        .get("x-api-key")
        .and_then(|value| value.to_str().ok())
        == Some("secret");

    if !is_valid {
        return (StatusCode::UNAUTHORIZED, "invalid or missing x-api-key").into_response();
    }

    next.run(req).await
}

async fn root(Extension(config): Extension<AppConfig>) -> String {
    format!("Hello from {}", config.app_name)
}

async fn health() -> Json<serde_json::Value> {
    Json(json!({ "status": "ok" }))
}

async fn list_users(State(state): State<AppState>) -> Json<Vec<User>> {
    let users = state.users.lock().unwrap();
    Json(users.clone())
}

async fn create_user(
    State(state): State<AppState>,
    Json(payload): Json<CreateUser>,
) -> (StatusCode, Json<User>) {
    let mut users = state.users.lock().unwrap();
    let user = User {
        id: users.len() as u32 + 1,
        name: payload.name,
    };
    users.push(user.clone());
    (StatusCode::CREATED, Json(user))
}

async fn get_user(
    State(state): State<AppState>,
    Path(id): Path<u32>,
) -> Result<Json<User>, StatusCode> {
    let users = state.users.lock().unwrap();
    users
        .iter()
        .find(|user| user.id == id)
        .cloned()
        .map(Json)
        .ok_or(StatusCode::NOT_FOUND)
}

async fn update_user(
    State(state): State<AppState>,
    Path(id): Path<u32>,
    Json(payload): Json<CreateUser>,
) -> Result<Json<User>, StatusCode> {
    let mut users = state.users.lock().unwrap();
    let user = users
        .iter_mut()
        .find(|user| user.id == id)
        .ok_or(StatusCode::NOT_FOUND)?;
    user.name = payload.name;
    Ok(Json(user.clone()))
}

async fn get_user_post(Path((user_id, post_id)): Path<(u32, u32)>) -> String {
    format!("user {user_id} post {post_id}")
}

async fn search(Query(params): Query<HashMap<String, String>>) -> String {
    format!("search params: {params:?}")
}

async fn not_found() -> (StatusCode, &'static str) {
    (StatusCode::NOT_FOUND, "Not Found")
}

3

マイグレーションでテーブルを作る

users テーブルを作る SQL を「マイグレーション」として用意し、サーバーの起動時に実行します。プロジェクト直下に migrations ディレクトリを作り、次のファイルを新規作成してください。

SQL migrations/0001_create_users.sql 
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL
);

id は INTEGER PRIMARY KEY AUTOINCREMENT なので、行を追加すると SQLite が番号を振ります。次に、main で接続した直後にマイグレーションを実行します。

Diff src/main.rs 
      let pool = SqlitePool::connect("sqlite://app.db?mode=rwc")          .await          .unwrap();++     sqlx::migrate!().run(&pool).await.unwrap();       let state = AppState {
  • sqlx::migrate!(): コンパイル時に、プロジェクト直下の migrations/ にある SQL ファイルを実行ファイルへ埋め込むマクロです。sqlx の CLI ツール（sqlx-cli）は使いません。
  • .run(&pool): まだ適用していないマイグレーションだけを実行します。適用した記録は、sqlx が作る _sqlx_migrations テーブルに残ります。
  • ファイル名は <番号>_<説明>.sql の形にします。番号の小さい順に適用されます。

ステップ 2 で作った空の app.db はそのままでかまいません。cargo build してから cargo run で起動します（pool の警告はまだ出ます）。

Terminal 
$ cargo build   Compiling database v0.1.0 (/path/to/05-database)warning: field `pool` is never read   ...warning: `database` (bin "database") generated 1 warning    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.89s$ cargo run   ... 2 つ目のターミナルで、sqlite3 コマンドを使って app.db の中を確かめます。.tables はテーブルの一覧、.schema はテーブルの定義を表示するコマンドです。

Terminal（2 つ目） 
$ sqlite3 app.db '.tables'_sqlx_migrations  users$ sqlite3 app.db '.schema users'CREATE TABLE users (    id INTEGER PRIMARY KEY AUTOINCREMENT,    name TEXT NOT NULL);$ sqlite3 app.db 'SELECT version, description, success FROM _sqlx_migrations'1|create users|1

users テーブルに加えて _sqlx_migrations テーブルができました。ファイル名の番号 0001 は version の 1 として、create_users は description の create users として記録されています。サーバーを止めてもう一度 cargo run で起動し、同じ SELECT を実行しても行は 1 件のままです。適用済みのマイグレーションは再実行されません。

✅ 確認ポイント

.tables に _sqlx_migrations と users が表示されれば OK です。確認できたら、サーバーを止めておきます。

4

一覧と取得を DB から返す（GET /users、GET /users/{id}）

ここからハンドラを 1 つずつ DB に置き換えます。まずは読み取り（Read）の GET /users と GET /users/{id} です。POST と PUT はまだ Vec を使うので、AppState の users はこのステップでは残します。

Diff src/main.rs

  • #[derive(sqlx::FromRow)]: 取得した行を User に変換できるようにします。SELECT id, name の列名が、同じ名前のフィールドに入ります。
  • id: i64: SQLite の INTEGER 列は 64 ビットの符号付き整数を格納できるので、Rust 側も同じ範囲の i64 で受け取ります。パスパラメーター Path<i64> と、create_user の as i64 も合わせて変えます。
  • sqlx::query_as::<_, User>(SQL): 結果を User として受け取るクエリを作ります。SQL の ? には .bind(id) で値を渡します。
  • fetch_all は全ての行を Vec で、fetch_optional は 0 件か 1 件の行を Option で返します。None のときは 04 と同じく 404 にします。
  • DB のエラーは map_err で 500（INTERNAL_SERVER_ERROR）に変え、? で返します。そのため list_users の戻り値も Result にしています。

unable to open database file が出たら ?mode=rwc を疑う

メッセージは「ファイルを開けない」という一般的な内容で、?mode=rwc がないことは書かれていません。?mode=rwc を付けない接続では、存在しないファイルは作られません。DB ファイルがまだない環境で起動する場合は、接続文字列を確認しましょう。

確認できたら、接続文字列を "sqlite://app.db?mode=rwc" に戻してください。2 つの失敗を並べると、次のように検出されるタイミングが異なります。

失敗ビルド起動検出されるタイミング
(a) SQL の列名の誤り通るできるそのクエリを実行したリクエストで 500
(b) ?mode=rwc の付け忘れ通るパニックで終了起動時（DB ファイルがない場合）

✅ 確認ポイント

(a) で 500 とサーバー側の no such column: nmae を、(b) で unable to open database file のパニックを確認できれば OK です。2 か所とも元に戻し、(a) で起動したサーバーも止めておきます。

cargo run で起動したサーバーは、ソースコードを保存しても変更を反映しません。各ステップでコードを変えたら、前のサーバーを Ctrl + C で止めてから cargo run し直してください。止め忘れたまま別のターミナルで起動すると、ポート 3000 が使用中のエラーになります（01 の「つまずきポイント」を参照）。

まとめ

sqlx の SqlitePool で SQLite に接続し、sqlx::migrate! で起動時にテーブルを作りました。 FromRow と query_as で行を構造体として受け取り、RETURNING と rows_affected() を使って CRUD の API を実装しました。 データは app.db に保存されるので、サーバーを再起動しても残ります。 SQL の誤りは実行時の 500 として、接続文字列の誤りは起動時のパニックとして現れることも確かめました。 次の項目では、独自のエラー型とバリデーションを実装します。
