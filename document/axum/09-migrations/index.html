マイグレーション運用と記事リソース

  • ⏱ 所要時間: 60分
  • 📊 難易度: 初級
  • 👤 対象: 08 までの users の API に 2 つ目のテーブルを足し、記事（posts）の API を作りたい人
  • 📋 前提: Rust の基本文法、SQL の基本（CREATE TABLE・SELECT・UPDATE）、08 で書いた結合テスト（tests/common/mod.rs と #[sqlx::test]）の構成
  • 🔗 前提となる項目: 08: 結合テスト

🎯 このレッスンで学ぶこと

  • sqlx-cli を入れ、sqlx migrate info・add・run でマイグレーションを管理する
  • 外部キー（REFERENCES ... ON DELETE CASCADE）と索引を持つ posts テーブルを追加する
  • SqliteConnectOptions で、外部キー・WAL・待ち時間を指定して DB に接続する
  • 記事の作成・取得・更新・削除を実装し、複数の項目の検証エラーを 1 回の 422 にまとめて返す
  • キーセット方式のページネーションで記事の一覧を返す
  • いいねの数を 1 文の UPDATE で原子的に増やす
  • 適用済みのマイグレーションを書き換えると何が起きるかを確かめる

概要

このレッスンから、題材に記事（posts）が登場します。 08 までの users に 2 つ目のテーブル posts を足し、記事の作成・一覧・取得・更新・削除と「いいね」の API を作ります。 ここで決める API の形（パス・JSON のフィールド名・エラーの形）は、以降の項目でも使い続けます。

テーブルを足すには、DB の構造を変えるマイグレーションを書きます。 08 までは migrations/0001_create_users.sql を 1 つ持ち、サーバーの起動時に適用していました。 このレッスンでは、マイグレーションを管理するコマンドラインツール sqlx-cli を使い、新しいマイグレーションの追加と適用状況の確認をコマンドで行います。

このレッスンで完成する記事の API は次のとおりです。

⚠️

このレッスンの API には、わざと残しているセキュリティ上の穴があります

09 の時点では、利用者のログイン（認証）がありません。記事の作成・更新・削除は、06 から使っている API キーだけで保護します。

そのため、API キーを知っている人なら誰でも、本文の author_id に他人の id を書いて他人の名前で投稿できます。他人の記事を書き換えたり削除したりもできます（ステップ 6 で実際に確かめます）。

この穴は、10「パスワードハッシュとログイン」と 11「認証エクストラクタと認可」で直します。このレッスンのコードを、そのまま公開する API に使わないでください。

3

posts テーブルのマイグレーションを追加し、接続オプションを置き換える

sqlx migrate add で、新しいマイグレーションのファイルを作ります。引数はマイグレーションの説明で、ファイル名の一部になります。

Terminal 
$ sqlx migrate add create_postsCreating migrations/0002_create_posts.sql$ ls migrations0001_create_users.sql0002_create_posts.sql$ cat migrations/0002_create_posts.sql-- Add migration script here$ sqlx migrate info1/installed create users2/pending create posts

ファイル名の先頭は 0002_ の連番になりました。sqlx migrate add は既存のファイルを見て、連番とタイムスタンプ（YYYYMMDDHHMMSS）のどちらで名前を付けるかを自動で決めます。ヘルプには、マイグレーションが 1 つだけでバージョンが 0 か 1 の場合は連番と判断する、と書かれています。0001 だけがあるこのプロジェクトは、これに当てはまります。

できたファイルの中身はコメント 1 行だけです。このコメントを消し、次の内容で上書きします。

SQL migrations/0002_create_posts.sql 
CREATE TABLE posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    author_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    body TEXT NOT NULL,
    like_count INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now')),
    updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ', 'now'))
);
CREATE INDEX posts_author_id_id ON posts (author_id, id);
  • author_id INTEGER NOT NULL REFERENCES users(id): 外部キーです。author_id には users テーブルに実在する id しか入れられません。存在しない id を入れようとすると、DB が外部キー違反のエラーを返します。
  • ON DELETE CASCADE: 参照先の user が削除されると、その user の記事も一緒に削除されます（連鎖削除）。ステップ 6 で確かめます。
  • like_count はいいねの数で、初期値は 0 です。
  • created_at・updated_at は、SQLite の strftime で作った ISO 8601 形式（UTC）の文字列です。日時を扱うクレートは追加せず、Rust 側では String として扱います。秒までの精度です。
  • CREATE INDEX posts_author_id_id ON posts (author_id, id): 「ある著者の記事を id の順に取る」ための索引です。ステップ 5 の一覧の絞り込みで使う条件に合わせています。

// 指定されたフィールドだけを検証し、不正なものは全部まとめて 1 回の 422 で返す
fn validate(title: Option<&str>, body: Option<&str>) -> Result<(), AppError> {
    let mut fields = BTreeMap::new();
    if let Some(title) = title
        && !(1..=100).contains(&title.trim().chars().count())
    {
        fields.insert(
            "title".to_string(),
            vec!["title must be 1 to 100 characters".to_string()],
        );
    }
    if let Some(body) = body
        && !(1..=5000).contains(&body.trim().chars().count())
    {
        fields.insert(
            "body".to_string(),
            vec!["body must be 1 to 5000 characters".to_string()],
        );
    }
    if fields.is_empty() {
        Ok(())
    } else {
        Err(AppError::Validation(fields))
    }
}

pub async fn create_post(
    State(state): State<AppState>,
    payload: Result<Json<CreatePost>, JsonRejection>,
) -> Result<(StatusCode, Json<Post>), AppError> {
    let Json(payload) = payload?;
    validate(Some(&payload.title), Some(&payload.body))?;
    let result = sqlx::query_as::<_, Post>(
        "INSERT INTO posts (author_id, title, body) VALUES (?, ?, ?) \
         RETURNING id, author_id, title, body, like_count, created_at, updated_at",
    )
    .bind(payload.author_id)
    .bind(payload.title.trim())
    .bind(payload.body.trim())
    .fetch_one(&state.pool)
    .await;
    match result {
        Ok(post) => Ok((StatusCode::CREATED, Json(post))),
        // 外部キー制約に違反した = author_id の user がいない
        Err(sqlx::Error::Database(error)) if error.is_foreign_key_violation() => {
            Err(AppError::field("author_id", "author not found"))
        }
        Err(error) => Err(error.into()),
    }
}

pub async fn get_post(
    State(state): State<AppState>,
    Path(id): Path<i64>,
) -> Result<Json<Post>, AppError> {
    let post = sqlx::query_as::<_, Post>(
        "SELECT id, author_id, title, body, like_count, created_at, updated_at \
         FROM posts WHERE id = ?",
    )
    .bind(id)
    .fetch_optional(&state.pool)
    .await?;
    post.map(Json).ok_or(AppError::NotFound("post not found"))
}

pub async fn update_post(
    State(state): State<AppState>,
    Path(id): Path<i64>,
    payload: Result<Json<UpdatePost>, JsonRejection>,
) -> Result<Json<Post>, AppError> {
    let Json(payload) = payload?;
    validate(payload.title.as_deref(), payload.body.as_deref())?;
    // 未指定（None → NULL）の項目は COALESCE で今の値のまま残す
    let post = sqlx::query_as::<_, Post>(
        "UPDATE posts SET title = COALESCE(?1, title), body = COALESCE(?2, body), \
         updated_at = strftime('%Y-%m-%dT%H:%M:%SZ', 'now') \
         WHERE id = ?3 RETURNING id, author_id, title, body, like_count, created_at, updated_at",
    )
    .bind(payload.title.as_deref().map(str::trim))
    .bind(payload.body.as_deref().map(str::trim))
    .bind(id)
    .fetch_optional(&state.pool)
    .await?;
    post.map(Json).ok_or(AppError::NotFound("post not found"))
}

pub async fn delete_post(
    State(state): State<AppState>,
    Path(id): Path<i64>,
) -> Result<StatusCode, AppError> {
    let result = sqlx::query("DELETE FROM posts WHERE id = ?")
        .bind(id)
        .execute(&state.pool)
        .await?;
    if result.rows_affected() == 0 {
        Err(AppError::NotFound("post not found"))
    } else {
        Ok(StatusCode::NO_CONTENT)
    }
}
  • Post は DB の行と応答の JSON を兼ねます。sqlx::FromRow で行から作り、Serialize で JSON にします。フィールド名はそのまま JSON のキー（snake_case）になります。
  • validate は、渡された項目だけを検査し、不正な項目を全部 fields に集めてから 1 回の 422 で返します。title と body の両方が不正なら、両方を一度に知らせます。長さは前後の空白を除いた（trim）後の文字数で数え、保存するのも trim した値です。
  • if let Some(title) = title && ... は、edition 2024 で使える let チェーンです。「値があり、かつ長さが範囲外」を 1 つの if で書けます。
  • create_post は、author_id の user がいるかを事前に SELECT で確かめません。そのまま INSERT し、外部キー違反になったら（is_foreign_key_violation()）422 の fields.author_id に変換します。存在の確認を DB の制約に任せるので、確認してから挿入するまでの間に user が消える、という競合も起きません。
  • RETURNING は、INSERT・UPDATE した行をその場で返す SQL の句です。作った記事を取り直すための SELECT が要りません。
  • update_post は PATCH 用で、title と body はどちらも省略できます（Option）。省略された項目は None で、SQL には NULL として渡ります。COALESCE(?1, title) は「?1 が NULL なら今の title のまま」という意味です。空文字（""）は省略とは別扱いで、検証で 422 になります。updated_at は現在時刻にします。
  • ?1・?2・?3 は番号付きのプレースホルダーで、.bind した順に 1, 2, 3 と対応します。値は全てプレースホルダーで渡し、SQL の文字列には埋め込みません。
  • この時点では、更新・削除する人が記事の著者かどうかを検査していません。冒頭の注意のとおり、11 で直します。

つまずきポイント

💡

新しいマイグレーションを足したのに、起動しても適用されない

sqlx::migrate!() は、ビルドの時点で migrations/ の SQL を埋め込みます。執筆時に試したところ、既存のファイルの内容を書き換えると再ビルドされましたが、新しいファイルを足しただけでは cargo build が再ビルドせず、起動しても新しいテーブルは作られませんでした。touch src/main.rs でソースの更新日時を変えてから cargo build すると、再ビルドされて適用されます。

毎回 touch するのを避けたい場合は、sqlx migrate build-script を使う方法もあります。migrations/ が変わったら再ビルドするよう指示する build.rs（println!("cargo:rerun-if-changed=migrations");）を作ります。このレッスンの完成コードでは使っていません。

💡

別の場所に空の app.db ができる

sqlx-cli は、カレントディレクトリの .env を読みます。sqlite://app.db の app.db も、カレントディレクトリからの相対パスです。sqlx migrate info・run は、必ず 09-migrations ディレクトリで実行してください。

💡

Error: VersionMismatch(1) でサーバーが起動しない

適用済みのマイグレーション（この場合は 0001）のファイルが、適用したときと変わっています。コメントや空白の変更でも起きます。ファイルを元の内容に戻してください（ステップ 7 を参照）。

💡

sqlite3 で入れた行は、外部キーの制約が効かない

sqlite3 コマンドは、外部キーを既定で無効にしています。sqlite3 で行を入れて確かめるときは、先に PRAGMA foreign_keys=ON; を実行してください（ステップ 4 の読み物を参照）。

💡

2 ページ目に、1 ページ目と同じ記事が出る

cursor には、前のページの応答の next_cursor をそのまま渡します。cursor は「この id より古い記事から」という意味です。執筆時に next_cursor の 3 ではなく 1 ページ目の先頭の 4 を渡したところ、1 ページ目にあった id 3 がもう一度返りました。

💡

/posts/abc の 400 が JSON ではない

パスの型が合わないときは、Axum が text/plain の 400 を返します。これは 02 から変わっていない挙動です（06 で JSON に包んだのは Json の拒否だけです）。後の項目（12）で、ほかのエラーと同じ JSON の形に統一する予定です。一方、クエリ文字列の型が合わないとき（?limit=abc）は、ステップ 5 で QueryRejection を取り込んだので JSON の 400 になります。

💡

PATCH しても updated_at が変わらない

updated_at は秒までしか持ちません。作成と同じ秒のうちに更新すると、created_at と同じ値になります。1 秒以上待ってから試してください。
