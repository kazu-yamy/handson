HTTP の防御層

  • ⏱ 所要時間: 60分
  • 📊 難易度: 初級
  • 👤 対象: 12 までの API に、ログインの総当たりやいいねの連打を止めるレート制限と、CORS・セキュリティヘッダーを掛けたい人
  • 📋 前提: Rust の基本文法、04 のミドルウェア、08 の結合テスト、10 のログイン、12 の layers::apply とハッシュ計算の同時実行数の上限（HASH_SLOTS）
  • 🔗 前提となる項目: 12: エラー応答の統一と入力の防御

🎯 このレッスンで学ぶこと

  • governor で email 単位のレート制限を掛け、同じ email へのログインを 6 回目から 429 と Retry-After で止める
  • 接続元の IP 単位の制限を、登録・ログイン・いいねの 3 つのルートにだけ掛ける
  • X-Forwarded-For を既定では信用せず、信用するときは右端の値を使う理由を説明できる
  • CORS を、許可リストを設定したときだけ有効にし、CORS が認可の仕組みではないことを確かめる
  • セキュリティヘッダーと cache-control: no-store を、エラーを含む全ての応答に付ける
  • レート制限で防げないこと（ロックアウト、多数の IP からの攻撃）を、実測を元に説明できる

概要

10〜12 では、次の課題を「13 で扱う」として残してきました。

  • ログインの総当たり（10）: 同じ email に、何回でもパスワードを試せる。
  • いいねの連打（09）: いいねは認証の要らないエンドポイントで、誰でも何回でも押せる。
  • 登録・ログインの連打によるハッシュ計算の占有（10・12）: 12 で、パスワードハッシュの同時実行数を 4 個に絞った（HASH_SLOTS）。ただし、この上限はサーバー全体で 1 つしかない。大量のログインが来ると、ほかの利用者のログインや登録も順番待ちになり、タイムアウト（408）になりうる。1 つの送信元からの連打も止めない。
  • CORS とセキュリティヘッダー（12）: ブラウザから呼ばれる場合の CORS の設定や、x-content-type-options などのヘッダーを付けていない。
  • 64 KiB 未満の長い email（12）: 上限に収まる長さの email でのログインは、DB の検索まで進む。

このレッスンでは、これらを HTTP の層でまとめて扱います。直す前と直した後の応答は次のとおりです。

できること・できないこと

このレッスンで入れる仕組みは、どれも「ある攻撃を止める代わりに、別の攻撃には効かない」ものです。先に一覧表でまとめます。詳しくは各ステップと読み物で、執筆時の実測とあわせて説明します。

仕組み止められること止められないこと・注意ステップ
email 単位の制限1 つの email への総当たり（毎分 5 回まで）。BFF の後ろで接続元の IP が 1 つに見えても効く他人の email に失敗を重ねると、本人も正しいパスワードでログインできなくなる（ロックアウト）。実測では、攻撃者が約 12 秒ごとに 1 回送り続けるかぎり、本人は入れなかった2・4
IP 単位の制限1 つの IP からの連打（登録・ログイン、いいね）。email を変えながら試す攻撃（パスワードスプレー）や、登録の連打による argon2 の占有を、1 つの IP からなら早めに止める多数の IP からの攻撃は止まらない。ロックアウトもほとんど抑えない。プロキシの後ろでは、設定しないと全員が 1 つの枠を共有する3・4
X-Forwarded-For の扱い既定では無視するので、ヘッダーの偽装で IP 単位の制限を回避されない信用する設定（TRUST_FORWARDED_FOR=true）のまま、プロキシを通らずに直接つながれる構成で動かすと、偽装で回避される4
制限の状態の置き場所プロセスのメモリに持つので、外部のストアが要らない再起動で消える。サーバーを複数台にすると、台ごとに別々に数える2・4
CORS許可したオリジンのページの JavaScript にだけ、応答を読ませる（ブラウザの中での話）認可の仕組みではない。curl などブラウザ以外からのリクエストは止まらず、サーバーは処理して応答を返す6
セキュリティヘッダーブラウザが応答を扱う方法を制限するcurl やサーバー間の通信には関係しない。JSON だけを返すこの API では、効果が限られるものもある7

limiter を作る

新しいファイル src/rate_limit.rs を作ります。3 つの limiter をまとめた RateLimits と、limiter を 1 回使って、使い切っていたら 429 を返す check です。IP 単位の 2 つ（auth_by_ip・like_by_ip）は、ステップ 3 で使います。

use governor::{DefaultKeyedRateLimiter, Quota, clock::Clock};
use std::hash::Hash;
use std::net::IpAddr;
use std::num::NonZeroU32;
use std::time::Duration;

use crate::error::AppError;

// 制限値は API 契約 4.6 のとおり。コードの定数で、環境変数では変えない。
// Quota::per_minute(n) は「バースト n 回、60 / n 秒ごとに 1 回分回復」（固定窓ではなく GCRA）
const LOGIN_BY_EMAIL_PER_MINUTE: u32 = 5;
const AUTH_BY_IP_PER_MINUTE: u32 = 10;
const LIKE_BY_IP_PER_MINUTE: u32 = 30;

pub struct RateLimits {
    // POST /auth/login。キーは正規化した email（trim + 小文字化）
    pub login_by_email: DefaultKeyedRateLimiter<String>,
    // POST /auth/register と POST /auth/login で共有する。キーは接続元 IP
    pub auth_by_ip: DefaultKeyedRateLimiter<IpAddr>,
    // POST /posts/{id}/like。キーは接続元 IP
    pub like_by_ip: DefaultKeyedRateLimiter<IpAddr>,
}

impl RateLimits {
    pub fn new() -> RateLimits {
        RateLimits::with_quotas(
            Quota::per_minute(NonZeroU32::new(LOGIN_BY_EMAIL_PER_MINUTE).unwrap()),
            Quota::per_minute(NonZeroU32::new(AUTH_BY_IP_PER_MINUTE).unwrap()),
            Quota::per_minute(NonZeroU32::new(LIKE_BY_IP_PER_MINUTE).unwrap()),
        )
    }

    // テストで「時間がたてば回復する」ことを短い時間で確かめるために、上限を差し替えられるようにしておく
    pub fn with_quotas(login_by_email: Quota, auth_by_ip: Quota, like_by_ip: Quota) -> RateLimits {
        RateLimits {
            login_by_email: DefaultKeyedRateLimiter::keyed(login_by_email),
            auth_by_ip: DefaultKeyedRateLimiter::keyed(auth_by_ip),
            like_by_ip: DefaultKeyedRateLimiter::keyed(like_by_ip),
        }
    }
}

impl Default for RateLimits {
    fn default() -> Self {
        RateLimits::new()
    }
}

// 1 回分の枠を使う。使い切っていたら、次に通るまでの秒数を持つ 429 を返す
pub fn check<K: Hash + Eq + Clone>(
    limiter: &DefaultKeyedRateLimiter<K>,
    key: &K,
) -> Result<(), AppError> {
    limiter.check_key(key).map_err(|not_until| {
        let wait = not_until.wait_time_from(limiter.clock().now());
        AppError::RateLimited {
            retry_after_secs: retry_after_secs(wait),
        }
    })
}

// Retry-After は整数の秒。切り上げて、最小は 1（0 にすると「すぐ再送してよい」と読めてしまう）
pub fn retry_after_secs(wait: Duration) -> u64 {
    let secs = wait.as_secs() + u64::from(wait.subsec_nanos() > 0);
    secs.max(1)
}
  • DefaultKeyedRateLimiter<K> は、キー（ここでは email や IP）ごとに別々に数える limiter です。キーを初めて見たときに、そのキーの枠が作られます。
  • Quota::per_minute(5) は、続けて 5 回まで通し、その後は 12 秒ごとに 1 回分ずつ回復する、という意味です。1 分ごとに数え直す固定の枠ではありません（GCRA という方式）。5 回使い切った直後は、12 秒待つと 1 回だけ通ります。
  • check は、枠を使い切っていると、次に通るまでの時間を retry_after_secs で秒に直します。小数は切り上げ、最小は 1 秒です。0 にすると「すぐに再送してよい」と読めてしまうためです。
  • with_quotas は、テストで上限を差し替えるために用意しています（ステップ 5）。

X-Forwarded-For を信用しない理由と、古いキーの掃除

X-Forwarded-For の右端だけを信用する

リバースプロキシや BFF（Next.js のサーバーなど）の後ろで動かすと、API から見た接続元の IP は、常にプロキシの IP になります。そこで、プロキシは「自分に接続してきた相手の IP」を X-Forwarded-For ヘッダーの右端に書き足して転送します。ただし、このヘッダーはクライアントも自由に書けます。プロキシが 1 段の構成では、右端がクライアントの IP で、それより左にある値はクライアントが送ってきたものです。プロキシが 2 段以上の構成では、右端は手前のプロキシの IP になります。

  • 既定（TRUST_FORWARDED_FOR=false）: ヘッダーを無視し、接続元の IP で数えます。ヘッダーを毎回変えても、制限を回避できません。
  • TRUST_FORWARDED_FOR=true: X-Forwarded-For の右端の値で数えます。右端は、信用するプロキシが最後に書き足した値だからです（プロキシが 1 段の構成では、クライアントの IP）。左端を偽っても回避できません。読めない値のときは、接続元の IP に戻します。

true にしてよいのは、信用するプロキシの後ろで動かし、API にプロキシを通らずに直接つながれない構成のときだけです。直接つながれる構成で true にすると、右端もクライアントが書けるので、右端を毎回変えるだけで別の枠になります（下の読み物で、右端を変えると別の枠になることを確かめています）。

逆に、プロキシの後ろで false のままにすると、全ての利用者がプロキシの IP 1 つに見えます。全員で 1 つの枠（登録とログインを合わせて毎分 10 回）を共有するので、1 人が連打すると全員が 429 になります。プロキシの後ろでは、email 単位の制限が主な防御で、IP 単位の制限は補助です。

async fn the_limit_recovers_as_time_passes(pool: SqlitePool) {
    // 実時間で 12 秒待たなくてよいように、回復を 300 ミリ秒ごと・バースト 2 回にした limiter を差し込む
    let mut state = test_state(pool);
    let quick = Quota::with_period(Duration::from_millis(300))
        .unwrap()
        .allow_burst(std::num::NonZeroU32::new(2).unwrap());
    state.limits = Arc::new(RateLimits::with_quotas(
        quick,
        Quota::per_minute(std::num::NonZeroU32::new(100).unwrap()),
        Quota::per_minute(std::num::NonZeroU32::new(100).unwrap()),
    ));
    let app = app_with(state);

    // 失敗するログインは argon2 の検証を通るので 1 回に数十ミリ秒かかり、負荷が高いと 3 回目までに 1 回分
    // 回復してしまうことがある。「3 回目で必ず 429」と決め打ちせず、429 になるまで送る（上限 10 回）
    let mut limited = false;
    for _ in 0..10 {
        let (status, _, _) = login_status(&app, "alice@example.com", "wrong-password-123").await;
        if status == StatusCode::TOO_MANY_REQUESTS {
            limited = true;
            break;
        }
        assert_eq!(status, StatusCode::UNAUTHORIZED);
    }
    assert!(limited, "never rate limited");

    // 429 になった直後から 400 ミリ秒待てば（回復の間隔は 300 ミリ秒）、必ず 1 回分は回復している
    tokio::time::sleep(Duration::from_millis(400)).await;
    let (status, _, _) = login_status(&app, "alice@example.com", "wrong-password-123").await;
    assert_eq!(status, StatusCode::UNAUTHORIZED);
}

実時間で 12 秒待たなくてよいように、300 ミリ秒ごとに 1 回分回復し、続けて 2 回まで通す limiter を差し込みます。失敗するログインは argon2 の検証を通るので、1 回に数十ミリ秒かかることがあります。そのため「3 回目で必ず 429」とは決め打ちせず、429 になるまで送ってから、回復の間隔より長く待ちます。

時間に依存するテストは、余裕を持たせる

執筆時の最初の版は、回復を 100 ミリ秒ごとにして「3 回目で必ず 429」と決め打ちしていました。テストが並列に走って CPU が混むと、3 回目までに 1 回分が回復してしまい、12 回中 4 回失敗しました（left: 401 / right: 429）。上の版に直した後、cargo test を 15 回続けて流し、失敗が出ないことを確かめています。同じ理由で、掃除のテストも回復を 200 ミリ秒、待ち時間を 400 ミリ秒にしています。

CORS を許可リストで有効にする

ブラウザは、あるオリジン（スキーム・ホスト・ポートの組）のページの JavaScript が、別のオリジンの API の応答を読むことを、既定では許しません（同一オリジンポリシー）。CORS は、API の側が「このオリジンのページになら読ませてよい」とブラウザに伝えて、この制約を緩める仕組みです。Authorization ヘッダーを付けるリクエストなどでは、ブラウザは本来のリクエストの前に、送ってよいかを OPTIONS のリクエスト（プリフライト）で尋ねます。詳しくは MDN の CORS の解説 を参照してください。

この API では、CORS を既定で無効にします。Next.js トラックでは、ブラウザは Next.js のサーバーを呼び、Axum を呼ぶのは Next.js のサーバー（BFF）です。ブラウザが Axum を直接呼ばないので、CORS は要りません。ブラウザから直接呼ぶ必要が出たときだけ、オリジンを明示して許可します。

⚠️

CORS は認可の仕組みではない

CORS は、ブラウザの中で、応答を JavaScript に渡すかどうかを決めるためのものです。curl やサーバー間の通信など、ブラウザ以外からのリクエストは止まりません。サーバーは許可していないオリジンからのリクエストも処理し、応答を返します（下で確かめます）。誰が何をしてよいかは、11 の認証と認可で守ります。

セキュリティヘッダーを全ての応答に付ける

次の 4 つのヘッダーを、エラーを含む全ての応答に付けます。OWASP の REST Security Cheat Sheet にある、API の応答向けの組み合わせです。

ヘッダー値目的
x-content-type-optionsnosniffブラウザに Content-Type を推測させず、宣言どおりに扱わせる（JSON を HTML として解釈させない）
content-security-policydefault-src 'none'; frame-ancestors 'none'この応答からは何も読み込ませず、どのページの枠（iframe など）にも入れさせない
referrer-policyno-referrer遷移先に、遷移元の URL（Referer）を送らせない
cache-controlno-store共有キャッシュにも、ブラウザのキャッシュにも保存させない。ログインの応答のように、トークンを含む応答があるため

どのヘッダーも、ブラウザなどのクライアントに応答の扱い方を伝えるものです。curl やサーバー間の通信では、受け取った側が従わなければ効果はありません。この API の応答は JSON だけで、ページとして表示するためのものではありません。そのため、ページの表示に関わる content-security-policy や referrer-policy は、効果が限られます。応答が想定外の扱われ方をしたときの備えとして付けておきます。cache-control: no-store は、トークンを途中のキャッシュに残さないためのものです。Next.js トラックでは、Axum の応答を HTTP のキャッシュに頼らず、Next.js 側のキャッシュで持つ設計です。

HTTPS を強制する Strict-Transport-Security（HSTS）は付けません。HTTPS の通信を終端する場所（リバースプロキシなど）で付けるヘッダーだからです。

まだ残っていること

このレッスンで、1 つの送信元からの連打は早めに 429 で止まるようになりました。一方で、次の課題は残っています。執筆時に確かめていないことも含めて挙げます。

  • HTTPS の終端と HSTS: この API は HTTP で待ち受けます。HTTPS の終端と Strict-Transport-Security は、前段のリバースプロキシなどで扱う前提です。
  • 多数の IP からの攻撃: IP 単位の制限は、1 つの IP からの連打にしか効きません。多数の IP から少しずつ送られると止まりません。その場合に HASH_SLOTS の順番待ちが 408 になるかは、確かめていません。
  • ロックアウト: 他人の email を狙った締め出しへの緩和策（ステップ 4 の読み物）は実装していません。
  • IPv6 のアドレスの扱い: アドレス 1 つをそのままキーにしています。/64 などの範囲にまとめるかどうかは検討していません。
  • limiter のメモリ: キーの件数が掃除で減ることは確かめましたが、プロセスのメモリ使用量は測っていません。状態は再起動で消え、複数台では台ごとに数えます。
  • ブラウザでの CORS: curl でヘッダーを確かめただけで、ブラウザでの動き（コンソールのメッセージなど）は確かめていません。
  • 配線ミスの 500: into_make_service_with_connect_info を忘れたときの 500 は text/plain で、契約の JSON の形になりません（つまずきポイント）。

まとめ

governor の limiter を AppState に持たせ、ログインに email 単位、登録・ログイン・いいねに IP 単位のレート制限を掛けました。 接続元の IP は既定で X-Forwarded-For を信用せず、信用する設定のときだけ右端を使います。 CORS は許可リストがあるときだけ有効にし、4 つのセキュリティヘッダーをエラーを含む全ての応答に付けました。
