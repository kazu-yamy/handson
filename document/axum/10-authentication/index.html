パスワードハッシュとログイン

  • ⏱ 所要時間: 60分
  • 📊 難易度: 初級
  • 👤 対象: 09 までの API に、利用者の登録とパスワードによるログインを足したい人
  • 📋 前提: Rust の基本文法、SQL の基本、09 で使った sqlx-cli（sqlx migrate）と結合テスト（#[sqlx::test]）の構成
  • 🔗 前提となる項目: 09: マイグレーション運用と記事リソース

🎯 このレッスンで学ぶこと

  • argon2（argon2id）でパスワードをハッシュ化し、PHC 形式の文字列として保存・検証する
  • 重いハッシュ計算を spawn_blocking で別スレッドに逃がし、debug ビルドでも argon2 だけを最適化する
  • 認証情報とセッションのテーブルをマイグレーションで追加する
  • 3 つの INSERT を 1 つのトランザクションにまとめて登録処理を書き、重複したメールアドレスを 409 にする
  • 乱数のトークンを発行し、DB にはトークンの SHA-256 だけを保存する
  • ログインの失敗を、理由を区別しない同じ 401 で返す

概要

09 では、記事の作成・更新・削除を API キーだけで保護していました。API キーさえあれば、誰の名義でも投稿できる状態です。 足りないのは、リクエストを送ってきたのが「誰であるか」を確かめる仕組み（認証）です。

このレッスンでは、その土台として利用者の登録とログインを作ります。 登録ではパスワードを安全な形に変えて保存し、ログインに成功したらトークンを発行します。 このレッスンで増えるエンドポイントは次の 2 つです。

メソッドパス認証成功時主なエラー
POST/auth/register不要201 {"user": {"id", "name"}, "token", "expires_at"}409（メールアドレスの重複）、422
POST/auth/login不要200（登録と同じ形）401（理由によらず同じ文言）、422（JSON の型違い）

既存のエンドポイント（/health・/users・/posts など）は 09 のまま変えません。

⚠️

このレッスンを終えても、記事の API はまだ守られていません

10 で作るのは、利用者が「誰であるか」を確かめるための登録とログインまでです。発行したトークンを受け取って確かめる処理はまだありません。記事の作成・更新・削除は 09 と同じく API キーだけで保護されており、他人の名義で投稿できる穴も残っています。

トークンを使ってリクエストの送り手を特定し、自分の記事だけを変更できるようにするのは、11「認証エクストラクタと認可」です。ログアウト（/auth/logout）と、自分の情報を返す /auth/me も 11 で作ります。

06 から使っている POST /users（API キーで保護）も残しています。ここで作った user には認証情報が無いので、ログインできません（ステップ 7 で確かめます）。11 で /users の書き込み系を外し、登録を /auth/register に一本化します。

パスワードをハッシュ化して検証する

パスワードの扱いを src/password.rs にまとめます。まずは、ハッシュ化と検証の 2 つの関数と、その単体テストを書きます。

DB にパスワードをそのまま（平文で）保存すると、DB が漏れたとき（バックアップの流出や SQL インジェクションなど）に、全員のパスワードがそのまま読めてしまいます。そこで、パスワードから計算したハッシュだけを保存します。ログインのときは、送られてきたパスワードから同じ計算をして照合します。

ハッシュには、意図的に計算を重くした argon2 の argon2id 方式を使います。SHA-256 のような速いハッシュだと、漏れたハッシュに対して、候補のパスワードを次々に計算して照合する総当たりが速く進んでしまいます。

Rust src/password.rs 
use argon2::{
    Argon2,
    password_hash::{PasswordHasher, PasswordVerifier, phc::PasswordHash},
};

// パスワードを argon2id でハッシュ化し、PHC 形式の文字列（$argon2id$v=19$...）で返す。
// ソルトは hash_password がランダムに作って文字列の中に埋め込む
pub fn hash_password(password: &str) -> Result<String, argon2::password_hash::Error> {
    let hash = Argon2::default().hash_password(password.as_bytes())?;
    Ok(hash.to_string())
}

// 保存してあるハッシュ文字列とパスワードが一致するか。壊れたハッシュ文字列も false 扱い
pub fn verify_password(password: &str, hash: &str) -> bool {
    let Ok(parsed) = PasswordHash::new(hash) else {
        return false;
    };
    Argon2::default()
        .verify_password(password.as_bytes(), &parsed)
        .is_ok()
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn hash_has_phc_format_and_differs_every_time() {
        let first = hash_password("correct horse battery").unwrap();
        let second = hash_password("correct horse battery").unwrap();
        println!("{first}");
        println!("{second}");
        assert!(first.starts_with("$argon2id$v=19$m=19456,t=2,p=1$"));
        assert_ne!(first, second); // ソルトが毎回違うので、同じパスワードでも別のハッシュになる
    }

    #[test]
    fn verify_accepts_right_password_and_rejects_wrong_one() {
        let hash = hash_password("correct horse battery").unwrap();
        assert!(verify_password("correct horse battery", &hash));
        assert!(!verify_password("wrong password", &hash));
        assert!(!verify_password(
            "correct horse battery",
            "not a phc string"
        ));
    }
}

  • Argon2::default() は、argon2id 方式と既定のパラメータで計算します。
  • hash_password は、ソルト（ハッシュごとに作るランダムな値）を自動で作り、結果の文字列に埋め込みます。返る文字列は PHC 形式と呼ばれ、方式・パラメータ・ソルト・ハッシュを 1 つにまとめたものです。

既定のパラメータについて

argon2 クレート（0.6.0）の既定値 m=19456（19 MiB）・t=2・p=1 をそのまま使います。これは OWASP Password Storage Cheat Sheet が argon2id の最小構成として挙げる設定の 1 つと同じ値です（2026 年 10 月確認）。サーバーに余裕があれば、より大きくしても構いません。

argon2 は意図的に重い計算で、最適化しない debug ビルドでは、さらに何倍も遅くなります。テストのたびに待たされないよう、argon2 と、argon2 が内部で使う blake2 だけを、debug ビルドでも最適化します。Cargo.toml の末尾に追記します。

ハッシュ計算を別スレッドで実行する

argon2 の計算は、CPU を十数ミリ秒占有します。Axum の async のハンドラは、tokio のワーカースレッドの上で、ほかのリクエストと交代しながら進みます。ハンドラの中で直接計算すると、その間、そのワーカースレッドではほかのリクエストが進みません。そこで tokio::task::spawn_blocking を使い、重い処理のための専用のスレッドで計算します。

use axum::{Json, extract::State, extract::rejection::JsonRejection, http::StatusCode};
use serde::{Deserialize, Serialize};
use std::collections::BTreeMap;

use crate::error::AppError;
use crate::password::hash_password_blocking;
use crate::routes::users::User;
use crate::state::AppState;

// password を持つので Debug / Serialize は付けない（付けるとログや応答にうっかり出せてしまう）
#[derive(Deserialize)]
pub struct RegisterRequest {
    name: String,
    email: String,
    password: String,
}

// 検証と正規化を済ませた入力
struct NewAccount {
    name: String,
    email: String,
    password: String,
}

impl RegisterRequest {
    // 不正なフィールドは全部まとめて 1 回の 422 で返す
    fn validate(self) -> Result<NewAccount, AppError> {
        let mut fields = BTreeMap::new();

        let name = self.name.trim().to_string();
        if !(1..=50).contains(&name.chars().count()) {
            fields.insert(
                "name".to_string(),
                vec!["name must be 1 to 50 characters".to_string()],
            );
        }

        // メールアドレスは前後の空白を取って小文字にそろえる
        let email = self.email.trim().to_lowercase();
        if !email.contains('@') || email.len() > 254 {
            fields.insert(
                "email".to_string(),
                vec!["email must contain @ and be 254 characters or less".to_string()],
            );
        }

        // 下限 15 は NIST SP 800-63B-4（パスワードだけで認証する場合は 15 文字以上）に合わせた値。上限は極端に長い入力を弾くため
        if !(15..=128).contains(&self.password.chars().count()) {
            fields.insert(
                "password".to_string(),
                vec!["password must be 15 to 128 characters".to_string()],
            );
        }

        if fields.is_empty() {
            Ok(NewAccount {
                name,
                email,
                password: self.password,
            })
        } else {
            Err(AppError::Validation(fields))
        }
    }
}

#[derive(Serialize)]
pub struct RegisterResponse {
    user: User,
}

pub async fn register(
    State(state): State<AppState>,
    payload: Result<Json<RegisterRequest>, JsonRejection>,
) -> Result<(StatusCode, Json<RegisterResponse>), AppError> {
    let Json(payload) = payload?;
    let account = payload.validate()?;

    // ハッシュ計算はトランザクションを開く前に済ませる（計算中にトランザクションを持ち続けない）
    let password_hash = hash_password_blocking(account.password).await?;

    // users と credentials の 2 つの INSERT を 1 つのトランザクションにする。
    // 途中で `return Err(...)` すると tx が drop され、それまでの INSERT は自動でロールバックされる
    let mut tx = state.pool.begin().await?;
    let user = sqlx::query_as::<_, User>("INSERT INTO users (name) VALUES (?) RETURNING id, name")
        .bind(&account.name)
        .fetch_one(&mut *tx)
        .await?;
    let inserted =
        sqlx::query("INSERT INTO credentials (user_id, email, password_hash) VALUES (?, ?, ?)")
            .bind(user.id)
            .bind(&account.email)
            .bind(&password_hash)
            .execute(&mut *tx)
            .await;
    match inserted {
        Ok(_) => {}
        // email の UNIQUE 制約に違反した = すでに登録されているメールアドレス
        Err(sqlx::Error::Database(error)) if error.is_unique_violation() => {
            return Err(AppError::Conflict("email already registered"));
        }
        Err(error) => return Err(error.into()),
    }
    tx.commit().await?;

    Ok((StatusCode::CREATED, Json(RegisterResponse { user })))
}
  • RegisterRequest には Debug も Serialize も付けません。パスワードを持つ型にこれらを付けると、{:?} でのログへの出力や、応答への混入が 1 行でできてしまうためです。
  • validate は、不正な項目を全部まとめて 1 回の 422 で返します（09 と同じ考え方）。name は前後の空白を除いて 1〜50 文字、email は前後の空白を除いて小文字にそろえ、@ を含む 254 文字以下、password は 15〜128 文字です。
  • 下限の 15 文字は、NIST SP 800-63B の 2025 年の改訂（SP 800-63B-4）に合わせた値です。この改訂は、パスワードだけで認証する場合は 15 文字以上を求め、8 文字は多要素認証の一部として使う場合の下限としています。上限の 128 文字は、同じ文書の「64 文字以上を受け付ける」を満たしたうえで、極端に長い入力を受け付けないための値です。
  • ハッシュ計算は、トランザクションを開く（pool.begin()）前に済ませます。計算をトランザクションの中（最初の INSERT の後）に置くと、その間 SQLite の書き込みロックを持ち続け、ほかの書き込みを待たせます。begin() の直後に置いても、計算の間プールの接続を 1 本占有します。
  • トランザクションは state.pool.begin().await? で始め、各クエリに &mut *tx を渡し、最後に tx.commit() で確定します。commit を呼ばずに関数を抜けると（return Err(...) や ? を含む）、tx が破棄され、それまでの INSERT は自動でロールバックされます。
  • &mut *tx は、Transaction を参照外し（Deref）した先の接続（SqliteConnection）を借りる書き方です。* を忘れて &mut tx と書いたときのエラーは、つまずきポイントに載せています。
  • メールアドレスの重複は、DB の UNIQUE 制約の違反（is_unique_violation()）で判定し、409 を返します。「先に SELECT で存在を確かめてから INSERT する」書き方だと、同じメールアドレスのリクエストが同時に 2 つ来たときに、両方とも通ってしまいます。

use base64::{Engine, engine::general_purpose::URL_SAFE_NO_PAD};

// 32 バイトの乱数を base64url（パディング無し、43 文字）にした、意味を持たない（不透明な）トークンを作る
pub fn generate_token() -> Result<String, getrandom::Error> {
    let mut bytes = [0u8; 32];
    getrandom::fill(&mut bytes)?;
    Ok(URL_SAFE_NO_PAD.encode(bytes))
}

// DB にはトークンそのものではなく SHA-256（32 バイト）だけを保存する。

pub fn hash_token(token: &str) -> Vec<u8> {

ログインの失敗で理由を区別しない理由

「そのメールアドレスは登録されていません」と返すと、ログインの API を使って、あるメールアドレスが登録済みかどうかを調べられてしまいます。そこで、ステータス・ヘッダー・本文を同じにし、ダミーのハッシュで応答時間の差も小さくしています。

読み物: 128 文字を超えるパスワードを、計算せずに 401 にする理由

登録できるパスワードは 128 文字までです。それより長いパスワードで登録された利用者はいないので、ログインで 128 文字を超えるパスワードが来たら、正しいパスワードのはずがありません。

そこで、128 文字を超える入力は、DB を引かず、ハッシュも計算せずに同じ 401 を返します。登録済みかどうかに関係なく同じ応答・同じ速さ（実測 1 ミリ秒前後）なので、登録の有無の手がかりにはなりません。分かるのは「128 文字を超えると速く返る」ことだけで、これは公開している検証規則と同じ情報です。argon2 の計算時間は入力の長さにほとんど左右されないので、この早期リターンは DoS 対策ではなく、無駄な計算を省くためのものです。

テスト login_with_a_huge_password_is_unauthorized は、100,000 文字のパスワードで同じ文言の 401 になることを確かめます。
