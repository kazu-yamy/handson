JSON リクエスト/レスポンス

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: 02 でルーティングとパスパラメーターを扱えるようになり、次に JSON で API を作りたい人
  • 📋 前提: Rust の基本文法（構造体・#[derive(...)] 属性・パターンによる分解）、cargo run と curl の基本操作ができること、JSON の書き方を知っていること
  • 🔗 前提となる項目: 02: ルーティングとハンドラ

🎯 このレッスンで学ぶこと

  • serde と serde_json を依存に追加し、axum の JSON サポートが既定で有効なことを確かめる
  • #[derive(Serialize)] を付けた構造体を Json<T> で返し、content-type: application/json になることを確かめる
  • #[derive(Deserialize)] を付けた構造体でリクエストの JSON を受け取り、201 Created を返す
  • 不正なリクエストが 415・400・422 のどれで拒否されるかを確かめる
  • json! マクロで、構造体を定義せずに JSON を返す
  • Path と Json を併用し、Json を引数の最後に置く必要があることをコンパイルエラーで確かめる

概要

02 で作ったサーバーのハンドラを、プレーンテキストではなく JSON を返すように書き換えます。 さらに、リクエストの本文で送られてきた JSON を Rust の構造体として受け取れるようにします。 Rust の値と JSON の変換には serde を使い、axum の Json を戻り値や引数（extractor）として使います。

このレッスンの完成時には、サーバーが次のルートへ応答します。02 から変わったところを太字にしています。

メソッドパス返す内容
GET/Hello, Axum!
GET/healthJSON {"status":"ok"}
GET/usersユーザー 2 件の JSON 配列
POST/users本文の JSON を受け取り、201 と作成したユーザーの JSON
GET/users/{id}ユーザー 1 件の JSON（id が数値でなければ 400）
PUT/users/{id}本文の JSON を受け取り、更新後のユーザーの JSON
GET/users/{user_id}/posts/{post_id}user {user_id} post {post_id}
GET/search受け取ったクエリパラメーターの一覧
（上記以外）どれにもマッチしないパス404 と本文 Not Found
ℹ️

使用バージョン

Rust（rustc）1.98.1 / cargo 1.98.1（Rust edition 2024）で動作を確認しています。クレートのバージョンは axum 0.8.9 / tokio 1.53.1 / serde 1.0.229 / serde_json 1.0.151 です。 バージョンは執筆時点（2026年9月）のものです。このレッスンでは serde と serde_json を新たに追加します。

2

serde と serde_json を追加する

JSON との変換には、Rust の定番のシリアライズ・ライブラリ serde と、その JSON 実装の serde_json を使います。 追加する前に、今の依存関係に serde 関連のクレートが入っているかを cargo tree で見てみます。サーバーは止めたままで構いません。

Terminal 
$ cargo tree | grep -i serde│   ├── serde_core v1.0.229│   ├── serde_json v1.0.151│   │   ├── serde_core v1.0.229│   ├── serde_path_to_error v0.1.20│   │   └── serde_core v1.0.229│   ├── serde_urlencoded v0.7.1│   │   └── serde v1.0.229│   │       └── serde_core v1.0.229

Cargo.toml にはまだ書いていないのに、serde_json が依存関係に含まれています。 axum は既定で json フィーチャーが有効になっており、Json を使うために axum 自身が serde_json に依存しているからです。

ℹ️

axum の JSON サポートは最初から有効

axum の Json は、Cargo.toml に axum = "0.8.9" と書いただけで使えます。フィーチャーを追加する必要はありません。

それでも serde と serde_json を自分で追加するのは、自分のコードで #[derive(Serialize)] や serde_json::json! を直接使うためです。axum に JSON サポートを足すためではありません。

cargo add で 2 つのクレートを追加します。serde には、構造体から変換処理を自動生成する derive フィーチャーを付けます。

Terminal 
$ cargo add serde --features derive    Updating crates.io index      Adding serde v1.0.229 to dependencies             Features:             + derive             + serde_derive             + std             - alloc             - rc             - unstable$ cargo add serde_json    Updating crates.io index      Adding serde_json v1.0.151 to dependencies             Features:             + std             - alloc             - arbitrary_precision             - float_roundtrip             - indexmap             - preserve_order             - raw_value             - unbounded_depth

Features: の + は有効、- は無効なフィーチャーです。serde の derive が有効になっていることを確認してください。変更後の Cargo.toml は次のとおりです。

TOML Cargo.toml

✅ 確認ポイント

Cargo.toml の [dependencies] に serde（features = ["derive"]）と serde_json が追加されていれば OK です。このステップではサーバーを起動しません。

3

構造体を JSON で返す（GET /users/{id}、GET /users）

ユーザーを表す構造体 User を定義し、GET /users/{id} と GET /users が JSON を返すようにします。 src/main.rs を次のように変更してください。

変更点は次の 3 つです。

  • use 文: axum::Json と serde::Serialize を追加します。
  • User 構造体: #[derive(Serialize)] を付けると、serde が構造体を JSON などの形式へ変換する処理を自動で生成します。
  • list_users・get_user: 戻り値の型を Json<...> にし、値を Json(...) で包んで返します。Json<Vec<User>> のように Vec をそのまま包めば、配列の JSON になります。
変更後の src/main.rs 全体を見る
Rust src/main.rs 
use axum::{
    Json, Router,
    extract::{Path, Query},
    http::StatusCode,
    routing::get,
};
use serde::Serialize;
use std::collections::HashMap;

#[derive(Serialize)]
struct User {
    id: u32,
    name: String,
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(root))
        .route("/health", get(health))
        .route("/users", get(list_users).post(create_user))
        .route("/users/{id}", get(get_user))
        .route("/users/{user_id}/posts/{post_id}", get(get_user_post))
        .route("/search", get(search))
        .fallback(not_found);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on {}", listener.local_addr().unwrap());
    axum::serve(listener, app).await.unwrap();
}

async fn root() -> &'static str {
    "Hello, Axum!"
}

async fn health() -> &'static str {
    "ok"
}

async fn list_users() -> Json<Vec<User>> {
    Json(vec![
        User {
            id: 1,
            name: "alice".to_string(),
        },
        User {
            id: 2,
            name: "bob".to_string(),
        },
    ])
}

async fn create_user() -> &'static str {
    "create user"
}

async fn get_user(Path(id): Path<u32>) -> Json<User> {
    Json(User {
        id,
        name: "alice".to_string(),
    })
}

async fn get_user_post(Path((user_id, post_id)): Path<(u32, u32)>) -> String {
    format!("user {user_id} post {post_id}")
}

async fn search(Query(params): Query<HashMap<String, String>>) -> String {
    format!("search params: {params:?}")
}

async fn not_found() -> (StatusCode, &'static str) {
    (StatusCode::NOT_FOUND, "Not Found")
}

4

JSON を受け取る（POST /users）

次は反対向きに、リクエストの本文（ボディ）で送られてきた JSON を受け取ります。 POST /users で {"name":"alice"} のような JSON を受け取り、作成したユーザーを 201 Created とともに返すようにします。

Diff src/main.rs 
- use serde::Serialize;+ use serde::{Deserialize, Serialize};  use std::collections::HashMap;   #[derive(Serialize)]  struct User {      id: u32,      name: String,  }+ + #[derive(Deserialize)]+ struct CreateUser {+     name: String,+ }   #[tokio::main]  ...      ])  } - async fn create_user() -> &'static str {-     "create user"- }+ async fn create_user(Json(payload): Json<CreateUser>) -> (StatusCode, Json<User>) {+     let user = User {+         id: 1,+         name: payload.name,+     };+     (StatusCode::CREATED, Json(user))+ }

変更点は次の 3 つです。

  • CreateUser 構造体: 受け取る JSON の形を表します。#[derive(Deserialize)] を付けると、JSON から構造体へ変換する処理が自動で生成されます。送る側と受け取る側で必要な derive が違う点に注意してください（Serialize は構造体 → JSON、Deserialize は JSON → 構造体）。
  • 引数 Json(payload): Json<CreateUser>: 02 の Path(id): Path<u32> と同じ書き方です。リクエストの本文が CreateUser に変換されて payload に入ります。
  • 戻り値 (StatusCode, Json<User>): 02 の not_found で使った (StatusCode, &'static str) と同じく、1 つ目の要素がステータスコード、2 つ目の要素が本文になります。
ℹ️

id は固定値

このレッスンではデータベースを使わないため、作成したユーザーの id は常に 1 を返します。本来は保存先（データベースなど）で採番します。データベースへの接続は 05 の項目で扱います。

変更後の src/main.rs 全体を見る
Rust src/main.rs

    Json, Router,
    extract::{Path, Query},
    http::StatusCode,
    routing::get,
};

use std::collections::HashMap;

#[derive(Serialize)]
struct User {
    id: u32,
    name: String,
}

struct CreateUser {
    name: String,
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(root))
        .route("/health", get(health))
        .route("/users", get(list_users).post(create_user))
        .route("/users/{id}", get(get_user))
        .route("/users/{user_id}/posts/{post_id}", get(get_user_post))
        .route("/search", get(search))
        .fallback(not_found);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on {}", listener.local_addr().unwrap());
    axum::serve(listener, app).await.unwrap();
}

async fn root() -> &'static str {
    "Hello, Axum!"
}

async fn health() -> &'static str {
    "ok"
}

async fn list_users() -> Json<Vec<User>> {
    Json(vec![
        User {
            id: 1,
            name: "alice".to_string(),
        },
        User {
            id: 2,
            name: "bob".to_string(),
        },
    ])
}

async fn create_user(Json(payload): Json<CreateUser>) -> (StatusCode, Json<User>) {
    let user = User {
        id: 1,
        name: payload.name,
    };
    (StatusCode::CREATED, Json(user))
}

async fn get_user(Path(id): Path<u32>) -> Json<User> {
    Json(User {
        id,
        name: "alice".to_string(),
    })

5

不正なリクエストの拒否（415 / 400 / 422）を確かめる

ステップ 4 のサーバーを起動したまま、POST /users にわざと正しくないリクエストを 4 種類送り、Json がどう拒否するかを確かめます。 コードは変更しません。

まず、-H 'content-type: application/json' を付けずに送ります。-d だけで送ると、curl は content-type: application/x-www-form-urlencoded を付けます。このため axum は JSON として受け付けず、415 を返します。

Terminal（2 つ目） 
$ curl -i -X POST http://127.0.0.1:3000/users -d '{"name":"alice"}'HTTP/1.1 415 Unsupported Media Typecontent-type: text/plain; charset=utf-8content-length: 54date: Sat, 26 Sep 2026 08:40:22 GMTExpected request with `Content-Type: application/json`

次に、content-type は正しく付けたうえで、本文の中身を 3 通りに変えて送ります。1 つ目は途中で切れた JSON、2 つ目は name がない JSON、3 つ目は name が文字列ではなく数値の JSON です。

Terminal（2 つ目） 
$ curl -i -X POST http://127.0.0.1:3000/users -H 'content-type: application/json' -d '{"name":'HTTP/1.1 400 Bad Requestcontent-type: text/plain; charset=utf-8content-length: 92date: Sat, 26 Sep 2026 08:40:22 GMTFailed to parse the request body as JSON: name: EOF while parsing a value at line 1 column 8$ curl -i -X POST http://127.0.0.1:3000/users -H 'content-type: application/json' -d '{}'HTTP/1.1 422 Unprocessable Entitycontent-type: text/plain; charset=utf-8content-length: 97date: Sat, 26 Sep 2026 08:40:22 GMTFailed to deserialize the JSON body into the target type: missing field `name` at line 1 column 2$ curl -i -X POST http://127.0.0.1:3000/users -H 'content-type: application/json' -d '{"name": 1}'HTTP/1.1 422 Unprocessable Entitycontent-type: text/plain; charset=utf-8content-length: 128date: Sat, 26 Sep 2026 08:40:22 GMTFailed to deserialize the JSON body into the target type: name: invalid type: integer `1`, expected a string at line 1 column 10

結果を表にまとめます。

送ったリクエストステータス拒否された理由
content-type: application/json を付けない415 Unsupported Media Typeリクエストが JSON であると示されていない
途中で切れた JSON（{"name":）400 Bad RequestJSON の構文として正しくない
必須フィールドがない（{}）422 Unprocessable EntityJSON としては正しいが、CreateUser に変換できない
型が違う（{"name": 1}）422 Unprocessable EntityJSON としては正しいが、CreateUser に変換できない

どのケースでも、ハンドラ create_user が呼ばれる前に Json がリクエストを拒否し、ステータスコードと本文を返しています。 ハンドラの中にエラー処理を書く必要はありません。なお、エラー本文の文言は axum の既定のものです。独自の形式に変える方法は、このレッスンでは扱いません。

💡

400 と 422 の違い

400 と 422 は混同しやすいので、区別して覚えておきましょう。400 は「JSON として読めない」（構文エラー）、422 は「JSON としては読めたが、Rust の型に合わない」（フィールドの欠落や型の不一致）です。本文の書き出しも Failed to parse と Failed to deserialize で分かれています。

✅ 確認ポイント

4 つのリクエストが順に 415・400・422・422 になれば OK です。確認できたら、サーバーを止めておきます。

6

json! マクロと Path + Json の併用（GET /health、PUT /users/{id}）

最後の機能追加として、2 つの変更をします。 1 つ目は、GET /health を {"status":"ok"} という JSON を返すように変えることです。このような小さな JSON のために構造体を定義するのは大げさなので、serde_json の json! マクロで組み立てます。 2 つ目は、ユーザーの名前を更新する PUT /users/{id} を追加することです。パスパラメーターの id と、本文の JSON の両方を受け取ります。

Diff src/main.rs

Rust src/main.rs 
use axum::{
    Json, Router,
    extract::{Path, Query},
    http::StatusCode,
    routing::get,
};
use serde::{Deserialize, Serialize};
use serde_json::json;
use std::collections::HashMap;

#[derive(Serialize)]
struct User {
    id: u32,
    name: String,
}

#[derive(Deserialize)]
struct CreateUser {
    name: String,
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(root))
        .route("/health", get(health))
        .route("/users", get(list_users).post(create_user))
        .route("/users/{id}", get(get_user).put(update_user))
        .route("/users/{user_id}/posts/{post_id}", get(get_user_post))
        .route("/search", get(search))
        .fallback(not_found);

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000")
        .await
        .unwrap();
    println!("listening on {}", listener.local_addr().unwrap());
    axum::serve(listener, app).await.unwrap();
}

async fn root() -> &'static str {
    "Hello, Axum!"
}

async fn health() -> Json<serde_json::Value> {
    Json(json!({ "status": "ok" }))
}

async fn list_users() -> Json<Vec<User>> {
    Json(vec![
        User {
            id: 1,
            name: "alice".to_string(),
        },
        User {
            id: 2,
            name: "bob".to_string(),
        },
    ])
}

async fn create_user(Json(payload): Json<CreateUser>) -> (StatusCode, Json<User>) {
    let user = User {
        id: 1,
        name: payload.name,
    };
    (StatusCode::CREATED, Json(user))
}

async fn get_user(Path(id): Path<u32>) -> Json<User> {
    Json(User {
        id,
        name: "alice".to_string(),
    })
}

async fn update_user(Path(id): Path<u32>, Json(payload): Json<CreateUser>) -> Json<User> {
    Json(User {
        id,
        name: payload.name,
    })
}

async fn get_user_post(Path((user_id, post_id)): Path<(u32, u32)>) -> String {
    format!("user {user_id} post {post_id}")
}

async fn search(Query(params): Query<HashMap<String, String>>) -> String {
    format!("search params: {params:?}")
}

async fn not_found() -> (StatusCode, &'static str) {
    (StatusCode::NOT_FOUND, "Not Found")
}

⚠️

本文を読む extractor は引数の最後に置く

Json のように、リクエストの本文を読み取る extractor は、ハンドラの引数の最後に置くというルールが axum にはあります。リクエストの本文は非同期のストリームで 1 度しか読めないため、本文を消費する extractor は 1 つだけ、しかも最後に置く必要があるのです。

ハンドラを .route(...) に登録した行で Handler<_, _> is not implemented というエラーが出たら、まず引数の順番を疑いましょう。

02 で見た Path<u32> の変換失敗（400）や、ステップ 5 の Json の拒否（415 / 400 / 422）は、リクエストを受けたときに起こる実行時のエラーでした。 extractor の順番の誤りは、それらと違ってコンパイル時に検出されます。

確認できたら、update_user の引数を Path(id): Path<u32>, Json(payload): Json<CreateUser> の順に戻してください。

✅ 確認ポイント

引数の順番を入れ替えると error[E0277] のコンパイルエラーになり、元の順番に戻したことを確認できれば OK です。このステップではサーバーを起動しません。
