認証エクストラクタと認可

  • ⏱ 所要時間: 60分
  • 📊 難易度: 初級
  • 👤 対象: 10 で発行したトークンを使って、記事の API を「本人だけが書き換えられる」状態にしたい人
  • 📋 前提: Rust の基本文法、SQL の基本、02・03 のエクストラクタ（ハンドラの引数。Json は最後に置く）、08 の結合テスト（#[sqlx::test]）の構成
  • 🔗 前提となる項目: 10: パスワードハッシュとログイン

🎯 このレッスンで学ぶこと

  • 認証（誰であるか）と認可（その人に許された操作か）の違いを説明できる
  • FromRequestParts を実装した AuthUser で、Authorization: Bearer のトークンから利用者を取り出す
  • GET /auth/me とログアウト（POST /auth/logout）を作り、期限切れのセッションを掃除する
  • 記事の著者をリクエストの本文ではなくトークンの持ち主で決め、更新・削除を所有者だけに限る
  • 他人の記事への操作を、403 ではなく存在しない記事と同じ 404 で返す
  • 07 から使ってきた API キーと、/users の書き込み系のルートを廃止する

概要

09 では、記事の作成・更新・削除を API キーだけで保護していました。API キーを持っていれば、本文の author_id に他人の id を書いて他人の名義で投稿でき、他人の記事も書き換え・削除できます。09 で意図的に残していた穴です。

10 では、利用者の登録とログインを作り、ログインに成功するとトークンを発行するところまで進めました。ただし、発行したトークンを受け取って確かめる処理はまだありません。

このレッスンでは、10 のトークンを使って、次の 2 つの検査を入れます。

  1. 認証: リクエストの Authorization: Bearer <トークン> から、送り手が「誰であるか」を確かめる。
  2. 認可: その人に「許された操作か」を確かめる。この API では、記事を更新・削除できるのは、その記事の著者だけです。

あわせて、07 から使ってきた API キー（x-api-key ヘッダー）を廃止します。/users の書き込み系（POST /users・PUT|DELETE /users/{id}）も削除し、利用者の登録は /auth/register に一本化します。このレッスンで変わるエンドポイントは次のとおりです。

メソッドパス10 まで11 から
GET/auth/me無し追加。トークンが必要。200 {"id", "name", "email"}
POST/auth/logout無し追加。トークンが必要。204（そのトークンのセッションだけを削除）
POST/postsAPI キー。著者は本文の author_idトークンが必要。著者はトークンの持ち主（本文の author_id は無視）
PATCH / DELETE/posts/{id}API キー。誰の記事でも変更できるトークンが必要。所有者だけ。他人の記事は 404
POST / PUT / DELETE/users、/users/{id}API キー削除（405 になる）

読み取り（GET /posts・GET /posts/{id}・GET /users・GET /users/{id}）は、これまでどおりトークン無しで呼べます。いいね（POST /posts/{id}/like）も同じです。

AuthUser エクストラクタと GET /auth/me を作る

リクエストからトークンを取り出し、その持ち主を特定する処理を、エクストラクタとして作ります。02・03 で見たとおり、エクストラクタはハンドラの引数に置く型で、Axum がハンドラを呼ぶ前にリクエストから値を作ります。Path や Json と同じように、自分で作った型もエクストラクタにできます。

エクストラクタには 2 種類のトレイトがあります。

  • FromRequestParts: リクエストの本文以外（Parts。メソッド・URI・ヘッダーなど）だけを読む。本文を消費しないので、1 つのハンドラに何個でも置ける。
  • FromRequest: 本文を読む（消費する）。Json がこちらで、03 で確かめたとおり、ハンドラの引数の最後に 1 つだけ置ける。

トークンは Authorization ヘッダーにあるので、FromRequestParts で作ります。新しいファイル src/auth_user.rs を作ってください。

Rust src/auth_user.rs 
use axum::{
    extract::FromRequestParts,
    http::{header::AUTHORIZATION, request::Parts},
};

use crate::error::AppError;
use crate::state::AppState;
use crate::token::hash_token;

// ハンドラの引数に置くだけで「ログイン済みであること」を要求する型。
// 認証に失敗すると、ハンドラの本体は呼ばれずに 401 が返る。
// Debug は付けない（token_hash をログに出す事故を防ぐ）
pub struct AuthUser {
    pub user_id: i64,
    pub name: String,
    // ログアウトで「このトークンのセッションだけ」を消すために持つ（トークンそのものは持たない）
    pub token_hash: Vec<u8>,
}

// 無い・形式が違う・見つからない・期限切れのどれでも同じ文言にする（理由を区別して教えない）
const UNAUTHORIZED: &str = "missing or invalid bearer token";

// `Authorization: Bearer <token>` からトークンを取り出す。スキーム名の大文字小文字は区別しない（RFC 9110）
fn bearer_token(parts: &Parts) -> Option<&str> {
    let value = parts.headers.get(AUTHORIZATION)?.to_str().ok()?;
    let (scheme, token) = value.split_once(' ')?;
    if scheme.eq_ignore_ascii_case("bearer") && !token.is_empty() {
        Some(token)
    } else {
        None
    }
}

#[derive(sqlx::FromRow)]
struct SessionUser {
    user_id: i64,
    name: String,
}

// Rejection に AppError を使うので、失敗は他のハンドラと同じ形式の 401 になる
impl FromRequestParts<AppState> for AuthUser {
    type Rejection = AppError;

    async fn from_request_parts(
        parts: &mut Parts,
        state: &AppState,
    ) -> Result<Self, Self::Rejection> {
        let token = bearer_token(parts).ok_or(AppError::Unauthorized(UNAUTHORIZED))?;
        let token_hash = hash_token(token);

        // 期限の判定は DB の時計（unixepoch()）で行う。アプリ側の時刻とずれる心配がない
        let session = sqlx::query_as::<_, SessionUser>(
            "SELECT u.id AS user_id, u.name \
             FROM sessions s JOIN users u ON u.id = s.user_id \
             WHERE s.token_hash = ? AND s.expires_at > unixepoch()",
        )
        .bind(&token_hash)
        .fetch_optional(&state.pool)
        .await?
        .ok_or(AppError::Unauthorized(UNAUTHORIZED))?;

        Ok(AuthUser {
            user_id: session.user_id,
            name: session.name,
            token_hash,
        })
    }
}
  • impl FromRequestParts<AppState> for AuthUser と、AppState 専用として実装します。from_request_parts の引数 state から DB のプール（state.pool）を使えます。
  • type Rejection = AppError; が、取り出しに失敗したときの応答の型です。AppError::Unauthorized は 10 で作ったもので、ほかのエラーと同じ JSON 形式の 401 に、WWW-Authenticate: Bearer ヘッダーを付けて返します。エクストラクタが失敗すると、ハンドラの本体は呼ばれません。
  • bearer_token は、Authorization の値を最初の空白で「スキーム名」と「トークン」に分けます。スキーム名の大文字と小文字は区別しません（コメントにあるとおり RFC 9110 の決まりで、bearer でも通します）。トークンが空の場合や、スキーム名が Bearer 以外（Basic など）の場合は None です。
  • 照合は、10 と同じ hash_token（SHA-256）で計算したハッシュで、sessions の token_hash を引きます。DB にはトークンそのものが無いので、トークンのまま引くことはできません。
  • 期限の判定は、SQL の s.expires_at > unixepoch() で、DB の時計を使います。10 で期限（expires_at）を決めたときも DB の unixepoch() を使ったので、アプリ側の時刻とずれる心配がありません。
  • 失敗の文言は UNAUTHORIZED の 1 つだけです。ヘッダーが無い・形式が違う・見つからない・期限切れのどれでも、同じ 401 を返し、理由を区別して教えません。10 のログイン失敗と同じ考え方です。
  • 照合の SQL そのものが失敗したとき（DB に届かないなど）は、401 ではなく 500（code: internal）になります。認証の失敗とは区別し、詳細はサーバーのログにだけ出します。
  • AuthUser には Debug を付けません。{:?} でログに出せないようにして、token_hash をうっかり出す事故を防ぎます。
  • token_hash を持たせているのは、ステップ 3 のログアウトで「今使っているトークンのセッションだけ」を消すためです。トークンそのもの（平文）は持ちません。

読み物: エクストラクタ方式とミドルウェア方式

10 までの API キーは、ルーターに route_layer でミドルウェアを掛け、そのルーターの全ルートを保護していました。このレッスンでは、ハンドラの引数に AuthUser を置くエクストラクタ方式に切り替えます。

  • エクストラクタ方式では、認証が要るハンドラだけに引数を書きます。ハンドラは、認証済みの利用者（user.user_id）を型として受け取れます。

  • エラーの形がそろっていない応答: 削除したルートなどへの 405 は本文が空で、09 で見たパスの型違い（/posts/abc）の 400 は text/plain のままです。どちらも、ほかのエラーと同じ JSON の形になっていません。
  • 期限切れのセッションの掃除: ログイン時にまとめて消す簡易版です。ログインが無い間は、期限切れの行が DB に残ります（照合では弾かれます）。

まとめ

FromRequestParts を実装した AuthUser で、Bearer トークンから利用者を特定しました。 記事の著者はトークンの持ち主で決め、更新・削除は所有者だけに限り、他人の記事は存在しない記事と同じ 404 で返します。 API キーと /users の書き込み系は廃止しました。

観点このレッスンでの扱い
認証AuthUser（FromRequestParts<AppState>）。Authorization: Bearer のトークンの SHA-256 で sessions を引き、期限は unixepoch() で判定する。失敗は全て同じ 401（WWW-Authenticate: Bearer 付き）
引数の順AuthUser は Json より前。認証が本文の解析より先に走る
ログアウトと期限ログアウトはそのトークンのセッション行だけを削除。期限切れの行はログイン時に掃除する（簡易版）
