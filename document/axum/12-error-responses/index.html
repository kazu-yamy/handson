エラー応答の統一と入力の防御

  • ⏱ 所要時間: 60分
  • 📊 難易度: 初級
  • 👤 対象: 11 までの API で、すべてのエラー応答を同じ JSON の形にそろえ、本文のサイズ・処理時間・パスワードハッシュの計算に上限を設けたい人
  • 📋 前提: Rust の基本文法、02・03 のエクストラクタ、06・07 の AppError と log_request、08 の結合テスト、11 の AuthUser
  • 🔗 前提となる項目: 11: 認証エクストラクタと認可

🎯 このレッスンで学ぶこと

  • エクストラクタ（Json・Path・Query）の拒否を AppError に変える包み（AppJson・AppPath・AppQuery）を作り、エラーの message を固定の文言にする
  • 405 を契約の JSON にし、Bearer の後ろの複数の空白を受け付ける
  • 本文サイズの上限（64 KiB、413）とタイムアウト（408）を層（レイヤー）で掛け、本文の無いエラーを JSON に補う安全網を置く
  • 層を重ねる順番で結果が変わることを、テストと curl で確かめる
  • パスワードハッシュの同時実行数を Semaphore で 4 個に絞る

概要

09〜11 では、次の課題を「12 で扱う」として残してきました。

  • パスの型違い（09）: /posts/abc のように {id} が数値として読めないと、Axum が text/plain の 400 を返す。ほかのエラーと同じ JSON の形になっていない。
  • 本文サイズとハッシュ計算の上限（10）: 大量の要求で CPU を使わせる攻撃への対策として、本文サイズとパスワードハッシュの同時実行数に上限を設ける。
  • 405 の本文と、本文サイズ・タイムアウト（11）: 削除したルートなどへの 405 は本文が空。本文のサイズの上限とタイムアウトも無い。

ステップ 1 で「直す前」の応答を確かめると、ほかにも 2 つの問題が見つかります。1 つは、拒否の message が Axum や serde_json の原文のままで、送った値（パスワードなど）がそのまま応答に出ることです。もう 1 つは、Authorization: Bearer の後ろの空白が 2 つ以上だと 401 になることです。このレッスンでは、これらをまとめて片付けます。直す前と直した後の応答は次のとおりです。

セキュリティの考え方

このレッスンで入れる仕組みが何のためのものかを、先に一覧表でまとめます。詳しくは各ステップで説明します。

論点このレッスンでの扱いステップ
エラーの形をそろえるすべてのエラーを {"error": {"code", "message"}} の形にする。主な理由は API の契約で、クライアントは code を見る 1 通りの処理でエラーを扱える。text/plain や空の本文が混ざらない2〜4
入力値を応答に出さない拒否の message を、ステータスごとの固定の文言にする。直す前は、パスワードに数値を送ると、その値が message にそのまま出ていた1・2
詳細はどこに残すかDB のエラーなど内部の詳細は、06 から応答には出さずサーバーのログにだけ出している。拒否の詳細（Axum の原文）は送られた値を含みうるので、ログにも出さない2
本文サイズの上限Axum の既定は 2 MiB。この API の本文（記事の本文は 5000 文字まで）には大きすぎるので 64 KiB にし、超えたら 413。検証や DB の検索まで進ませない4・5
タイムアウト1 つのリクエストの処理時間に上限（既定 10 秒）を設け、超えたら 408。ただし、打ち切っても、別スレッドで計算中のパスワードハッシュは止まらない4・5・6
ハッシュ計算の同時実行数argon2 は 1 回で 19 MiB のメモリと十数ミリ秒の CPU を使う。上限が無いと、同時に来た要求の数だけ並んで走る。同時に 4 個までにし、超えた分は順番を待つ。待ち時間もタイムアウトに含まれる6
層の順番層の順番（と、ステップ 3 の時点での method_not_allowed_fallback の位置）を間違えても、ビルドは通り、警告も出ない。テストと curl で確かめる3・4・つまずき
SQL を文字列で組み立てない値は .bind() で渡す。sqlx 0.9 は、format! で組み立てた SQL をコンパイルエラーにする（読み物）7

このレッスンを終えても、まだ残っている課題があります。最後の「まだ残っていること」にまとめます。

拒否を AppError に変える包みを作る

エクストラクタは、リクエストから値を作れないと、ハンドラを呼ばずに「拒否（Rejection）」を返します。これまでは、Json と Query の拒否を Result で受け取っていました。ハンドラの引数を payload: Result<Json<T>, JsonRejection> とする書き方です。取り出すときに、let Json(payload) = payload?; で AppError に変えます。

この書き方は、書き忘れても動いてしまいます。実際に Path は、02 から 11 までずっと Path(id): Path<i64> のままでした。そのため、拒否が Axum の既定の text/plain で返っていました（ステップ 1 の /posts/abc）。そこで、拒否を必ず AppError に変える型を作り、ハンドラの引数の型をその型に置き換えます。新しいファイル src/extract.rs を作ってください。

Rust src/extract.rs 
use axum::extract::{FromRequest, FromRequestParts, Path, Query, Request};
use axum::http::request::Parts;
use serde::de::DeserializeOwned;

use crate::error::AppError;

// axum の Json / Path / Query の薄い包み。中身は axum のものをそのまま呼び、
// 拒否（Rejection）だけを AppError に変える。ハンドラの引数の型を置き換えるだけで、
// 失敗時の応答が契約の JSON にそろう（`Result<Json<T>, JsonRejection>` と書き忘れる余地が無い）

pub struct AppJson<T>(pub T);

impl<S, T> FromRequest<S> for AppJson<T>
where
    S: Send + Sync,
    T: DeserializeOwned + Send,
{
    type Rejection = AppError;

    async fn from_request(req: Request, state: &S) -> Result<Self, Self::Rejection> {
        let axum::Json(value) = axum::Json::<T>::from_request(req, state).await?;
        Ok(AppJson(value))
    }
}

pub struct AppPath<T>(pub T);

impl<S, T> FromRequestParts<S> for AppPath<T>
where
    S: Send + Sync,
    T: DeserializeOwned + Send,

// Router::layer は「後に書いたものほど外側」になる。リクエストは外側から内側へ、応答は内側から外側へ通る
pub fn apply(router: Router, config: &Config) -> Router {
    router
        // 一番内側: 本文を読むエクストラクタ（Json など）にだけ効く。超えると JsonRejection 経由で 413 になる
        .layer(DefaultBodyLimit::max(MAX_BODY_BYTES))
        // 処理に時間がかかりすぎたら 408 にする。この層が返す応答は本文が空
        .layer(TimeoutLayer::with_status_code(
            StatusCode::REQUEST_TIMEOUT,
            config.request_timeout,
        ))
        // 本文の無いエラー応答を契約の JSON に補う。TimeoutLayer より外側に置かないと 408 が素通りする
        .layer(middleware::map_response(fill_empty_error_body))
        // 一番外側: タイムアウトで捨てられたリクエストもログに残す
        .layer(middleware::from_fn(log_request))
}

// ステータスが 4xx / 5xx で content-type が無い（＝どの層も本文を作っていない）応答を、契約の JSON に置き換える。
// 将来、本文の空のエラーを返す層を足しても、形がそろう安全網。Allow など元のヘッダーは残す
async fn fill_empty_error_body(response: Response) -> Response {
    let status = response.status();
    let is_error = status.is_client_error() || status.is_server_error();
    if !is_error || response.headers().contains_key(CONTENT_TYPE) {
        return response;
    }
    let (mut parts, _) = response.into_parts();
    parts.headers.remove(CONTENT_LENGTH);
    let mut filled = error_response(status, code_for_status(status), message_for_status(status));
    filled.headers_mut().extend(parts.headers);
    filled
}

async fn log_request(req: Request, next: Next) -> Response {
    let method = req.method().clone();
    let uri = req.uri().clone();
    let start = Instant::now();

    let response = next.run(req).await;

    let elapsed: Duration = start.elapsed();
    println!("{method} {uri} -> {} ({elapsed:?})", response.status());
    response
}

Router::layer は、後に書いたものほど外側になります。リクエストは外側から内側へ、応答は内側から外側へ通ります。apply の層は、外側から順に次のとおりです。

  1. log_request（一番外側）: タイムアウトで打ち切られたリクエストも含めて、全てのリクエストを 1 行ずつログに出す。
  2. fill_empty_error_body（安全網）: 内側から返ってきた応答のうち、ステータスが 4xx / 5xx で、content-type の無いものを、契約の JSON に置き換える。content-type が無いのは、どこも本文を作っていない応答。元の応答のヘッダー（Allow など）は引き継ぐ。
  3. TimeoutLayer: 処理が config.request_timeout を超えたら打ち切って 408 を返す。この 408 は本文が空なので、外側の安全網で JSON になる。
  4. DefaultBodyLimit（一番内側）: 本文を読むエクストラクタ（AppJson など）が読める大きさを 64 KiB にする。超えると拒否になり、ステップ 2 の変換で 413 の JSON になる。

安全網を TimeoutLayer より内側に置くと、408 は安全網を通らずに外へ出ていき、本文の無い応答のままになります。これもビルドは通り、警告も出ません（「つまずきポイント」）。順番は、テストで確かめます。

10 で作ったパスワードハッシュ（argon2id）は、意図的に重い計算です。10 の計測用のテストで、1 回の時間を確かめます。

ハッシュと検証は、どちらも 1 回あたり十数ミリ秒です。argon2 の既定の設定（PHC 文字列の m=19456）では、1 回の計算で 19,456 KiB（19 MiB）のメモリを使います。10 では、この計算を spawn_blocking で別スレッドに逃がしましたが、同時に走る数には上限がありませんでした。ログインが 40 件同時に来れば、40 個の argon2 が同時に走ります。

そこで、同時に走る argon2 の数を、tokio の Semaphore で 4 個に絞ります。Semaphore は「許可証（permit）」を決まった数だけ持ち、取れなかった要求は、どれかが返されるまで待ちます。src/password.rs を次のように変えます。

  • HASH_SLOTS は static なので、サーバー全体で 1 つです。どの利用者・どの接続元からのリクエストでも、同時に計算するのは 4 個までです。5 個目からは、acquire().await で順番を待ちます。
  • 待っている間も、ステップ 4 のタイムアウトが効きます。待ちが長くなれば、そのリクエストは 408 になります。
  • permit（acquire の戻り値）は、spawn_blocking のクロージャの中へ move し、let _permit = permit; で計算が終わるまで持ちます。コメントにあるとおり、タイムアウトで呼び出し側が打ち切られても、計算中のスレッドが permit を持ち続け、計算が終わってから返します。打ち切られた後も、別スレッドの計算そのものは止まりません。計算が終わるまで permit を持たせて、同時に動く argon2 が上限を超えないようにしています。permit をクロージャの外に持った場合の挙動は、この教材では試していません。
  • HASH_SLOTS と MAX_CONCURRENT_HASHES は、次のテストから使うので pub にしています。

// （同じファイルの別のテストと並列に走ると、permit の数が揺れる）
#[tokio::test]
async fn concurrent_hashes_are_limited_and_slots_are_always_returned() {
    // 1. 上限より多い 8 個を同時に呼んでも、全部成功する（待たされるだけ）。終わったら permit は全部戻る
    let tasks: Vec<_> = (0..8)
        .map(|_| tokio::spawn(hash_password_blocking("correct horse battery".to_string())))
        .collect();
    for task in tasks {
        assert!(task.await.unwrap().is_ok());
    }
    assert_eq!(HASH_SLOTS.available_permits(), MAX_CONCURRENT_HASHES);

    // 2. 順番待ちもタイムアウトに含まれる。ハッシュだけをするハンドラに 100ms のタイムアウトを掛け、
    //    40 件を同時に送る（4 個ずつ処理するので、後ろの方は 100ms に間に合わず 408）
    let mut config = test_config();
    config.request_timeout = Duration::from_millis(100);
    let router = Router::new().route(
        "/hash",
        get(|| async {
            hash_password_blocking("correct horse battery".to_string())
                .await
                .map(|_| "done")
        }),
    );
    let app = layers::apply(router, &config);
    let start = Instant::now();
    let tasks: Vec<_> = (0..40)
        .map(|_| tokio::spawn(send_raw(app.clone(), get_request("/hash"))))
        .collect();
    let mut ok = 0;
    let mut timed_out = 0;
    for task in tasks {
        let (status, _, _) = task.await.unwrap();
        match status {
            StatusCode::OK => ok += 1,
            StatusCode::REQUEST_TIMEOUT => timed_out += 1,
            other => panic!("unexpected status {other}"),
        }
    }
    println!(
        "200: {ok}, 408: {timed_out}, elapsed: {:?}",
        start.elapsed()
    );
    assert!(ok >= 1 && timed_out >= 1, "200: {ok}, 408: {timed_out}");

    // 3. タイムアウトで future が捨てられても、計算中のスレッドが permit を持ち続け、終わったら返す。
    //    計算が全部終わるのを待てば、permit は元の数に戻る
    for _ in 0..100 {
        if HASH_SLOTS.available_permits() == MAX_CONCURRENT_HASHES {
            return;
        }
        tokio::time::sleep(Duration::from_millis(50)).await;
    }
    panic!(
        "permits were not returned: {}",
        HASH_SLOTS.available_permits()
    );
}

HASH_SLOTS はプロセス全体で 1 つなので、ほかのテストが同時にハッシュを計算すると、空いている permit の数が揺れます。password.rs の単体テストにも、ハッシュを計算するテストがあります。そこで、テストを別のファイル（cargo test では別のテストバイナリー、つまり別のプロセス）に置き、1 つのテストの中で順番に確かめます。

  1. 上限より多い 8 個を同時に呼んでも、全部成功する（待たされるだけ）。終わった後、permit は 4 個に戻る。
  2. ハッシュだけを計算するハンドラへ、100 ミリ秒のタイムアウトを掛けて 40 件を同時に送る。4 個ずつ処理されるので、後ろの方は間に合わず 408 になる。
  3. 408 になった後も、計算が終われば permit は 4 個に戻る。

ただし、AssertSqlSafe は「SQL に利用者の入力が混ざらないことを、書いた人が確かめた」という目印で、包むだけで安全になるわけではありません。この教材では、次の書き方に統一しています。

  • 値は SQL の文字列に入れず、.bind() で渡す。
  • 列名や並び順のような識別子を切り替える必要があるときは、利用者の入力を SQL に入れず、match で固定の文字列リテラルを選ぶ。
