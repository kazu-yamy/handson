Swift Testing

  • ⏱ 所要時間: 60分
  • 📊 難易度: 初級
  • 👤 対象: @Test と #expect でテストを書いたことがあり、増えてきたテストを整理して、失敗の原因を読み取りやすくしたい人
  • 📋 前提: 08 で SwiftData に保存する HandsonApp プロジェクトが手元にあること。Swift Testing の @Test・#expect・#expect(throws:)・try #require を使ったことがあること
  • 🔗 前提となる項目: 08 SwiftData

🎯 このレッスンで学ぶこと

  • #expect と #require の違いを、失敗したときの出力で確かめる
  • @Suite と表示名でテストを整理し、init に共通の準備を書く
  • arguments: でパラメータ化テストを書き、全組み合わせと zip を使い分ける
  • トレイト（タグ・無効化・条件付きの実行・課題の関連付け・制限時間・直列実行）を付け、コマンドラインで実行するテストを絞り込む
  • withKnownIssue で既知の不具合を記録し、confirmation でコールバックの回数を確かめる
  • XCTest で UI テストを書き、起動引数でメモリ上のデータベースに切り替える
  • コードカバレッジを計測し、ファイルごとの傾向を読む

概要

01〜08 では、作った機能を確かめるために @Test と #expect を使ってきました。この項目では、Swift Testing の機能を体系的に学び、既存のテストを整理します。 アプリの機能はほとんど変えません。テストを読みやすくまとめ、失敗したときに原因が分かる書き方を身につけます。

#expect と #require から始め、@Suite での整理・パラメータ化・トレイト・既知の問題・UI テスト・カバレッジの順に進めます。1 ステップで扱う概念は 1 つです。 完成すると、ユニットテストは 59 から 73 に増え、UI テストが 2 つ加わります。テストの結果は、全てターミナルの出力で確かめます。

ℹ️

使用バージョンと並行処理の設定

macOS 26.6.2 / Xcode 27.0 / Swift 6.4 / iPhone 17（iOS 27.0）のシミュレータは 08 と同じです。バージョンは執筆時点（2026年10月）のものです。Swift Testing は Xcode に含まれているので、追加のパッケージは要りません。

アプリターゲットは 08 と同じく、SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor です。一方、テストターゲット（HandsonAppTests）にはこの設定が無く、テストの型は既定でメインアクターの外（nonisolated）にあります。 そのため、メインアクターのコードを呼ぶテストの型には @MainActor を付けます。01 から続けてきた書き方です。

2

#expect と #require の違いを失敗の出力で確かめる

#expect と #require は、どちらも条件を確かめるマクロです。違いは、失敗した後にテストを続けるかどうかです。わざと失敗するテストを書いて、出力を比べます。 HandsonAppTests フォルダに ExpectRequireTests.swift を追加し、次の内容にします（Targets は HandsonAppTests）。

Swift HandsonAppTests/ExpectRequireTests.swift（わざと失敗させる版） 
import Testing
@testable import HandsonApp

struct ExpectRequireTests {

    @Test func expectKeepsGoing() {
        let item = TodoItem(title: "買い物")
        #expect(item.title == "牛乳")
        #expect(item.priority == .high)
        #expect(item.isDone)
    }

    @Test func requireStopsHere() throws {
        let titles: [String] = []
        let first = try #require(titles.first)
        #expect(first == "A")
    }
}
  • expectKeepsGoing(): タイトル・優先度・完了状態の 3 つを、全て間違った値で確かめます。
  • requireStopsHere(): 空の配列の first（nil）を try #require で取り出します。#require は失敗するとエラーを投げるので、テスト関数に throws を付けます。

-only-testing:HandsonAppTests/ExpectRequireTests で、このスイートだけを実行します。

💡

-parallel-testing-enabled NO を付けないと、テストごとの行が出ない

-parallel-testing-enabled NO を付けずに実行すると、xcodebuild の標準出力に Swift Testing の ✔ の行が 1 つも出ませんでした。出たのは ** TEST SUCCEEDED ** だけです。 この項目では、出力を読みながら進めるので、08 と同じく全てのテストのコマンドにこのオプションを付けます。

出力を確かめたら、ファイルの中身を通る版に置き換えます。@Suite("…") と @Test("…") の文字列は次のステップで説明します。

Swift HandsonAppTests/ExpectRequireTests.swift 
import Testing
@testable import HandsonApp

@Suite("#expect と #require")
struct ExpectRequireTests {

    @Test("#expect は失敗しても続行する（式の中身が展開される）")
    func expectShowsExpandedValues() {
        let item = TodoItem(title: "買い物")
        #expect(item.title == "買い物")
        #expect(item.priority == .medium)
        #expect(!item.isDone)
    }

    @Test("#require は失敗するとテストを中断し、オプショナルをアンラップする")
    func requireUnwrapsOptional() throws {
        let titles = ["A", "B"]
        let first = try #require(titles.first)  // nil なら、ここでテストが終わる
        #expect(first == "A")
    }
}
  • try #require(titles.first) は、値が nil でなければアンラップした値（ここでは String）を返します。オプショナルを取り出してから先を確かめたいときに使います。
  • 使い分けの目安: 後ろの確認が前提を満たさないと意味が無い（nil のまま続けても無駄な失敗が増える）ときは #require、それ以外は #expect です。

✅ 確認ポイント

わざと失敗させた版で、expectKeepsGoing() は with 3 issues、requireStopsHere() は with 1 issue になることを確かめます。通る版に置き換えた後の実行は、次のステップでまとめて行います。

トレイトとタグを付け、実行するテストを絞り込む

@Test や @Suite の引数に渡す .tags(…) や .disabled(…) を「トレイト」と呼びます。テストに分類や実行の条件を付けます。 まずタグを宣言します。HandsonAppTests フォルダに Tags.swift を追加し、次の内容にします（Targets は HandsonAppTests）。

Swift HandsonAppTests/Tags.swift 
import Testing

// タグは Tag の static プロパティとして宣言する。@Tag を付ける
extension Tag {
    @Tag static var validation: Self
    @Tag static var networking: Self
    @Tag static var slow: Self
}

主なトレイトを 1 つずつ付けたスイートを作ります。同じフォルダに TraitsTests.swift を追加します。

Swift HandsonAppTests/TraitsTests.swift 
import Foundation
import Testing
@testable import HandsonApp

@MainActor
@Suite("トレイト")
struct TraitsTests {

    @Test("タグを付ける", .tags(.validation, .slow))
    func tagged() {
        #expect(validatedName("Taro") == .success("Taro"))
    }

    @Test("条件を満たすときだけ実行する", .enabled(if: ProcessInfo.processInfo.environment["RUN_EXTRA"] != nil))
    func enabledIf() {
        #expect(Bool(true))
    }

    @Test("理由を付けて無効化する", .disabled("API の仕様が決まるまで止める"))
    func disabled() {
        #expect(Bool(false))
    }

    @Test("関連する課題を記録する", .bug("https://example.com/issues/123", "名前の上限を変えたい"))
    func bug() {
        #expect(validatedName("Taro") == .success("Taro"))
    }

    @Test("制限時間を付ける", .timeLimit(.minutes(1)))
    func timeLimit() async throws {
        try await Task.sleep(for: .milliseconds(10))
    }
}

// 既定では、テストは並列に実行される。.serialized を付けたスイートの中は 1 つずつ順番に実行する
@Suite("直列実行", .serialized)
struct SerializedTests {
    @Test(arguments: [1, 2, 3])
    func runsOneAtATime(n: Int) async throws {
        try await Task.sleep(for: .milliseconds(100))
        #expect(n > 0)
    }
}
  • .tags(.validation, .slow): テストにタグを付けます。タグは Tags.swift で宣言したものだけ使えます。
  • .enabled(if: 条件): 条件が真のときだけ実行します。ここでは環境変数 RUN_EXTRA があるときだけです。
  • .disabled("理由"): テストを実行せず、理由を出力に残します。コメントアウトと違い、ビルドは通り続けるので、コードが古くなりません。
  • .bug("URL", "説明"): 関連する課題をテストに結び付けます。テストの成否にかかわらず、課題の URL は xcodebuild の出力に出ません。
  • .timeLimit(.minutes(1)): 制限時間を超えたら失敗にします。指定できるのは分の単位だけです。
  • .serialized（SerializedTests）: 既定では、テストは並列に実行されます。.serialized を付けたスイートの中は、1 つずつ順番に実行します。共有の資源を使うテストを守るときに使います。

import Foundation
import Testing
@testable import HandsonApp

@MainActor
@Suite("既知の問題と confirmation")
struct KnownIssueAndConfirmationTests {

    // TodoStore.toggle は title で項目を探すので、同じタイトルが 2 つあると先頭の項目が切り替わる。
    // 直すまでの間、この失敗を「既知の問題」として記録する
    @Test("同じタイトルの 2 件目を toggle できる")
    func toggleSecondItemWithSameTitle() {
        let store = TodoStore(items: [TodoItem(title: "A"), TodoItem(title: "A")])
        withKnownIssue("toggle は title で探すため、同名の項目は先頭が切り替わる") {
            store.toggle(store.items[1])
            #expect(store.items[1].isDone)
        }
    }

    @Test("完了済みの項目を 1 件削除すると、コールバックが 1 回呼ばれる")
    func removeCompletedCallsBackOnce() async {
        let store = TodoStore(items: [
            TodoItem(title: "A"), TodoItem(title: "B", status: .done(.now)),
        ])
        await confirmation("onRemove が呼ばれる", expectedCount: 1) { removed in
            store.removeCompleted { _ in removed() }
        }
        #expect(store.items.map(\.title) == ["A"])
    }

    @Test("完了済みが無ければ、コールバックは呼ばれない")
    func removeCompletedNeverCallsBack() async {
        let store = TodoStore(items: [TodoItem(title: "A")])
        await confirmation("onRemove は呼ばれない", expectedCount: 0) { removed in
            store.removeCompleted { _ in removed() }
        }
        #expect(store.items.count == 1)
    }
}
  • withKnownIssue("説明") { … }: クロージャの中で起きた失敗を「既知の問題」として記録します。テスト自体は成功の扱いになります。
  • confirmation("説明", expectedCount: 1) { removed in … }: クロージャの中で removed() が呼ばれた回数を数え、expectedCount と一致しなければ失敗にします。expectedCount: 0 にすると、「呼ばれないこと」を確かめられます。confirmation は async の関数なので、await を付け、テストも async にします。

    }
}
  • app.launchArguments = ["-uiTesting"]: 起動引数を付けてアプリを起動します。UI テストは別のプロセスのアプリを操作するので、@testable import HandsonApp でアプリのコードを直接呼ぶことはできません。アプリの挙動を変えたいときは、このように起動引数で伝えます。
  • 画面の部品は、表示されている文言で探します。textFields["新しいタスク"] はプレースホルダー、buttons["追加"] はボタンの文字です。アイコンだけのボタンは、05 から付けている accessibilityLabel の「完了にする」「未完了に戻す」で探せます。
  • waitForExistence(timeout: 5): 部品が現れるまで最大 5 秒待ちます。画面の更新を待たずに exists を調べると、表示前に判定してしまうことがあります。
  • testAddedTaskAppearsInList の最初の確認（「ToDo はまだありません」）は、保存済みのデータが表示されていない、つまりメモリ上のコンテナで起動したことの確認も兼ねます。

UI テストのターゲットだけを実行します。シミュレータでアプリが起動し、文字の入力とタップが自動で行われます。ビルドを含めて 1 分ほどかかります。

演習

以下のチェックリストを使って、このレッスンの内容を振り返りましょう。

つまずきポイント

💡

テストの結果の行が 1 つも出ない

xcodebuild に -parallel-testing-enabled NO を付けているかを確かめてください。付けないと、Swift Testing の ✔ の行が標準出力に出ません（ステップ 2）。

💡

Test run with 0 tests で成功してしまう

-only-testing でテスト関数を指定するときは、'HandsonAppTests/ValidationTests/emptyNameThrows()' のように括弧を付けます。スイートは表示名ではなく型名で指定します（ステップ 5）。

💡

call to main actor-isolated … in a synchronous nonisolated context が出る

アプリのコードを呼ぶテストの型に @MainActor が付いているかを確かめてください。テストターゲットの型は既定で nonisolated です（ステップ 5）。

まとめ

#expect は失敗しても続行し、#require は中断することを、値が展開される失敗の出力で確かめました。@Suite と表示名でテストを整理し、テストごとに作られるインスタンスの init に共通の準備を書きました。 arguments: でパラメータ化テストを書き、トレイトでタグや実行の条件を付けました。withKnownIssue で既知の不具合を記録し、confirmation でコールバックの回数を確かめました。 UI テストは XCTest で書き、起動引数でメモリ上のコンテナに切り替えました。カバレッジを計測すると、モデルはほぼ網羅されていて、View はテストが少ないと分かりました。 次の項目では、WidgetKit と App Intents を使います。
