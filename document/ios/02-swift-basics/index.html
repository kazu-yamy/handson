2

オプショナルで「値が無い」を扱う（Profile）

最初のモデルとして、名前と省略可能なニックネームを持つ Profile を作ります。 まず、モデルを入れる Models フォルダとファイルを Xcode で作ります。

  1. ナビゲータで HandsonApp フォルダ（黄色）を右クリックし、New Group（または New Folder）で Models を作ります。
  2. Models を右クリックし、New File from Template…（メニューの File > New > File from Template…、⌘ + N でも可）を選びます。iOS > Swift File を選び、名前を Profile.swift、Targets は HandsonApp にチェックを付けて作成します。
  3. 同じ手順で、HandsonAppTests フォルダに ProfileTests.swift を作ります。Targets は HandsonAppTests にチェックを付けます。

01 で見たとおり、3 つのフォルダは同期フォルダです。Finder やエディタで HandsonApp/Models/Profile.swift のようにファイルを置くだけでも、ターゲットへ取り込まれます。project.pbxproj の編集は不要です。 以降のステップでファイルを追加するときも、どちらの方法でもかまいません。

Profile.swift に次の内容を書きます。

Swift HandsonApp/Models/Profile.swift 
struct Profile {
    let name: String
    let nickname: String?

    // if let: nil でなければ取り出す
    var displayName: String {
        if let nickname {
            return nickname
        }
        return name
    }

    // guard let: nil なら早期リターン
    func greeting() -> String {
        guard let nickname else {
            return "Hello, \(name)!"
        }
        return "Hello, \(nickname) (\(name))!"
    }

    // ??: nil のときの既定値
    var label: String {
        nickname ?? "(no nickname)"
    }

    // オプショナルチェーン: nil なら結果も nil
    var nicknameUppercased: String? {
        nickname?.uppercased()
    }
}

型名の後ろに ? を付けた String? がオプショナル型で、「String の値がある」か「値が無い（nil）」のどちらかを表します。 オプショナルのままでは String として使えないため、次の 4 つの書き方で中身を取り出します。

  • if let nickname { … }: nil でなければ、中身を同じ名前の定数 nickname（String 型）として取り出してブロックを実行します。if let nickname = nickname の省略形で、Swift 5.7 から使えます。
  • guard let nickname else { … }: nil なら else のブロックで早期リターンします。guard の後ろでは nickname を String として使えます。
  • nickname ?? "(no nickname)": nil のときに使う既定値を指定します。
  • nickname?.uppercased(): オプショナルチェーンです。nil なら uppercased() を呼ばずに結果も nil になるため、戻り値の型は String? です。

struct Profile にはイニシャライザを書いていません。構造体は独自のイニシャライザを書いていなければ、プロパティを全て受け取るイニシャライザ（Profile(name:nickname:)）が自動で用意されます。既定値を持つプロパティは、このイニシャライザの引数を省略できます。 テストでは、このイニシャライザでニックネームがある場合と無い場合を作り分けます。ProfileTests.swift に次の内容を書きます。

Swift HandsonAppTests/ProfileTests.swift 
import Testing
@testable import HandsonApp

@MainActor
struct ProfileTests {

    @Test func displayNameUsesNicknameWhenPresent() {
        let profile = Profile(name: "Taro", nickname: "Tarou")
        #expect(profile.displayName == "Tarou")
    }

    @Test func displayNameFallsBackToName() {
        let profile = Profile(name: "Taro", nickname: nil)
        #expect(profile.displayName == "Taro")
    }

    @Test func greetingWithAndWithoutNickname() {
        #expect(Profile(name: "Taro", nickname: "T").greeting() == "Hello, T (Taro)!")
        #expect(Profile(name: "Taro", nickname: nil).greeting() == "Hello, Taro!")
    }

    @Test func labelAndOptionalChaining() {
        let none = Profile(name: "Taro", nickname: nil)
        let some = Profile(name: "Taro", nickname: "tt")
        #expect(none.label == "(no nickname)")
        #expect(none.nicknameUppercased == nil)
        #expect(some.nicknameUppercased == "TT")
    }
}
ℹ️

テストの struct に @MainActor を付ける

01 で見たとおり、アプリターゲットは SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor です。そのため、Profile を含むアプリ側の型や関数は、暗黙のうちにメインアクターへ分離されます。 一方、テストターゲットにはこの設定がありません。01 ではテスト関数に @MainActor を付けましたが、この項目ではテストの struct 全体に付けて、中のテスト関数をまとめてメインアクターで実行します。 付け忘れると、01 と同じ call to main actor-isolated … in a synchronous nonisolated context のエラーになります。

3

構造体とクラスの違いを確かめる（Counter）

Swift には、データをまとめる型として構造体（struct）とクラス（class）があります。 同じ「カウンター」を両方で作り、代入したときの振る舞いを比べます。Models フォルダに Counter.swift を作り、次の内容を書きます。

Swift HandsonApp/Models/Counter.swift 
// 値型: 代入するとコピーされる
struct Counter {
    var count = 0

    mutating func increment() {
        count += 1
    }
}

// 参照型: 代入しても同じインスタンスを指す
final class CounterBox {
    var count = 0

    func increment() {
        count += 1
    }
}
  • struct Counter: 値型です。別の変数に代入すると、値がコピーされます。
  • mutating func increment(): 構造体のメソッドが自分のプロパティを書き換えるときは mutating を付けます。そのため、let で宣言した Counter では increment() を呼べません。
  • final class CounterBox: 参照型です。代入しても、同じインスタンスを指します。クラスは let で宣言していても、中のプロパティを書き換えられます。final は継承を禁止する指定です。

HandsonAppTests フォルダに CounterTests.swift を作り、次の内容を書きます。

Swift HandsonAppTests/CounterTests.swift 
import Testing
@testable import HandsonApp

@MainActor
struct CounterTests {

    @Test func structIsCopiedOnAssignment() {
        var a = Counter()
        var b = a
        b.increment()
        a.increment()
        a.increment()
        #expect(a.count == 2)
        #expect(b.count == 1)
    }

    @Test func classIsSharedOnAssignment() {
        let a = CounterBox()
        let b = a
        b.increment()
        a.increment()
        #expect(a.count == 2)
        #expect(a === b)
    }
}

structIsCopiedOnAssignment() では、var b = a の時点で a のコピーが b に入るため、b の変更は a に影響しません。 classIsSharedOnAssignment() では、a と b が同じインスタンスを指すため、どちらから increment() しても同じ count が増えます。 === は、2 つの参照が同じインスタンスを指すかを比べる演算子で、参照型にだけ使えます。

クラスと Swift 6 の並行性チェック

CounterBox のように書き換えられる状態を持つクラスは、複数のスレッドから同時に触るとデータ競合の原因になります。 このプロジェクトではアプリターゲットの既定の分離により、CounterBox は何も書かなくてもメインアクターに分離されるため、警告やエラーは出ません。

試しに、CounterBox へ nonisolated を付けてメインアクターから外してみます。そのうえで Task.detached から触るコードを Counter.swift へ足すと、次のようにビルドエラーになります（コードと出力は抜粋）。

Swift HandsonApp/Models/Counter.swift（試す場合のみ。抜粋） 
nonisolated final class CounterBox { … }

func incrementInBackground(_ box: CounterBox) {
    Task.detached {
        box.increment()
    }
}
Terminal 
Counter.swift:20:10: error: passing closure as a 'sending' parameter risks causing data races between main actor-isolated code and concurrent execution of the closure [#RegionIsolation::SendingClosureRisksDataRace]   |             `- note: closure captures main actor-isolated 'box'** BUILD FAILED **

incrementInBackground 自体は既定どおりメインアクターに分離されるため、引数の box はメインアクター側の値として扱われます。それを別スレッドで動く Task.detached に渡そうとしたため、エラーになりました。 対処には、メインアクターに閉じる（Task { … } を使う）方法や、actor にする方法などがあります。詳しくは 06（async/await と @MainActor）で扱います。試した場合は、足したコードを削除して元に戻してください。

列挙型と switch でパターンマッチする（TodoItem）

ToDo の 1 件を表す TodoItem を、優先度と状態を表す 2 つの列挙型（enum）と一緒に作ります。 Models フォルダに TodoItem.swift を作り、次の内容を書きます。

Swift HandsonApp/Models/TodoItem.swift 
import Foundation

enum Priority: Int, CaseIterable {
    case low = 1
    case medium
    case high

    var label: String {
        switch self {
        case .low: "低"
        case .medium: "中"
        case .high: "高"
        }
    }
}

// 関連値付きの enum
enum Status {
    case todo
    case done(Date)
}

struct TodoItem {
    let title: String
    var priority: Priority = .medium
    var status: Status = .todo

    var statusText: String {
        switch status {
        case .todo:
            "未完了"
        case .done(let date):
            "完了 (\(date.formatted(.iso8601.year().month().day())))"
        }
    }
}
  • enum Priority: Int, CaseIterable: 各ケースに Int の Raw 値を持たせた列挙型です。low = 1 とすると、以降のケースは 2、3 と続きます。CaseIterable に準拠すると、全ケースの配列 Priority.allCases が使えます。
  • enum Status: case done(Date) のように、ケースごとに値を持たせられます（関連値）。「完了」のときだけ完了日時を持つ、という形を型で表せます。
  • switch: 列挙型の全てのケースを網羅する必要があります。case .done(let date) と書くと、関連値を取り出せます。
  • switch を式として使い、各 case の値をそのまま戻り値にしています。この書き方は Swift 5.9 から使えます。
  • Date.formatted(.iso8601.year().month().day()) は日付を 2026-10-03 の形式にします。Date と合わせて Foundation の import が必要です。
💡

型名を Task にしない

Task は標準ライブラリの並行処理の型 Swift.Task（01 で使った Task.detached の Task）と名前が衝突します。そのため、この教材では ToDo の型を TodoItem としています。

HandsonAppTests フォルダに TodoItemTests.swift を作り、次の内容を書きます。

Swift HandsonAppTests/TodoItemTests.swift 
import Foundation
import Testing
@testable import HandsonApp

@MainActor
struct TodoItemTests {

    @Test func priorityRawValueAndCases() {
        #expect(Priority.high.rawValue == 3)
        #expect(Priority(rawValue: 1) == .low)
        #expect(Priority(rawValue: 9) == nil)
        #expect(Priority.allCases.map(\.label) == ["低", "中", "高"])
    }

    @Test func statusTextForTodo() {
        let item = TodoItem(title: "買い物")
        #expect(item.statusText == "未完了")
    }

    @Test func statusTextForDone() {
        let date = Date(timeIntervalSince1970: 0)
        let item = TodoItem(title: "買い物", priority: .high, status: .done(date))
        #expect(item.statusText.hasPrefix("完了 ("))
    }
}

Priority(rawValue: 9) のように Raw 値から列挙型を作るイニシャライザは、該当するケースが無いと nil を返します。戻り値の型はステップ 2 で学んだオプショナル（Priority?）です。 statusTextForDone() では、日付の中身ではなく "完了 (" で始まることだけを確かめています。表示される日付はタイムゾーンによってずれるためです。

5

プロトコルと拡張で共通の振る舞いを定義する（Describable）

ここまでに作った Profile・TodoItem・Counter に、「1 行の要約を返す」という共通の振る舞いを持たせます。 Swift では、型が満たすべき要件をプロトコル（protocol）で定義します。Models フォルダに Describable.swift を作り、次の内容を書きます。

Swift HandsonApp/Models/Describable.swift 
protocol Describable {
    var summary: String { get }
}

// デフォルト実装
extension Describable {
    var summary: String { "(no summary)" }
}

extension Profile: Describable {
    var summary: String { "Profile: \(displayName)" }
}

extension TodoItem: Describable {
    var summary: String { "\(title) [\(priority.label)] \(statusText)" }
}

// 準拠するだけでデフォルト実装が使える
extension Counter: Describable {}

// ジェネリクス: 同じ型の配列
func summaries<T: Describable>(_ items: [T]) -> [String] {
    items.map(\.summary)
}

// 存在型: 異なる型を混ぜた配列
func summaries(of items: [any Describable]) -> [String] {
    items.map(\.summary)
}
  • protocol Describable: 「読み取り可能な summary プロパティを持つ」という要件を定義します。
  • extension Describable { … }: プロトコルの拡張（extension）で summary の実装を書くと、それがデフォルト実装になります。
  • extension Profile: Describable { … }: 既存の型を後から拡張して、プロトコルに準拠させます。Profile と TodoItem は独自の summary を実装しているため、デフォルト実装より優先されます。
  • extension Counter: Describable {}: 準拠を宣言するだけで、summary はデフォルト実装の "(no summary)" になります。

末尾の 2 つの関数は、どちらも Describable の配列から要約の配列を作りますが、受け取れる配列が違います。

  • summaries<T: Describable>(_ items: [T]): ジェネリクスです。T は「Describable に準拠したある 1 つの型」を表すため、[TodoItem] のように同じ型だけの配列を受け取ります。
  • summaries(of items: [any Describable]): 存在型です。any Describable は「Describable に準拠した何らかの型の値」を表すため、Profile と Counter のように異なる型を混ぜた配列を受け取れます。

.map(\.summary) は、配列の各要素の summary を取り出した新しい配列を作ります。\.summary はプロパティを指す書き方（キーパス）です。

throws と Result でエラーを扱う（Validation）

名前の入力チェックを例に、エラー処理を書きます。Models フォルダに Validation.swift を作り、次の内容を書きます。

Swift HandsonApp/Models/Validation.swift 
enum ValidationError: Error, Equatable {
    case empty
    case tooLong(max: Int)
}

func validate(name: String) throws(ValidationError) {
    if name.isEmpty {
        throw .empty
    }
    if name.count > 10 {
        throw .tooLong(max: 10)
    }
}

// throws を Result に包み直した版
func validatedName(_ name: String) -> Result<String, ValidationError> {
    do {
        try validate(name: name)
        return .success(name)
    } catch {
        return .failure(error)
    }
}
  • enum ValidationError: Error, Equatable: エラーの種類を列挙型で定義します。投げる（throw）値は Error プロトコルに準拠している必要があります。tooLong(max:) は関連値で上限の文字数を持ちます。Equatable はテストで値を比べるために付けています。
  • throws(ValidationError): 型付き throws です。この関数が投げるエラーは ValidationError だけであることを宣言します。そのため、throw .empty のように型名を省略して書けます。
  • do / try / catch: エラーを投げる関数は try を付けて呼び、catch で受け取ります。型付き throws の関数を呼んでいるため、catch のブロック内の error は ValidationError 型になります。
  • Result<String, ValidationError>: 成功（.success）か失敗（.failure）のどちらかを値として返す型です。error が ValidationError 型なので、.failure(error) にそのまま包めます。
ℹ️

通常の throws にした場合

型を書かない通常の throws にすると、throw .empty が type 'any Error' has no member 'empty' でビルドに失敗します。throw ValidationError.empty に直しても、catch の error は any Error 型になります。そのため、.failure(error) の行が次のエラーでビルドに失敗します。

cannot convert value of type 'any Error' to expected argument type 'ValidationError'

型付き throws なら catch の error が ValidationError に確定するので、.failure(error) をそのまま書けます。

HandsonAppTests フォルダに ValidationTests.swift を作り、次の内容を書きます。

Swift HandsonAppTests/ValidationTests.swift 
import Testing
@testable import HandsonApp

@MainActor
struct ValidationTests {

    @Test func validNameDoesNotThrow() throws {
        try validate(name: "Taro")
    }

    @Test func emptyNameThrows() {
        #expect(throws: ValidationError.self) {
            try validate(name: "")
        }
    }

    @Test func tooLongNameThrowsWithAssociatedValue() {
        #expect(throws: ValidationError.tooLong(max: 10)) {
            try validate(name: "12345678901")
        }
    }

    @Test func resultVersion() {
        #expect(validatedName("Taro") == .success("Taro"))
        #expect(validatedName("") == .failure(.empty))
    }
}
  • validNameDoesNotThrow(): テスト関数自体に throws を付けると、中で try した関数がエラーを投げたときにテストが失敗になります。
  • #expect(throws: ValidationError.self) { … }: クロージャの中で ValidationError 型のエラーが投げられることを確かめます（エラーの型だけを確認）。
  • #expect(throws: ValidationError.tooLong(max: 10)) { … }: 投げられたエラーの値まで一致することを確かめます。値を比べるため、ValidationError に Equatable を付けています。

#expect(throws:) は投げられたエラーを ValidationError? として返します。let error = #expect(throws: ValidationError.self) { … } のように受け取れば、エラーの中身を確認できます。

演習

以下のチェックリストを使って、このレッスンの内容を振り返りましょう。

つまずきポイント

💡

call to main actor-isolated … in a synchronous nonisolated context が出る

テストの struct に @MainActor を付け忘れています。アプリ側の型は既定でメインアクターに分離されるため、テスト側もメインアクターで実行する必要があります。ステップ 2 の ProfileTests のように、struct の直前に @MainActor を付けてください。

💡

let で宣言した構造体のメソッドが呼べない

自分のプロパティを書き換えるメソッドには mutating が付いており、let で宣言した構造体からは呼べません。ステップ 3 の var a = Counter() のように var で宣言してください。クラスの場合は let でも中身を変更できます。

💡

クラッシュするテストを流したら、しばらく終わらない

強制アンラップなどでテストのプロセスが落ちると、再起動して残りのテストを流すため、終了まで 1 分ほどかかります。固まったわけではないので、** TEST FAILED ** が出るまで待ってください。
