TestFlight で配布

  • ⏱ 所要時間: 60分（Apple 側の処理待ちの時間を除く）
  • 📊 難易度: 中級
  • 👤 対象: 11 までで ToDo アプリを作り終え、自分の iPhone や知人の端末にベータ版として配りたい人
  • 📋 前提: 11 で Charts と地図を加えた HandsonApp プロジェクトが手元にあること。ステップ 1 のチーム設定とステップ 4 の後半以降には、有料の Apple Developer Program への加入が必要です（未加入でも、ステップ 4 の署名なしアーカイブまでは進められます）
  • 🔗 前提となる項目: 11 Charts と MapKit

🎯 このレッスンで学ぶこと

  • 配布の前に、Bundle ID・App Group・チームを自分のものにそろえる
  • バージョン（MARKETING_VERSION）とビルド番号（CURRENT_PROJECT_VERSION）を整え、agvtool でビルド番号を上げる
  • アプリアイコンと輸出コンプライアンスのキー ITSAppUsesNonExemptEncryption を設定する
  • xcodebuild archive でアーカイブを作り、中身と署名の有無を確かめる
  • App Store Connect にアプリを登録し、Xcode Organizer からアップロードする流れを知る
  • テスターを招待し、TestFlight アプリでのインストールとフィードバックの流れを知る

概要

11 までで作った ToDo アプリを、TestFlight でベータ配布します。TestFlight は、App Store に公開する前のビルドをテスターに配る Apple の仕組みです。 テスターは TestFlight アプリからベータ版をインストールし、スクリーンショット付きのフィードバックを送れます。

この項目は、性質の違う 2 つのパートでできています。

  • 実測パート（ステップ 1〜4 と 7 のコマンド）: これまでの項目と同じく、手元の Mac で実行したコマンドと実際の出力、ファイルの変更をそのまま載せています。
  • 手順解説パート（ステップ 5・6 と、ステップ 7 の再アップロード）: App Store Connect へのアプリ登録、アップロード、テスターの招待、TestFlight アプリでの操作です。
⚠️

手順解説パートについて

手順解説パートは、2026年10月時点の Apple の公式ヘルプに基づく手順です。執筆時には、実際のアップロードは行っていません（Apple Developer Program のアカウントに変更を加えないため）。 画面の文言は、公式ヘルプで確認できた英語表記のまま書いています。各手順には、公式ドキュメントへのリンクを付けています。画面の配置や文言が変わっている場合は、リンク先の最新の記載を優先してください。

ℹ️

Apple Developer Program が必要

App Store Connect と TestFlight は、有料の Apple Developer Program の会員向けの機能です。年会費は 99 USD で、加入手続きの中では現地通貨で表示されます。 加入していない Apple Account は、Xcode では「Personal Team」と表示されます。Personal Team では App Store Connect と TestFlight を使えません（Choosing a Membership、Enrollment）。

未加入の場合は、ステップ 1 の Bundle ID の変更と、ステップ 2・3、ステップ 4 の署名なしアーカイブと、ステップ 7 の agvtool までを進めてください。ステップ 1 のチーム設定、ステップ 4 の署名ありアーカイブ以降は、加入後に行います。

ℹ️

使用バージョン

Xcode 27.0 / Swift 6.4（Swift 6 言語モード）/ 最小対象 iOS 18.0 / シミュレータ iPhone 17（iOS 27.0）は 11 と同じです。バージョンは執筆時点（2026年10月）のものです。

2026年4月28日以降、App Store Connect にアップロードするアプリは Xcode 26 以降と iOS 26 SDK でビルドする必要があります。2026年9月9日以降は、iOS 13 以上を対象にする必要があります（Upcoming requirements）。Xcode 27 で最小対象 iOS 18 のこのアプリは、どちらも満たします。

準備

11 の完成コードをそのまま出発点にします。11-charts-mapkit がある場所で次のコマンドを実行し、ディレクトリごと 12-testflight にコピーします。

Terminal 
$ cp -R 11-charts-mapkit 12-testflight$ cd 12-testflight/HandsonApp$ export DD=/tmp/handson-ios-dd

以降のコマンドは全て、HandsonApp.xcodeproj があるこのフォルダで実行します。Xcode の場合は、12-testflight/HandsonApp/HandsonApp.xcodeproj を開きます。

手順

1

配布前の点検と、Bundle ID・App Group・チームの変更

まず、配布に関わるビルド設定を確かめます。xcodebuild -showBuildSettings は、ビルドせずに設定値だけを表示します。Release 構成のアプリターゲットの値を見ます。

Terminal 
$ xcodebuild -showBuildSettings -project HandsonApp.xcodeproj -target HandsonApp -configuration Release 2>/dev/null | grep -E ' (ASSETCATALOG_COMPILER_APPICON_NAME|CODE_SIGN_ENTITLEMENTS|CODE_SIGN_IDENTITY|CODE_SIGN_STYLE|CURRENT_PROJECT_VERSION|DEVELOPMENT_TEAM|IPHONEOS_DEPLOYMENT_TARGET|MARKETING_VERSION|PRODUCT_BUNDLE_IDENTIFIER|PRODUCT_NAME) = '    ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon    CODE_SIGN_ENTITLEMENTS = HandsonApp/HandsonApp.entitlements    CODE_SIGN_IDENTITY = Apple Development    CODE_SIGN_STYLE = Automatic    CURRENT_PROJECT_VERSION = 1    IPHONEOS_DEPLOYMENT_TARGET = 18.0    MARKETING_VERSION = 1.0    PRODUCT_BUNDLE_IDENTIFIER = com.example.HandsonApp    PRODUCT_NAME = HandsonApp

読み取れることは次のとおりです。

  • CODE_SIGN_STYLE = Automatic: 自動署名です。チームを設定すれば、必要な証明書やプロビジョニングプロファイルを Xcode が用意します。
  • DEVELOPMENT_TEAM は出力に出ません。チームがまだ設定されていません。
  • PRODUCT_BUNDLE_IDENTIFIER は com.example.HandsonApp です。ウィジェットの拡張（TodoWidgetExtension）は com.example.HandsonApp.TodoWidget です。
  • アプリと拡張の entitlements には、App Group group.com.example.HandsonApp が 1 つだけ入っています。
  • ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon ですが、AppIcon.appiconset には画像がまだありません（ステップ 3 で用意します）。

Bundle ID は全ての開発者の間で一意でなければなりません。com.example のままでは、自分のアカウントで登録できません。 Apple は、組織 ID（逆ドメイン）に自分のドメインを使うことを推奨しています（Preparing your app for distribution）。 ここでは com.example を com.yourname に置き換える例で示します。yourname の部分は、自分のドメインや名前に合わせて読み替えてください。

変える値は 3 種類で、アプリと拡張の両方をそろえます。

  • アプリの Bundle ID: com.yourname.HandsonApp
  • 拡張の Bundle ID: com.yourname.HandsonApp.TodoWidget
  • App Group: group.com.yourname.HandsonApp（App Group の ID は group. で始めます。Configuring app groups）

Bundle ID は Xcode で変えます。プロジェクトを選び、ターゲット HandsonApp と TodoWidgetExtension それぞれの Signing & Capabilities を開きます。そこにある Bundle Identifier 欄を書き換えます。 変更は project.pbxproj の Debug と Release の両方に入ります。

diff HandsonApp.xcodeproj/project.pbxproj（アプリ。Debug と Release の 2 か所） 
  				MARKETING_VERSION = 1.0;- 				PRODUCT_BUNDLE_IDENTIFIER = com.example.HandsonApp;+ 				PRODUCT_BUNDLE_IDENTIFIER = com.yourname.HandsonApp;  				PRODUCT_NAME = "$(TARGET_NAME)";
diff HandsonApp.xcodeproj/project.pbxproj（拡張。Debug と Release の 2 か所） 
  				MARKETING_VERSION = 1.0;- 				PRODUCT_BUNDLE_IDENTIFIER = com.example.HandsonApp.TodoWidget;+ 				PRODUCT_BUNDLE_IDENTIFIER = com.yourname.HandsonApp.TodoWidget;  				PRODUCT_NAME = "$(TARGET_NAME)";

App Group の ID は、アプリと拡張の entitlements と、10 で作った SharedStore の 3 か所に書かれています。3 か所とも同じ値に変えます。

diff HandsonApp/HandsonApp.entitlements と TodoWidgetExtension.entitlements（同じ変更） 
  	<key>com.apple.security.application-groups</key>  	<array>- 		<string>group.com.example.HandsonApp</string>+ 		<string>group.com.yourname.HandsonApp</string>  	</array>
diff HandsonApp/Shared/SharedStore.swift 
  nonisolated enum SharedStore {-     static let appGroupID = "group.com.example.HandsonApp"+     static let appGroupID = "group.com.yourname.HandsonApp"

最後に、Signing & Capabilities の Team で、Apple Developer Program に加入したチームを選びます。TestFlight で配布する場合は、全てのターゲットを加入済みのチームに割り当てます（Preparing your app for distribution）。 アップロードやエクスポートのときに、Xcode がそのアカウントに必要な署名用の資産を作ります。App ID や App Group を Web の Certificates, Identifiers & Profiles で手作業で登録する必要はありません。

加入済みの場合は、チームを選んだ後に、各ターゲットの App Groups 欄の (+) で group.com.yourname.HandsonApp を追加します。古い group.com.example.HandsonApp のチェックは外します。Xcode がアカウントに App Group を登録し、entitlements は上の diff と同じ内容になります（Configuring app groups）。 未加入の場合は、entitlements を直接書き換えれば、シミュレータで動きます。

⚠️

Bundle ID は最初のアップロード後に変えられない

最初のビルドをアップロードした後は、そのアプリの Bundle ID を変更できません（Preparing your app for distribution、App information）。この値を最後まで使います。

ℹ️

完成コードの Bundle ID とチーム

ブランチ ios/12-testflight の完成コードは、Bundle ID と App Group を com.example.* のまま残しています。チームも設定していません（DEVELOPMENT_TEAM は project.pbxproj にありません）。完成コードを使う場合も、このステップの変更を自分で行ってください。

✅ 確認ポイント

grep -rn "com.example" . を実行します。project.pbxproj のアプリと拡張の 4 行、entitlements の 2 ファイル、SharedStore.swift に、com.example が残っていないことを確かめます。 テストターゲット（com.example.HandsonAppTests など）は配布しないので、残っていても構いません。

2

バージョンとビルド番号を整える

アプリには 2 つの番号があります。どちらも project.pbxproj のビルド設定から、ビルド時に Info.plist へ書き込まれます。

  • バージョン（MARKETING_VERSION → CFBundleShortVersionString）: ユーザーに見せる番号です。
  • ビルド番号（CURRENT_PROJECT_VERSION → CFBundleVersion）: 同じバージョンの中でビルドを区別する番号です。

App Store Connect は、Bundle ID・バージョン・ビルド番号の組でビルドを識別します（App information、CFBundleVersion）。 ビルド番号は、数字とピリオドだけでできた、ピリオド区切りの 1〜3 個の整数です。

このステップでは、バージョンを 1.0 から 1.0.0 にします。ビルド番号は 1 のままにします。 MARKETING_VERSION は、アプリ・拡張・2 つのテストターゲットの Debug と Release で 8 か所あります。sed でまとめて書き換えます（出力はありません）。

Terminal 
$ sed -i '' 's/MARKETING_VERSION = 1.0;/MARKETING_VERSION = 1.0.0;/' HandsonApp.xcodeproj/project.pbxproj$ grep -c "MARKETING_VERSION = 1.0.0;" HandsonApp.xcodeproj/project.pbxproj8
diff HandsonApp.xcodeproj/project.pbxproj（8 か所とも同じ変更） 
- 				MARKETING_VERSION = 1.0;+ 				MARKETING_VERSION = 1.0.0;

Xcode で変える場合は、ターゲットの General にある Version 欄を使います。アプリと拡張のバージョンは同じ値にそろえておきます。

ビルド番号を上げるには、Xcode に付属する agvtool が使えます。ビルド番号を上げて再配布するときに使うので、ステップ 7 で実行します。

✅ 確認ポイント

grep -c が 8 を返すことを確かめます。ビルドすると、アプリと拡張の Info.plist は、どちらも CFBundleShortVersionString が "1.0.0" になります。CFBundleVersion は "1" です（ステップ 4 のアーカイブで確かめます）。

3

アプリアイコンと輸出コンプライアンスのキーを設定する

11 までのプロジェクトの AppIcon.appiconset には、画像がありません。1024×1024 の枠（universal・dark・tinted）が並んでいるだけです。 ここでは、1024×1024 でアルファチャンネルのない PNG を 1 枚用意し、universal の枠に入れます。

自分で用意した画像を使う場合は、1024×1024・アルファなしの PNG を用意します。HandsonApp/Assets.xcassets/AppIcon.appiconset/AppIcon.png として置き、下の sips から続けます。 画像が手元にない場合は、次のスクリプトで青地に白いチェックマークのアイコンを生成できます。リポジトリの外（ここでは /tmp/make-icon.swift）に保存します。

Swift /tmp/make-icon.swift 
import CoreGraphics
import ImageIO
import UniformTypeIdentifiers
import Foundation

let size = 1024
let cs = CGColorSpaceCreateDeviceRGB()
// alpha なし（noneSkipLast）で描画する
let ctx = CGContext(data: nil, width: size, height: size, bitsPerComponent: 8, bytesPerRow: 0,
                    space: cs, bitmapInfo: CGImageAlphaInfo.noneSkipLast.rawValue)!
ctx.setFillColor(CGColor(red: 0.12, green: 0.45, blue: 0.95, alpha: 1))
ctx.fill(CGRect(x: 0, y: 0, width: size, height: size))
// 白いチェックマーク
ctx.setStrokeColor(CGColor(red: 1, green: 1, blue: 1, alpha: 1))
ctx.setLineWidth(120)
ctx.setLineCap(.round)
ctx.setLineJoin(.round)
ctx.move(to: CGPoint(x: 290, y: 520))
ctx.addLine(to: CGPoint(x: 450, y: 360))
ctx.addLine(to: CGPoint(x: 740, y: 680))
ctx.strokePath()
let image = ctx.makeImage()!
let url = URL(fileURLWithPath: CommandLine.arguments[1]) as CFURL
let dest = CGImageDestinationCreateWithURL(url, UTType.png.identifier as CFString, 1, nil)!
CGImageDestinationAddImage(dest, image, nil)
CGImageDestinationFinalize(dest)

CGContext を CGImageAlphaInfo.noneSkipLast で作るのがポイントです。透明度の情報を持たない画像になります。スクリプトを実行し、sips でサイズとアルファの有無を確かめます。

Terminal 
$ swift /tmp/make-icon.swift HandsonApp/Assets.xcassets/AppIcon.appiconset/AppIcon.png$ sips -g pixelWidth -g pixelHeight -g hasAlpha HandsonApp/Assets.xcassets/AppIcon.appiconset/AppIcon.png…  pixelWidth: 1024  pixelHeight: 1024  hasAlpha: no

続けて Contents.json を書き換えます。dark と tinted の枠は削除し、universal の 1 枠に "filename" を足します。

diff HandsonApp/Assets.xcassets/AppIcon.appiconset/Contents.json 
  {    "images" : [      {+       "filename" : "AppIcon.png",        "idiom" : "universal",        "platform" : "ios",        "size" : "1024x1024"-     },-     {-       "appearances" : [-         {-           "appearance" : "luminosity",-           "value" : "dark"-         }-       ],-       "idiom" : "universal",-       "platform" : "ios",-       "size" : "1024x1024"-     },-     {-       "appearances" : [-         {-           "appearance" : "luminosity",-           "value" : "tinted"-         }-       ],-       "idiom" : "universal",-       "platform" : "ios",-       "size" : "1024x1024"      }    ],    "info" : {      "author" : "xcode",      "version" : 1    }  }

次は輸出コンプライアンスです。暗号化を使うアプリは、米国の輸出規制に関する申告が必要です。 アップロードしたビルドは、申告が済むまで Missing Compliance の状態になり、テスターに配れません（App build statuses）。 Info.plist の ITSAppUsesNonExemptEncryption を NO にすると、「暗号化を使っていない、または免除対象の暗号化だけを使っている」と申告できます。このキーがない場合、新しいバージョンをアップロードするたびに質問への回答が必要です（ITSAppUsesNonExemptEncryption）。

このプロジェクトは Info.plist をビルド設定から生成しています（GENERATE_INFOPLIST_FILE = YES）。そこで、アプリターゲットの Debug と Release の両方に INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO; を足します。 Xcode では、ターゲット HandsonApp の Info タブにキーを追加しても同じです。

diff HandsonApp.xcodeproj/project.pbxproj（アプリの Debug と Release の 2 か所） 
  				GENERATE_INFOPLIST_FILE = YES;+ 				INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO;  				INFOPLIST_KEY_UIApplicationSceneManifest_Generation = YES;
⚠️

NO にしてよいかは自分で判断する

HandsonApp の通信は、07 で使った URLSession の HTTPS だけです。OS に組み込まれた暗号化は、通常は書類提出の対象外です（Complying with Encryption Export Regulations）。 ただし、規制の解釈を誤った場合の責任は開発者にあると、Apple は明記しています（Overview of export compliance）。独自の暗号化を加えたアプリでは、NO にしないでください。

ここまでの変更（バージョン・アイコン・ITSAppUsesNonExemptEncryption）で、既存のテストが通ることを確かめます。

Terminal

✅ 確認ポイント

  • sips の出力が pixelWidth: 1024・pixelHeight: 1024・hasAlpha: no であること。
  • シミュレータにインストールすると、ホーム画面に青地に白いチェックのアイコンが「HandsonApp」の名前で表示されること。
  • ユニットテストが 24 スイート 82 件で通ること（1 件の known issue は、09 で作った既知の問題のデモで、意図どおりです）。UI テストは Executed 3 tests, with 0 failures です。
4

アーカイブを作り、中身と署名を確かめる

配布するビルドは、アーカイブ（.xcarchive）として作ります。アーカイブには、Release 構成でビルドしたアプリと、クラッシュログの解析に使うシンボル（dSYM）が入ります。 まず、署名を無効にしてアーカイブを作り、中身を確かめます。署名なしなら、Apple Developer Program に加入していなくても実行できます。

Terminal 
$ xcodebuild archive -project HandsonApp.xcodeproj -scheme HandsonApp -destination 'generic/platform=iOS' -archivePath HandsonApp.xcarchive -derivedDataPath $DD CODE_SIGNING_ALLOWED=NO…** ARCHIVE SUCCEEDED **

-destination 'generic/platform=iOS' は「実機向け（特定の端末を指定しない）」という意味です。CODE_SIGNING_ALLOWED=NO で署名を省きます。 できたアーカイブの中身は、次のとおりです（抜粋）。

Text HandsonApp.xcarchive/（抜粋） 
HandsonApp.xcarchive/
  Info.plist
  dSYMs/HandsonApp.app.dSYM
  dSYMs/TodoWidgetExtension.appex.dSYM
  Products/Applications/HandsonApp.app/
    HandsonApp  Info.plist  Assets.car  AppIcon60x60@2x.png  AppIcon76x76@2x~ipad.png
    PkgInfo  Metadata.appintents/  PlugIns/TodoWidgetExtension.appex
  • ウィジェットの拡張（TodoWidgetExtension.appex）は、アプリの PlugIns/ に入っています。アプリと拡張は 1 つのアーカイブで一緒に配布されます。
  • 1024×1024 の 1 枚から、端末ごとのサイズのアイコン（AppIcon60x60@2x.png など）が生成されています。
  • 10 で作ったショートカットの情報は Metadata.appintents/ に入っています。

アーカイブ自体の Info.plist を見ます。

Terminal 
$ plutil -p HandsonApp.xcarchive/Info.plist…"ApplicationProperties" => {  "ApplicationPath" => "Applications/HandsonApp.app"  "Architectures" => [    0 => "arm64"  ]  "CFBundleIdentifier" => "com.example.HandsonApp"  "CFBundleShortVersionString" => "1.0.0"  "CFBundleVersion" => "1"  "SigningIdentity" => ""  "Team" => ""}"ArchiveVersion" => 2…"Name" => "HandsonApp""SchemeName" => "HandsonApp"…

バージョンは 1.0.0、ビルド番号は 1 です。SigningIdentity と Team が空なのが、署名なしの印です。 この出力は、Bundle ID を com.example のまま実行したときのものです。ステップ 1 で変えた場合は、CFBundleIdentifier に自分の Bundle ID が出ます。 アプリの Info.plist は Products/Applications/HandsonApp.app/Info.plist です。ここには、ステップ 3 で設定した "ITSAppUsesNonExemptEncryption" => false と、CFBundleIconName（値は AppIcon）が入っています。

署名なしのアーカイブは、App Store Connect に送れません。配布には、チームの署名入りのアーカイブを使います。 たとえば、チーム ID だけをコマンドラインで渡し、Bundle ID は com.example のまま実行すると、次のように失敗します（チーム ID は伏せています）。

Terminal

(in target 'TodoWidgetExtension' from project 'HandsonApp')** ARCHIVE FAILED **

アプリと拡張のそれぞれの Bundle ID で、プロビジョニングプロファイルが求められています。このアカウントには、com.example.* の App ID とプロファイルがありません。 さらに、コマンドラインの xcodebuild は、-allowProvisioningUpdates を付けない限りプロファイルを自動で作りません。 xcodebuild -help には、このオプションについて「自動署名のターゲットでは、プロファイル・App ID・証明書を作成・更新する」と書かれています。

配布用のアーカイブは、ステップ 1 で自分の Bundle ID とチームを設定したうえで、Xcode で作るのが簡単です。 Scheme ツールバーで実行先を選び、メニューの Product > Archive を選びます。成功したアーカイブは Archives organizer に表示されます。Window > Organizer でも開けます（Distributing your app for beta testing and releases）。

Xcode 15 以降は、実行先がシミュレータのままでも、そのデバイスの種類に必要な全アーキテクチャを含めてアーカイブできます。

コマンドラインで署名ありのアーカイブを作る場合は、自分の Bundle ID とチームを設定したうえで -allowProvisioningUpdates を付けます。成功すると、署名なしのときと同じく ** ARCHIVE SUCCEEDED ** と表示されます。 -allowProvisioningUpdates を付けると、xcodebuild がアカウントに App ID・プロファイル・証明書を作成・更新します（xcodebuild -help）。執筆時はアカウントを変更しないため実行していません。

✅ 確認ポイント

  • 署名なしのアーカイブで ** ARCHIVE SUCCEEDED ** が表示され、Info.plist の CFBundleShortVersionString が "1.0.0"、CFBundleVersion が "1" であること。
  • （加入済みの場合）Xcode の Product > Archive で作ったアーカイブが Archives organizer に表示されること。
5

App Store Connect にアプリを登録してアップロードする

ℹ️

ここからは手順解説パート

このステップは、2026年10月時点の Apple の公式ヘルプに基づく手順です。執筆時に実際のアップロードは行っていません。画面の文言は公式ヘルプの英語表記です。App Store Connect を日本語で表示している場合は、対応する日本語の項目を探してください。

1. アプリを登録する（Add a new app）。 App Store Connect の Apps で左上の (+) を押し、New App を選びます。

⚠️

作ると元に戻しにくい値がある

SKU は作成後に変更できません。アプリを削除すると、アプリ名の権利を失います。また、SKU は同じ組織で再利用できません。ビルドをアップロード済みなら、Bundle ID も再利用できません（Remove an app）。練習用でも、値は慎重に決めてください。

ダイアログでは、次の項目を入力します。

  • Platforms: iOS を選びます。
  • Name: App Store に表示される名前です（2〜30 文字）。他の開発者が使っている名前は使えません。
  • Primary Language: 主な言語です。
  • Bundle ID: ステップ 1 で決めたアプリの Bundle ID を選びます。Xcode のプロジェクトと一致させます。
  • SKU: 社内管理用の ID で、利用者には見えません。英数字・ハイフン・ピリオド・アンダースコアが使えます。先頭に記号は置けません。
  • User Access: Limited Access か Full Access を選びます。

Create を押すと、ステータスが Prepare for Submission のアプリができます。 新しいアプリを追加するには、Account Holder が Business セクションで最新の契約に同意している必要があります。 未登録のまま初めてアップロードすると、登録に必要な情報を Xcode が尋ねます（Distributing your app for beta testing and releases）。

2. Organizer からアップロードする（Distributing your app for beta testing and releases）。 Organizer のサイドバーで Archives を選び、ステップ 4 のアーカイブを選んで Distribute App を押します。推奨設定の選択肢が並ぶので、次のどちらかを選びます。

  • TestFlight & App Store: TestFlight で配布し、App Store にも提出できる既定の設定です。
  • TestFlight Internal Only: TestFlight で配布し、チーム内だけに限定する既定の設定です。このビルドは App Store に提出できません。

練習なら TestFlight Internal Only が安全です。TestFlight & App Store は、ビルド番号の更新・自動署名・シンボル付きのアップロードを行う設定です。どちらの推奨設定でも、ビルド番号は Xcode が更新します（Preparing your app for distribution）。 Distribute を押すと、Xcode が処理・パッケージ化・アップロードを進めます。最後に、App Store Connect のビルドのページへのリンクが表示されます。 提出せずに簡易な自動検証だけを行いたい場合は、Validate App を使います。

3. 処理を待ち、輸出コンプライアンスを確かめる（Upload builds、Build upload statuses）。 アップロードしたビルドは、Apple 側の処理を経てから App Store Connect に表示されます。処理が終わるとメールが届きます。 アップロードのステータスは Processing から Complete か Failed に変わります。Processing のまま 24 時間を超えたら、問題が起きている可能性があります。Failed になった場合は、次のアップロードで同じビルド番号を使えます。

ステップ 3 で ITSAppUsesNonExemptEncryption を設定していない場合、ビルドは Missing Compliance になります。 その場合は、TestFlight タブでビルドを開き、Manage を押します。Provide Export Compliance Information で質問に答えます。手順は Provide export compliance information for beta builds にあります。

コマンドラインでエクスポート・アップロードする場合

Organizer の代わりに、xcodebuild -exportArchive でアーカイブを書き出せます。設定は ExportOptions.plist に書きます。次の内容は、App Store Connect 向けの形式で手元に書き出す設定です。リポジトリの外に保存します。

XML ExportOptions.plist 
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
	<key>method</key>
	<string>app-store-connect</string>
	<key>destination</key>
	<string>export</string>
</dict>
</plist>

xcodebuild -help（Xcode 27.0）には、主なキーが次のように説明されています。

  • method: 書き出し方です。app-store-connect・release-testing・enterprise・debugging・developer-id・mac-application・validation から選びます。旧名の app-store・ad-hoc・development は非推奨です。
  • destination: export（手元に書き出す）か upload（Apple にアップロードする）です。既定は export です。
  • manageAppVersionAndBuildNumber: アップロード時に Xcode がビルド番号を管理するかどうかです。既定は YES です。
  • testFlightInternalTestingOnly: 有効にすると、外部の TestFlight や App Store では配布できないビルドになります。
  • teamID: 書き出しに使うチームです。既定は、アーカイブをビルドしたチームです。

ステップ 4 の署名なしアーカイブに対して実行すると、チームがないため失敗します。

Terminal 
$ xcodebuild -exportArchive -archivePath HandsonApp.xcarchive -exportPath export -exportOptionsPlist ExportOptions.plist…error: exportArchive No Team Found in Archive  Use the Signing & Capabilities editor to assign a team to the targets and build a new archive.** EXPORT FAILED **

署名ありのアーカイブなら、export/ に書き出されます。destination を upload にすると、書き出す代わりに App Store Connect へ直接アップロードします。 Xcode の Accounts 設定に追加したアカウントで通信させるには -allowProvisioningUpdates を付けます。API キーを使う場合は -authenticationKeyPath・-authenticationKeyID・-authenticationKeyIssuerID を指定します。

署名ありアーカイブでの書き出しと upload は、アカウントに送信するため執筆時には実行していません（出力は載せていません）。

✅ 確認ポイント

App Store Connect でアプリの TestFlight タブを開き、アップロードしたビルド（バージョン 1.0.0）が表示されることを確かめます。処理が終わると、ビルドのステータスが Missing Compliance ではなく、Ready to Test などの状態で表示されます（App build statuses）。 Missing Compliance と出ている場合は、ステップ 3 の設定を見直します。

6

テスターを招待し、TestFlight アプリでフィードバックを送る

ℹ️

手順解説パート

このステップも、2026年10月時点の Apple の公式ヘルプに基づく手順です。執筆時に実際の配布は行っていません。

TestFlight のテスターには、内部テスターと外部テスターの 2 種類があります。

内部テスター外部テスター
対象自分のチームの App Store Connect ユーザーApp Store Connect ユーザーでない人（メールまたは公開リンクで招待）
人数の上限100 人アプリごとに 10,000 人
審査不要最初のビルドは TestFlight App Review が必要
出典Add internal testersInvite external testers

1. 内部テスターに配る（Add internal testers）。 TestFlight タブのサイドバーにある Internal Testing の (+) で、グループ名を入れて Create を押します。 Enable automatic distribution をオンにすると、Xcode からアップロードしたビルドが自動でこのグループに配られます。オフの場合は Add Builds で手動で追加します。 Invite Testers でテスターを選んで Add を押します。ビルドを追加するときに、テスターに試してほしいことを What to Test に書きます。 個人で加入した場合は自分が Account Holder なので、自分自身を内部テスターにできます。

2. TestFlight アプリでインストールする（TestFlight）。 テスターは、iPhone に App Store から TestFlight アプリをインストールします。招待メールの View in TestFlight（TestFlightで表示）か公開リンクをタップし、Accept（承諾）→ Install（インストール）をタップします。 1 人のテスターは、最大 30 台の端末にベータ版をインストールできます。

3. フィードバックを送る・受け取る。 テスターは、ベータ版のアプリでスクリーンショットを撮り、サムネイルをタップして書き込みを加えます。Done（完了）→ Share Beta Feedback（ベータ版フィードバックを共有）を選ぶと送信できます。アプリがクラッシュしたときは、詳細を送るかどうかを尋ねるアラートが出ます。 開発者は、受け取った内容を App Store Connect で見ます。TestFlight タブの Feedback にある Screenshots と Crashes です（View tester feedback）。 Xcode の Window > Organizer の Feedback でも見られます（Viewing and responding to feedback）。

外部テスターに配る場合

外部グループを作るには、先に内部グループが必要です。External Testing の (+) でグループを作り、Add Builds でビルドを追加して What to Test を書きます。最後に Submit Review を押して TestFlight App Review に提出します（Invite external testers）。

  • 最初のビルドは、全項目の審査を受けます。同じバージョンの後続のビルドは、審査が要らない場合があります。
  • 1 つのバージョンで同時に審査を受けられるのは 1 ビルドだけです。24 時間で提出できるのは 6 ビルドまでです。
  • 外部テストでは、テスト情報（Beta App Description など）が必須です。TestFlight タブの Test Information で入力します（Provide test information）。
  • メールの代わりに、Testers タブの Create Public Link で公開リンクを作れます。参加人数の上限（1〜10,000）も設定できます。
ℹ️

ビルドは 90 日で期限切れになる

TestFlight のビルドは、アップロードから最大 90 日間テストできます。期限を過ぎると、ステータスが Expired になり、テスターは使えなくなります（TestFlight overview）。 期限より前にテストを止めたい場合は、ビルドを開いて Expire Build を押します（Stop testing a build）。

✅ 確認ポイント

  • テスターの端末の TestFlight アプリに HandsonApp が表示され、インストールしたアプリが起動すること。
  • App Store Connect で、ビルドのステータスが Ready to Test や Testing になっていること（App build statuses）。
  • テスターが送ったスクリーンショットが、Feedback の Screenshots に表示されること。
7

（任意）ビルド番号を上げて再配布する

ToDo アプリを直したら、新しいビルドをアップロードしてテスターに届けます。同じバージョンのまま、ビルド番号だけを上げれば、同じバージョンの下にビルドが増えていきます。 iOS アプリの場合、新しいバージョンではビルド番号を 1 から振り直しても構いません（Preparing your app for distribution）。

agvtool new-version -all で、全ターゲットのビルド番号をまとめて変えられます。HandsonApp.xcodeproj があるフォルダで実行します。

Terminal 
$ agvtool new-version -all 2Setting version of project HandsonApp to:     2.Also setting CFBundleVersion key (assuming it exists)Updating CFBundleVersion in Info.plist(s)...Updated CFBundleVersion in "HandsonApp.xcodeproj/../TodoWidget/Info.plist" to 2Cannot find "HandsonApp.xcodeproj/../YES"

project.pbxproj の CURRENT_PROJECT_VERSION は、8 か所全てが 2 になります。 Updated … TodoWidget/Info.plist と表示されますが、実際には変わりません。このファイルには CFBundleVersion キーがないためです（git diff にも出ません）。

最後の Cannot find "HandsonApp.xcodeproj/../YES" は警告です。agvtool が GENERATE_INFOPLIST_FILE = YES の値 YES を Info.plist のパスとして読んだために出ます（この行を除くと出ないことを確かめました）。ビルド番号の変更には影響しません。

diff HandsonApp.xcodeproj/project.pbxproj（8 か所とも同じ変更） 
- 				CURRENT_PROJECT_VERSION = 1;+ 				CURRENT_PROJECT_VERSION = 2;

ビルド番号を変えたら、ステップ 4・5 と同じようにアーカイブしてアップロードします（ここからは手順解説パートです）。 ただし、Organizer の推奨設定（ステップ 5）でアップロードすると、Xcode がアップロード時にビルド番号を更新します。 Custom で Manage version and build number をオフにしたら、事前に自分で上げます（Preparing your app for distribution）。 内部グループで Enable automatic distribution をオンにしていれば、新しいビルドは自動でテスターに配られます。

💡

agvtool の変更は git diff で確かめる

agvtool は project.pbxproj を直接書き換えます。実行後は git diff で、意図した行だけが変わったことを確かめてください。 完成コード（ブランチ ios/12-testflight）は、ビルド番号を 1 に戻した状態（1.0.0 (1)）です。

✅ 確認ポイント

grep -c "CURRENT_PROJECT_VERSION = 2;" HandsonApp.xcodeproj/project.pbxproj が 8 を返すことを確かめます。アップロードした場合は、App Store Connect の TestFlight タブで、バージョン 1.0.0 の下にビルド 2 が加わります。

作業が終わったら、アーカイブと書き出しのフォルダを消しておきます。どちらもビルドの成果物なので、リポジトリには含めません。

Terminal 
$ rm -rf HandsonApp.xcarchive export

解答例を見る

つまずきポイント

💡

「No profiles for 'com.example.HandsonApp' were found」と出る

Bundle ID が com.example のままか、コマンドラインで -allowProvisioningUpdates を付けずにアーカイブしています。ステップ 1 で Bundle ID とチームを自分のものに変え、Xcode の Product > Archive でアーカイブします。 エラーはアプリと拡張の Bundle ID ごとに出ます。拡張の Bundle ID も変えたか確かめてください。

💡

「No Team Found in Archive」と出る

署名なし（CODE_SIGNING_ALLOWED=NO）で作ったアーカイブは書き出せません。メッセージのとおり、Signing & Capabilities でターゲットにチームを割り当て、アーカイブを作り直します。

💡

アイコンの画像にアルファチャンネルが入っている

App Store 用のアイコンは、アルファチャンネルのない画像にします。自分で用意した PNG は、sips -g hasAlpha で hasAlpha: no になっていることを確かめてください。 ローカルのビルドでは、アルファ付きの PNG でもエラーになりません。そのため、アップロードの前に必ず確かめます。

💡

ビルドが「Missing Compliance」のまま配れない

ITSAppUsesNonExemptEncryption がアプリの Info.plist に入っていません。ステップ 3 の設定を確かめるか、App Store Connect でビルドを開き、Provide Export Compliance Information の質問に答えます。

まとめ

配布の前に、Bundle ID・App Group・チームを自分のものにそろえ、バージョンを 1.0.0 にしました。1024×1024・アルファなしのアプリアイコンを用意し、ITSAppUsesNonExemptEncryption を NO にしました。 xcodebuild archive で署名なしのアーカイブを作って中身を確かめ、署名ありのアーカイブにはチームとプロファイルが必要なことを、実際のエラーから確かめました。 手順解説パートでは、App Store Connect へのアプリ登録と、Organizer の Distribute App でのアップロードを押さえました。テスターの招待とフィードバック、ビルド番号を上げての再配布の流れも確認しました。
