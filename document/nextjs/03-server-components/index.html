サーバーコンポーネントとデータ取得

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: 02 を終え、外部 API のデータを Next.js の画面に表示したい人
  • 📋 前提: JavaScript の async / await と Promise の基本が分かること
  • 🌐 ネットワーク: 外部 API（JSONPlaceholder）に接続できる環境が必要
  • 🔗 前提となる項目: 02: App Router の基礎とファイルベースルーティング

🎯 このレッスンで学ぶこと

  • サーバーコンポーネントがサーバー上で動くことを確かめ、クライアントコンポーネントとの違いを説明できる
  • async コンポーネントの中で fetch を使い、外部 API のデータを表示できる
  • fetch のキャッシュ設定によって、ビルド結果（Static / Dynamic / ISR）が変わることを読み取れる
  • Promise.all で並列にデータを取得し、Suspense でページの一部を後から表示できる
  • Route Handler で自前の API エンドポイントを作れる
  • error.tsx でデータ取得の失敗を画面に表示できる

概要

02 では、記事データを src/app/blog/_data/posts.ts の配列に直接書き、loading.tsx の動作を見せるために 1 秒の delay() を入れていました。 このレッスンでは、この配列を外部 API からの取得に置き換えます。ダミーの遅延が担っていた「データを待つ時間」は、本物の API の応答待ちが引き継ぎます。

外部 API には、登録不要で使えるテスト用の REST API「JSONPlaceholder」（https://jsonplaceholder.typicode.com）を使います。 記事（/posts）とユーザー（/users）のダミーデータを JSON で返してくれます。

ℹ️

出発点

02 で使ったプロジェクトをそのまま使って続けます。ディレクトリ名は変えなくて構いません。 02 の完成状態（_data/posts.ts の配列と 1 秒の delay() を使うブログ）がこのレッスンのスタート地点です。

⚠️

インターネット接続が必要です

このレッスンでは、開発サーバーの実行中だけでなく npm run build の実行中にも JSONPlaceholder へアクセスします。 オフラインの環境や、社内プロキシで外部への通信が制限されている環境では、ページの表示やビルドが失敗します。 うまくいかないときは、まずブラウザで https://jsonplaceholder.typicode.com/posts/1 を開き、JSON が表示されるかを確かめてください。

次に、JSONPlaceholder から記事を取得する関数を作ります。API が返す形（JsonPlaceholderPost）を toPost で画面用の Post に変換し、 API の id を動的ルート [slug] の値として使います。 応答が失敗（res.ok が false）のときは例外を投げます。この例外はステップ 6 で error.tsx が受け止めます。

TypeScript src/features/posts/api/fetchPosts.ts 
import type { Post } from "../types";

const API_BASE = "https://jsonplaceholder.typicode.com";

type JsonPlaceholderPost = {
  id: number;
  userId: number;
  title: string;
  body: string;
};

function toPost(raw: JsonPlaceholderPost): Post {
  return {
    id: raw.id,
    userId: raw.userId,
    // JSONPlaceholder の id をそのまま動的ルート [slug] の値として使う。
    slug: String(raw.id),
    title: raw.title,
    body: raw.body,
  };
}

export async function fetchPosts(): Promise<Post[]> {
  const res = await fetch(`${API_BASE}/posts?_limit=5`);

  if (!res.ok) {
    throw new Error(`記事一覧の取得に失敗しました (status: ${res.status})`);
  }

  const posts: JsonPlaceholderPost[] = await res.json();

  return posts.map(toPost);
}

export async function fetchPost(id: string): Promise<Post | null> {
  const res = await fetch(`${API_BASE}/posts/${id}`);

  if (res.status === 404) {
    return null;
  }

  if (!res.ok) {
    throw new Error(`記事の取得に失敗しました (status: ${res.status})`);
  }

  const post: JsonPlaceholderPost = await res.json();

  return toPost(post);
}

ここで fetch に渡しているのは、ブラウザと同じ標準の fetch です。サーバーコンポーネントは async 関数にできるので、await fetchPosts() のように書くだけで取得が終わるまで待てます。

3

キャッシュの挙動をビルド結果で確かめる

Next.js 16 の fetch は、オプションによって「いつ外部 API にアクセスするか」が変わります。その違いは、npm run build の Route (app) の一覧に表れます。 まず、ステップ 2 のようにオプションを省略したときの動作を押さえておきます。

  • npm run dev（開発中）では、リクエストのたびに外部 API から取得します。
  • npm run build では、ビルド中に 1 回だけ取得し、その結果を静的な HTML として保存します（○ Static）。ただし、そのルートで cookies()・headers() などのリクエスト時に決まる API を使っている場合は、リクエストのたびに取得します。
⚠️

「オプション省略 = 毎回取得する動的なページ」ではない

開発中は毎回取得されるため、オプションを省略すると本番でも常に最新のデータを取りに行くと思いがちです。 実際には、/blog のようにリクエスト時に決まる入力を使わないルートでは、ビルド時に 1 回だけ取得した内容が静的な HTML に焼き込まれます。この場合のビルド結果は、次に試す cache: "force-cache" と同じです。 リクエストごとに取得する動的なページ（ƒ Dynamic）にしたいときは、cache: "no-store" を明示します。この挙動は、Next.js 同梱ドキュメントの fetch の API リファレンスに記載されています。

ここからはオプションだけを変えてビルドを 3 回実行し、結果を比べます。開発サーバーを Ctrl + C で止めてから進めてください。 ビルドはいずれも次のコマンドで実行します。前回の結果が残らないよう、.next を消してからビルドします。

Terminal 
$ rm -rf .next && npm run build

4

Promise.all で並列に取得し、Suspense で一部を後から表示する

一覧ページに、記事ごとの著者名と、ページ下部の「投稿者一覧」を追加します。ユーザー情報は JSONPlaceholder の /users から取得します。 記事と同じように、src/features/users/ に型と取得関数を作ります。

TypeScript src/features/users/types.ts 
export type User = {
  id: number;
  name: string;
  username: string;
};
TypeScript src/features/users/api/fetchUsers.ts 
import type { User } from "../types";

const API_BASE = "https://jsonplaceholder.typicode.com";

type JsonPlaceholderUser = {
  id: number;
  name: string;
  username: string;
};

/**
 * ユーザー一覧を取得する。オプション省略（auto no cache）。
 * Data Cache は使わないが、静的ルートではビルド時に 1 回だけ取得される。
 */
export async function fetchUsers(): Promise<User[]> {
  const res = await fetch(`${API_BASE}/users`);

  if (!res.ok) {
    throw new Error(`ユーザー一覧の取得に失敗しました (status: ${res.status})`);
  }

  const users: JsonPlaceholderUser[] = await res.json();

  return users.map((user) => ({
    id: user.id,
    name: user.name,
    username: user.username,
  }));
}

一覧ページを次の内容に書き換えます（全文）。

TypeScript src/app/blog/page.tsx 
import Link from "next/link";
import { Suspense } from "react";
import { fetchPosts } from "@/features/posts/api/fetchPosts";
import { fetchUsers } from "@/features/users/api/fetchUsers";
import { AuthorList } from "./_components/AuthorList";
import styles from "./page.module.scss";

export default async function BlogPage() {
  // 投稿と著者を直列に await すると 2 回分の待ち時間がかかる。
  // Promise.all で同時に投げて、両方の完了を 1 回の待ち時間にまとめる。
  const [posts, users] = await Promise.all([fetchPosts(), fetchUsers()]);

  const authorNameById = new Map(users.map((user) => [user.id, user.name]));

  return (
    <div>
      <h1 className={styles.title}>Blog</h1>
      <ul className={styles.list}>
        {posts.map((post) => (
          <li key={post.slug} className={styles.item}>
            <Link href={`/blog/${post.slug}`} className={styles.itemTitle}>
              {post.title}
            </Link>
            <p className={styles.itemAuthor}>
              by {authorNameById.get(post.userId) ?? "unknown"}
            </p>
            <p className={styles.itemBody}>{post.body}</p>
          </li>
        ))}
      </ul>

      {/*
        AuthorList は fetchUsers() を内部で再度呼んでいるが、
        同一レンダーパス中の同一 URL・オプションの GET fetch は Next.js が自動的にメモ化するため、
        実際に発生する外部リクエストは 1 回だけになる。
        Suspense でストリーミングされる境界であることを示すため、あえて別コンポーネントに切り出している。
      */}
      <Suspense fallback={<p className={styles.authorsLoading}>投稿者一覧を読み込み中...</p>}>
        <AuthorList />
      </Suspense>
    </div>
  );
}

ポイントは 2 つです。

  • 並列取得: await fetchPosts() と await fetchUsers() を順に書くと、1 つ目の応答を待ってから 2 つ目を送るため、待ち時間が 2 回分かかります。 Promise.all で 2 つを同時に送れば、待ち時間は遅いほう 1 回分で済みます。
  • Suspense: <Suspense> で包んだ AuthorList は、データの準備ができるまで fallback の「投稿者一覧を読み込み中...」が表示されます。準備ができると、その部分だけが後から差し込まれます（ストリーミング）。
💡

<Suspense> と loading.tsx の使い分け

loading.tsx は、ルートセグメント（ここでは /blog 配下）のページ全体を 1 つのフォールバックで覆います。ページ全体の準備ができるまで、中身はまとめて表示されません。 <Suspense> は、ページの中の特定の部分だけを囲む境界です。囲んだ部分が待っている間も、ページのほかの部分（記事一覧など）は先に表示されます。

両方を併用できます。ページを移動した直後の反応をよくしたいときは loading.tsx、ページ内で「すぐ見せたい部分」と「少し待たせてもよい部分」を分けたいときは <Suspense> を使います。 今回は、記事一覧はすぐ見せ、投稿者一覧は後から表示してもよい、という想定で AuthorList だけを <Suspense> で包んでいます。

ℹ️

同じ fetch を何度呼んでも、リクエストは 1 回にまとまる

page.tsx と AuthorList はどちらも fetchUsers() を呼んでいます。layout.tsx と page.tsx も、どちらも fetchPosts() を呼んでいます。 1 回の描画の中で、同じ URL・同じオプションの GET の fetch は自動的にまとめられ（メモ化）、外部 API へのリクエストは 1 回しか送られません。 そのため、データが必要なコンポーネントの中で、それぞれ取得関数を呼んで構いません。

このメモ化は 1 回の描画の間だけ有効で、ステップ 3 の revalidate などによるキャッシュ（リクエストをまたいで保持される）とは別の仕組みです。 なお、この例では page.tsx が先に fetchUsers() の完了を待っているため、AuthorList のフォールバックはほとんど目に見えない場合があります。ストリーミングの境界の書き方を示すために、あえて別コンポーネントに分けています。

⚠️

async コンポーネントはサーバーコンポーネントの中でだけ使える

AuthorList のような async function のコンポーネントは、サーバーコンポーネントの JSX の中では <AuthorList /> とそのまま書けます。 ただし、"use client" を付けたクライアントコンポーネントから import して使うことはできません。

Route Handler で /api/posts を公開する

Route Handler は、route.ts に HTTP メソッド名（GET・POST など）の関数を書いて、Web API のエンドポイントを作る仕組みです。 page.tsx と同じくフォルダ構成が URL になり、src/app/api/posts/route.ts は /api/posts になります。

TypeScript src/app/api/posts/route.ts 
import { NextResponse } from "next/server";

// Route Handler。ブラウザや curl など、サーバーコンポーネントの外側から呼ばれる
// 独立した Web API エンドポイントとして動く。サーバーコンポーネントから直接この URL を
// fetch する必要はない（fetchPosts() は JSONPlaceholder を直接叩いている）。
export async function GET() {
  const res = await fetch("https://jsonplaceholder.typicode.com/posts?_limit=5");

  if (!res.ok) {
    return NextResponse.json(
      { error: `記事一覧の取得に失敗しました (status: ${res.status})` },
      { status: res.status },
    );
  }

  const posts = await res.json();

  return NextResponse.json({ posts });
}
ℹ️

なぜ fetchPosts は /api/posts を呼ばないのか

Route Handler は、ブラウザの JavaScript・モバイルアプリ・curl など、Next.js のコンポーネントの外にいるクライアントへ API を公開するためのものです。 サーバーコンポーネントはもともとサーバー上で動いているので、外部 API やデータベースに直接アクセスできます。自分の Route Handler を経由すると、同じサーバーの中で HTTP リクエストを 1 回余分に往復させることになります。 そのため、fetchPosts は JSONPlaceholder を直接呼んでいます。

reset と retry

この教材では、エラー状態を消して中身を描画し直す reset() をボタンに割り当てています。 Next.js 16.3 からは、中身のデータを取得し直してから描画し直す retry() が正式な API になり、公式ドキュメントでは多くの場合 retry() を使うよう勧めています。 実際のアプリで「もう一度読み込む」ボタンを作るときは、retry() を検討してください。

ℹ️

本番環境ではエラーメッセージが表示されない

開発中は error.message に元の例外のメッセージが入るため、画面に「ユーザー一覧の取得に失敗しました (status: 404)」と表示されます。 本番ビルドでは、機密情報の漏えいを防ぐため、サーバーコンポーネントから渡されるエラーは汎用のメッセージと識別子（error.digest）に置き換えられます。この挙動は、Next.js 同梱ドキュメントの error.js の API リファレンスに記載されています。
