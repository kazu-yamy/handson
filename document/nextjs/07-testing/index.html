概要

06 までで、ブログのページと再利用できる部品がそろいました。 このレッスンでは、関数や部品が期待どおりに動くことをコードで確かめる「自動テスト」を導入します。 テストがあれば、あとで部品を書き換えたときに壊れた箇所をコマンド 1 つで見つけられます。

テストの種類と役割分担

フロントエンドのテストは、何を・どこで動かすかによって次のように分けられます。

種類確かめるもの実行環境このトラックでの扱い
純粋関数のユニットテスト入力に対する戻り値（例: filterPosts、fetchPosts）Vitest の unit プロジェクト07（このレッスン）
コンポーネントテスト描画結果・操作による状態の変化・コールバックの呼び出しVitest の unit プロジェクト（jsdom）07（このレッスン）
ブラウザテスト（Storybook の play）ストーリーが描画できるか、簡単な操作の結果Vitest の storybook プロジェクト（Playwright + Chromium）05 で導入済み
E2E テスト起動したアプリをブラウザで通しで操作した結果実ブラウザ + 起動したサーバーこのトラックでは扱わない

jsdom は、ブラウザの DOM を Node.js 上で再現するライブラリです。 本物のブラウザを起動しないので速い反面、レイアウトの計算はしません。 たとえば jsdom では getBoundingClientRect() は幅と高さに 0 を返し、IntersectionObserver も用意されていません。 そのため、このトラックでは「見た目とブラウザでの動作は Storybook、ロジックの分岐や状態の変化は unit プロジェクト」と役割を分けます。

05 の Storybook 用プロジェクトとの関係

05 で storybook init を実行したとき、Vitest の設定ファイル vitest.config.ts が作られました。 その test.projects には、ストーリーを Chromium で実行する storybook プロジェクトが 1 つだけ定義されています。 Vitest の projects を使うと、1 つの設定ファイルの中に、実行環境の違うテストのまとまりを複数並べられます。 このレッスンでは、この配列に jsdom で動く unit プロジェクトを追加します。 実行するときは --project=unit のように名前を指定して、片方だけを動かせます。

次に、unit プロジェクト専用のセットアップファイル vitest.setup.ts をプロジェクト直下に作ります。 セットアップファイルは、各テストファイルの前に毎回実行されます。

TypeScript vitest.setup.ts 
// unit プロジェクト（jsdom）専用のセットアップファイル。
// @testing-library/jest-dom の toBeInTheDocument() などのカスタムマッチャーを追加する。
import "@testing-library/jest-dom/vitest";

import { afterEach } from "vitest";
import { cleanup } from "@testing-library/react";

// test.globals を true にしていない（globals は使わず describe/it/expect を明示 import する方針）ため、
// @testing-library/react が Jest/Vitest のグローバル afterEach を検出できず、
// render() したコンポーネントが次のテストの DOM に残ってしまう。
// そのため cleanup() をここで手動で afterEach に登録する。
afterEach(() => {
  cleanup();
});

1 行目の import で、jest-dom のマッチャーが Vitest の expect に追加されます。 後半の afterEach(() => { cleanup(); }) は、テストごとに描画した要素を片付ける処理です。 このトラックでは describe / it / expect を毎回 "vitest" から import する方針にし、Vitest の globals オプションは有効にしません。 その場合、Testing Library は片付けを自動では登録しないので、ここに書いて登録します。 登録し忘れたときに何が起きるかは、ステップ 3 で実際のエラーを見ます。

unit には extends: true を付けない

既存の storybook プロジェクトには extends: true が付いていて、ルートの設定を引き継ぎます。 unit プロジェクトは必要な設定をすべて自分で書くので、extends: true は付けていません。 なお、tsconfig.json は変更しません。 jest-dom のマッチャーの型は @testing-library/jest-dom/vitest の import で読み込まれるため、types への追記は不要でした。

絞り込みを純粋関数に切り出してテストする

最初のテストの題材は、04 で作った記事の絞り込みです。 06 までの PostFilter は、絞り込みの処理をコンポーネントの中に直接書いていました。 この形のままテストするには、コンポーネントを描画し、入力欄に文字を打ち込み、表示された件数を読む必要があります。

そこで、絞り込みの処理だけを 純粋関数（同じ入力には必ず同じ出力を返し、外部の状態を変えない関数）として切り出します。 純粋関数なら、配列と検索語を渡して戻り値を比べるだけでテストできます。 「テストしやすい形に切り出す」ことは、ロジックと表示を分ける設計そのものでもあります。

src/features/posts/lib/filterPosts.ts を新しく作ります。

TypeScript src/features/posts/lib/filterPosts.ts 
export type FilterablePost = {
  slug: string;
  title: string;
  body: string;
  authorName: string;
};

/**
 * 記事一覧を検索語で絞り込む。
 * 大文字小文字を区別せず、title または body に検索語を含む記事だけを返す。
 * query が空文字（前後の空白のみを含む）のときは全件を返す。
 */
export function filterPosts(posts: FilterablePost[], query: string): FilterablePost[] {
  const normalizedQuery = query.trim().toLowerCase();

  if (normalizedQuery === "") {
    return posts;
  }

  return posts.filter((post) =>
    `${post.title} ${post.body}`.toLowerCase().includes(normalizedQuery),
  );
}

import { describe, expect, it } from "vitest";
import { filterPosts, type FilterablePost } from "./filterPosts";

const posts: FilterablePost[] = [
  { slug: "1", title: "Next.js 入門", body: "App Router を使う", authorName: "Alice" },
  { slug: "2", title: "Rust ではじめる Web API", body: "Axum を使う", authorName: "Bob" },
  { slug: "3", title: "TypeScript の型システム", body: "型推論について", authorName: "Carol" },
];

describe("filterPosts", () => {
  it("query が空文字のときは全件を返す", () => {
    expect(filterPosts(posts, "")).toEqual(posts);
  });

  it("query が空白のみのときも全件を返す", () => {
    expect(filterPosts(posts, "   ")).toEqual(posts);
  });

  it("title に部分一致する記事だけを返す", () => {
    const result = filterPosts(posts, "Next");

    expect(result).toEqual([posts[0]]);
  });

  it("大文字小文字を区別しない", () => {
    const result = filterPosts(posts, "typescript");

    expect(result).toEqual([posts[2]]);
  });

  it("body に部分一致する記事だけを返す", () => {
    const result = filterPosts(posts, "Axum");

    expect(result).toEqual([posts[1]]);
  });

  it("該当する記事がないときは空配列を返す", () => {
    expect(filterPosts(posts, "存在しない記事")).toEqual([]);
  });
});

  • expect(実際の値).toEqual(期待する値) は、配列やオブジェクトの中身が等しいかを比べます。
  • ケースは「空文字」「空白のみ」「タイトルに部分一致」「大文字小文字を区別しない」「本文に部分一致」「該当なし」の 6 つです。filterPosts の trim() と toLowerCase() が、それぞれどのケースで必要になるかを対応させて読んでみてください。

3

コンポーネントを描画して操作する

次は、コンポーネントを描画して検証します。 Testing Library の基本は、render で描画し、screen から要素を探し、expect で確かめる流れです。 要素を探すときは、画面の利用者が認識できる情報（ロールやラベル、表示されたテキスト）を使います。 まずは 06 で作った Button から始めます。

TypeScript src/components/Button/Button.test.tsx 
import { render, screen } from "@testing-library/react";
import { describe, expect, it } from "vitest";
import { Button } from "./Button";

describe("Button", () => {
  it("デフォルトでは variant=primary / size=md が data-* 属性に反映される", () => {
    render(<Button>送信</Button>);

    const button = screen.getByRole("button", { name: "送信" });

    expect(button).toHaveAttribute("data-variant", "primary");
    expect(button).toHaveAttribute("data-size", "md");
  });

  it("variant / size を指定すると data-* 属性が反映される", () => {
    render(
      <Button variant="secondary" size="sm">
        いいね
      </Button>,
    );

    const button = screen.getByRole("button", { name: "いいね" });

    expect(button).toHaveAttribute("data-variant", "secondary");
    expect(button).toHaveAttribute("data-size", "sm");
  });
});

screen.getByRole("button", { name: "送信" }) は、「送信」という名前（アクセシブルな名前）を持つボタンを探します。 toHaveAttribute は jest-dom が追加したマッチャーで、06 で variant / size を出力するようにした data-* 属性を確かめます。

続いて、クリックで状態が変わる LikeButton をテストします。 LikeButton は aria-label に「記事 1 にいいねする」を設定しているので、その名前でボタンを探せます。

TypeScript src/components/LikeButton/LikeButton.test.tsx 
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, expect, it, vi } from "vitest";
import { LikeButton } from "./LikeButton";

describe("LikeButton", () => {
  it("初期表示で initialCount が表示される", () => {
    render(<LikeButton postId={1} initialCount={3} />);

    expect(screen.getByRole("button", { name: "記事 1 にいいねする" })).toHaveTextContent(
      "👍 いいね 3",
    );
  });

  it("クリックするたびにカウントが 1 ずつ増える", async () => {
    const user = userEvent.setup();
    render(<LikeButton postId={1} initialCount={0} />);

    const button = screen.getByRole("button", { name: "記事 1 にいいねする" });
    await user.click(button);
    await user.click(button);

    expect(button).toHaveTextContent("👍 いいね 2");
  });

  it("クリックすると onLiked が更新後のカウントで 1 回だけ呼ばれる", async () => {
    const user = userEvent.setup();
    const onLiked = vi.fn();
    render(<LikeButton postId={1} initialCount={0} onLiked={onLiked} />);

    await user.click(screen.getByRole("button", { name: "記事 1 にいいねする" }));

    expect(onLiked).toHaveBeenCalledTimes(1);
    expect(onLiked).toHaveBeenCalledWith(1);
  });
});
  • userEvent.setup() で操作用のインスタンスを作ってから render し、await user.click(...) でクリックします。setup() を render より先に呼ぶ書き方は Testing Library の公式ドキュメントが推奨しており、このレッスンでは、すべての操作をこの書き方で統一します。
  • user.click は Promise を返します。await を忘れると、クリックによる状態の更新が反映される前に検証してしまい、成功したり失敗したりする不安定なテストの原因になります。
  • vi.fn() は、呼ばれた回数と引数を記録する関数（モック関数）です。toHaveBeenCalledTimes(1) と toHaveBeenCalledWith(1) で、onLiked が更新後のカウントで 1 回だけ呼ばれたことを確かめます。

fetch をモックしてデータ取得関数をテストする

03 で作った fetchPosts は、JSONPlaceholder から記事を取得します。 テストのたびに本物の API へアクセスすると、ネットワークの状態で結果が変わり、失敗時の動きも試せません。 そこで、グローバルの fetch を、決まった値を返す偽物（モック）に差し替えます。

TypeScript src/features/posts/api/fetchPosts.test.ts 
import { afterEach, describe, expect, it, vi } from "vitest";
import { fetchPosts } from "./fetchPosts";

// レスポンスの一部（.ok と .json() だけ）を満たすダミー。fetch の戻り値全体（Response 型）を
// 作り込む必要はなく、fetchPosts が実際に使っているプロパティだけあれば十分。
function createResponse(overrides: { ok: boolean; status?: number; body?: unknown }) {
  return {
    ok: overrides.ok,
    status: overrides.status ?? (overrides.ok ? 200 : 500),
    json: async () => overrides.body,
  } as Response;
}

describe("fetchPosts", () => {
  afterEach(() => {
    vi.unstubAllGlobals();
  });

  it("正常系: JSONPlaceholder のレスポンスを Post[] に変換して返す", async () => {
    const fetchMock = vi.fn().mockResolvedValue(
      createResponse({
        ok: true,
        body: [
          { id: 1, userId: 10, title: "タイトル1", body: "本文1" },
          { id: 2, userId: 20, title: "タイトル2", body: "本文2" },
        ],
      }),
    );
    vi.stubGlobal("fetch", fetchMock);

    const posts = await fetchPosts();

    expect(posts).toEqual([
      { id: 1, userId: 10, slug: "1", title: "タイトル1", body: "本文1" },
      { id: 2, userId: 20, slug: "2", title: "タイトル2", body: "本文2" },
    ]);
    expect(fetchMock).toHaveBeenCalledWith(
      "https://jsonplaceholder.typicode.com/posts?_limit=5",
      { next: { revalidate: 60 } },
    );
  });

  it("異常系: res.ok が false のときは status を含むエラーを投げる", async () => {
    vi.stubGlobal(
      "fetch",
      vi.fn().mockResolvedValue(createResponse({ ok: false, status: 503 })),
    );

    await expect(fetchPosts()).rejects.toThrow("記事一覧の取得に失敗しました (status: 503)");
  });
});
  • createResponse: fetchPosts が使うのは ok / status / json() だけなので、その 3 つだけを持つオブジェクトを as Response で Response 型として扱います。
  • vi.fn().mockResolvedValue(...): 呼ばれると、指定した値で解決する Promise を返すモック関数を作ります。
  • vi.stubGlobal("fetch", fetchMock): グローバルの fetch をモック関数に置き換えます。afterEach の vi.unstubAllGlobals() で元に戻し、ほかのテストに影響を残さないようにします。
  • 正常系: 戻り値が slug を付けた形に変換されていることに加えて、fetch が正しい URL と { next: { revalidate: 60 } } で呼ばれたことも確かめます。
  • 異常系: ok: false のレスポンスを返させ、await expect(fetchPosts()).rejects.toThrow(...) で、ステータスコードを含むエラーで失敗することを確かめます。
ℹ️

vi.stubGlobal と vi.spyOn

vi.stubGlobal は、fetch のようなグローバルな値をまるごと置き換えます。 一方 vi.spyOn(オブジェクト, "メソッド名") は、既存のオブジェクトのメソッドを監視し、必要なら中身を差し替えます。 ステップ 5 では、vi.spyOn(console, "error") で React が出す警告を捕まえます。

// async コンポーネント。fetch が終わるまでの間、page.tsx 側の Suspense fallback が表示され、

import { describe, expect, it, vi } from "vitest";
import { AuthorList } from "./AuthorList";

vi.mock("@/features/users/api/fetchUsers", () => ({
  fetchUsers: vi.fn().mockResolvedValue([
    { id: 1, name: "Alice", username: "alice" },
    { id: 2, name: "Bob", username: "bob" },
  ]),
}));

describe("AuthorList", () => {
  it("直接 <AuthorList /> を render すると React が警告を出し、中身が描画されない（記録用）", () => {
    // AuthorList は async 関数コンポーネント（サーバーコンポーネント）なので、
    // 通常のクライアント向け render() に JSX としてそのまま渡しても例外は投げられない。
    // 代わりに React が console.error に警告を出し、コンポーネントの中身は描画されない。
    const consoleError = vi.spyOn(console, "error").mockImplementation(() => {});

    render(<AuthorList />);

    // React は console.error("%s is an async Client Component. ...", "<AuthorList>") のように
    // 書式文字列とコンポーネント名を別引数で渡すため、1 引数目だけを検証する。
    expect(consoleError).toHaveBeenCalledWith(
      expect.stringContaining(
        "%s is an async Client Component. Only Server Components can be async at the moment.",
      ),
      "<AuthorList>",
    );
    expect(screen.queryByText(/Alice/)).not.toBeInTheDocument();

    consoleError.mockRestore();
  });

  it("await AuthorList() の戻り値を render すると、fetchUsers の結果が表示される", async () => {

    expect(screen.getByText("Alice（@alice）")).toBeInTheDocument();
    expect(screen.getByText("Bob（@bob）")).toBeInTheDocument();

});

  • 1 つ目のテスト（記録用）: 直接描画したときの挙動を残すためのテストです。vi.spyOn(console, "error").mockImplementation(() => {}) で上の警告を捕まえ、出力を止めます。React は警告の書式文字列とコンポーネント名 "<AuthorList>" を別々の引数で渡すため、検証も 2 引数で書きます。最後の mockRestore() で console.error を元に戻します。

⚠️

vi.mock はファイルの先頭に巻き上げられる

vi.mock の呼び出しは、どこに書いても、ファイル内の import 文より前に移動して実行されます（巻き上げ、hoisting）。 AuthorList を import した時点で、すでに fetchUsers がモックになっているのはこのためです。 その反面、ファイル内で宣言した変数をファクトリの中で参照すると、初期化前の変数を読むことになります。この場合は ReferenceError が起きやすくなります。 ここではファクトリの中でモックのデータまで完結させて、この問題を避けています。
