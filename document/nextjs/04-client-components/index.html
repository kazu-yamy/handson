クライアントコンポーネントと状態管理

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: 03 を終え、クリックや入力に反応する画面を Next.js で作りたい人
  • 📋 前提: React のコンポーネントと props、JSX の基本が分かること
  • 🌐 ネットワーク: 03 と同じく外部 API（JSONPlaceholder）に接続できる環境が必要
  • 🔗 前提となる項目: 03: サーバーコンポーネントとデータ取得

🎯 このレッスンで学ぶこと

  • 状態・イベント・ブラウザ API の有無で、サーバーコンポーネントとクライアントコンポーネントを使い分けられる
  • "use client" を付けたコンポーネントで useState を使い、クリックや入力に反応する UI を作れる
  • サーバーからクライアントへ渡す props の制約（シリアライズ可能な値だけ）を説明できる
  • 「データ取得はサーバー、操作はクライアント」の分担と、children でサーバーコンポーネントを包むパターンを使える
  • useEffect でブラウザ API の値を反映し、window is not defined とハイドレーション不一致を避けられる
  • useState と useReducer の違いを説明できる

概要

03 では、サーバーコンポーネントで外部 API のデータを取得して表示しました。ただし、表示した画面はクリックや入力をしても何も変わりません。 このレッスンでは、03 のブログに「いいねボタン」「記事の検索」「投稿者一覧の開閉」「テーマ切り替え」を加え、ユーザーの操作に反応する部分をクライアントコンポーネントとして作ります。

ℹ️

出発点

03 で使ったプロジェクトをそのまま使って続けます。03 の完成状態（JSONPlaceholder から記事と投稿者を取得するブログ）がこのレッスンのスタート地点です。 作業を始める前に、package.json の name を 04-client-components に直しておきます（02-app-router のまま残っている場合があります）。

使用バージョン

Node.js 24.21.0 / npm 11.19.0 / Next.js 16.3.6 / React 19.2.8 / sass 1.105.0 で動作を確認しています（執筆時点: 2026年9月）。03 と同じ構成です。

サーバーとクライアントの使い分けの判断基準

03 で見たとおり、App Router のコンポーネントは既定でサーバーコンポーネントです。クライアントコンポーネントにするのは、次の表の左側のどれかが必要な部分だけに絞ります。

コンポーネントに必要なもの選ぶ種類このレッスンでの例
状態（useState / useReducer）クライアントいいね数、検索語、開閉状態
イベント（onClick / onChange など）クライアントボタンのクリック、検索ボックスへの入力
ブラウザ API（window / document / localStorage）と useEffectクライアントテーマの保存と読み込み
上のどれも不要（async / await でのデータ取得、表示だけの部分）サーバー（既定のまま）blog/page.tsx、AuthorList

ページ全体をクライアントコンポーネントにするのではなく、操作が必要な小さな部品だけを切り出して "use client" を付けます。 データの取得や表示だけの部分はサーバーに残しておけば、03 で作った fetch やキャッシュの仕組みをそのまま使えます。

⚠️

"use client" はファイル単位で、import 先まで効く

"use client" は、そのファイルを「サーバーとクライアントの境界」にする指定です。そのファイルが import しているモジュールも、まとめてクライアント向けの JavaScript に含まれます。 つまり、"use client" のファイルの中で import したコンポーネントは、それ自身に "use client" がなくてもクライアントで実行されます。 境界をツリーの上のほうに置くほど、クライアントに送る JavaScript が増え、サーバーコンポーネントとして書ける範囲が狭くなります。境界はできるだけ末端の小さな部品に置きます。

1

2

useState でいいねボタンを作る

記事の詳細ページに「いいね」ボタンを置きます。クリックのたびに数が増えるので、状態（useState）とイベント（onClick）が必要です。 冒頭の判断基準に照らすとクライアントコンポーネントになります。

このボタンは記事ページ以外でも再利用できる部品なので、src/components/LikeButton/ に置きます。 src/components/ はこのレッスンで初めて作るディレクトリです。

TypeScript src/components/LikeButton/LikeButton.tsx 
"use client";

import { useState } from "react";
import styles from "./LikeButton.module.scss";

type LikeButtonProps = {
  postId: number;
  initialCount: number;
};

// "use client" を付けたクライアントコンポーネント。
// サーバーコンポーネント（例: blog/[slug]/page.tsx）の JSX の中にそのまま置ける。
export function LikeButton({ postId, initialCount }: LikeButtonProps) {
  const [count, setCount] = useState(initialCount);

  return (
    <button
      type="button"
      className={styles.button}
      onClick={() => setCount((current) => current + 1)}
      aria-label={`記事 ${postId} にいいねする`}
    >
      👍 いいね {count}
    </button>
  );
}

1 行目の "use client" が、このファイルをクライアントコンポーネントにする指定です。import より前、ファイルの先頭に書きます。 useState(initialCount) は「現在の値 count」と「値を更新する関数 setCount」の組を返します。 setCount((current) => current + 1) のように関数を渡すと、直前の値をもとに次の値を計算できます。

ℹ️

クライアントコンポーネントもサーバーで HTML が生成される

「クライアントコンポーネント」という名前ですが、ブラウザだけで動くわけではありません。初回アクセス時にはサーバーでも一度実行され、その結果が HTML として返されます（SSR）。 ブラウザはその HTML をすぐに表示し、あとから届いた JavaScript がボタンにクリック処理を結び付けます。この「結び付け」をハイドレーションと呼びます。 "use client" が意味するのは「ブラウザでも動く（ブラウザ向けの JavaScript に含める）」ことであり、「サーバーでは動かない」ことではありません。この性質は、ステップ 6 で重要になります。

✅ 確認ポイント

ブラウザで「👍 いいね 3」のボタンが表示され、クリックするたびに数が 1 ずつ増えれば成功です（/blog/1 の初期値は 1 * 3 = 3）。 ページを再読み込みすると初期値に戻ることも確かめましょう。状態はブラウザのメモリにしかないためです。 curl の結果に「いいね」が含まれていれば、SSR されていることも確認できています。

3

props のシリアライズ制約を確かめる（関数は渡せない）

サーバーコンポーネントからクライアントコンポーネントに渡す props は、サーバーからブラウザへ送られます。そのため、送れる形（シリアライズ可能な値）でなければなりません。 関数を渡すとどうなるかを、一時的な変更で確かめます。まず LikeButton に、いいねされたときに呼ぶ関数 onLiked を受け取る props を追加します。

Diff src/components/LikeButton/LikeButton.tsx（一時的な変更） 
  type LikeButtonProps = {    postId: number;    initialCount: number;+   onLiked?: () => void;  };

保存すると、LikeButton.tsx の型に次の警告が表示されます。

エディタの警告表示（LikeButton.tsx） 
Props must be serializable for components in the "use client" entry file. "onLiked" is a functionthat's not a Server Action. Rename "onLiked" either to "action" or have its name end with "Action"e.g. "onLikedAction" to indicate it is a Server Action. [71007] (typescript)

⚠️

props で渡せるのはシリアライズ可能な値だけ

サーバーコンポーネントからクライアントコンポーネントへ渡せるのは、文字列・数値・真偽値・プレーンなオブジェクトや配列など、データとして送れる値です。関数は渡せません。 「クリックされたら何かしたい」ときは、その処理自体をクライアントコンポーネントの中に書きます。 サーバー側で処理を実行したい場合は、エラーメッセージにも出てくる Server Actions を使います（このレッスンでは扱いません）。

確認できたら、LikeButton.tsx の onLiked と、[slug]/page.tsx の呼び出し側の変更を元に戻します。

✅ 確認ポイント

関数を渡した状態で、開発サーバーのターミナルに Event handlers cannot be passed to Client Component props. が表示されれば成功です。 元に戻したあと、/blog/1 のいいねボタンがステップ 2 と同じように動くことを確かめてください。

4

PostFilter で「取得はサーバー、操作はクライアント」に分ける

記事一覧に検索ボックスを付け、入力した語による絞り込みをその場で行えるようにします。 ステップ 1 で見たとおり、blog/page.tsx 自体をクライアントコンポーネントにはできません。 そこで、データの取得は page.tsx（サーバー）に残し、一覧の描画と検索の操作だけを PostFilter（クライアント）に切り出します。 PostFilter は一覧ページ専用の部品なので、blog/_components/ に置きます。

TypeScript src/app/blog/_components/PostFilter/PostFilter.tsx 
"use client";

import Link from "next/link";
import { useState } from "react";
import styles from "./PostFilter.module.scss";

type PostListItem = {
  slug: string;
  title: string;
  body: string;
  authorName: string;
};

type PostFilterProps = {
  posts: PostListItem[];
};

// データ取得（fetchPosts / fetchUsers）はサーバーである page.tsx が担当し、
// この PostFilter は受け取った posts を検索語で絞り込んで表示するだけの役割を持つ。
// 「データ取得はサーバー、操作はクライアント」という役割分担の例。
export function PostFilter({ posts }: PostFilterProps) {
  const [query, setQuery] = useState("");

  const normalizedQuery = query.trim().toLowerCase();
  const filteredPosts =
    normalizedQuery === ""
      ? posts
      : posts.filter((post) =>
          `${post.title} ${post.body}`.toLowerCase().includes(normalizedQuery),
        );

  return (
    <div>
      <input
        type="search"
        value={query}
        onChange={(event) => setQuery(event.target.value)}
        placeholder="記事を検索（タイトル・本文）"
        className={styles.input}
        aria-label="記事を検索"
      />
      <p className={styles.count}>
        {filteredPosts.length} / {posts.length} 件
      </p>

      <ul className={styles.list}>
        {filteredPosts.map((post) => (
          <li key={post.slug} className={styles.item}>
            <Link href={`/blog/${post.slug}`} className={styles.itemTitle}>
              {post.title}
            </Link>
            <p className={styles.itemAuthor}>by {post.authorName}</p>
            <p className={styles.itemBody}>{post.body}</p>
          </li>
        ))}
      </ul>

      {filteredPosts.length === 0 && (
        <p className={styles.empty}>「{query}」に一致する記事はありません。</p>
      )}
    </div>
  );
}

PostFilter 自身は fetch を一度も呼びません。props で受け取った posts を、query の値で絞り込んで表示するだけです。 filteredPosts は状態として持たず、描画のたびに posts と query から計算しています。 ほかの状態から計算できる値は、useState を増やさずにこのような派生値として書くのが基本です。

  const [posts, users] = await Promise.all([fetchPosts(), fetchUsers()]);

  const authorNameById = new Map(users.map((user) => [user.id, user.name]));

  // 文字列・数値などシリアライズ可能な値だけにする。著者名はここで解決してから渡す。
  const postsWithAuthor = posts.map((post) => ({
    slug: post.slug,
    title: post.title,
    body: post.body,
    authorName: authorNameById.get(post.userId) ?? "unknown",
  }));

  return (
    <div>
      <h1 className={styles.title}>Blog</h1>

      {/*
        データ取得（fetchPosts / fetchUsers）はここサーバーコンポーネントで行い、
        一覧の描画と検索操作は PostFilter（クライアントコンポーネント）に委ねる。
      */}
      <PostFilter posts={postsWithAuthor} />

      {/*
        AuthorList は fetchUsers() を内部で再度呼んでいるが、
        同一レンダーパス中の同一 URL・オプションの GET fetch は Next.js が自動的にメモ化するため、

        Suspense でストリーミングされる境界であることを示すため、あえて別コンポーネントに切り出している。
      */}
      <Suspense fallback={<p className={styles.authorsLoading}>投稿者一覧を読み込み中...</p>}>
        <AuthorList />
      </Suspense>
    </div>
  );

6-5. 最終形: 理由を書いてルールを無効にする

react-hooks/set-state-in-effect は、useEffect の中で同期的に setState を呼ぶ書き方を指摘するルールです。 今回の setTheme(initial) は、React の外にある localStorage の値をマウント後に取り込む処理です。6-2 と 6-3 で確かめたとおり、この処理は描画中には行えません。 そこで、理由をコメントに書いたうえで、この 1 行だけルールを無効にします。 あわせて、保存値が無ければ window.matchMedia("(prefers-color-scheme: dark)") で OS の配色設定を確認し、それを初期テーマとして使うようにしています。最終形の全文は次のとおりです。

TypeScript src/components/ThemeToggle/ThemeToggle.tsx 
"use client";

import { useEffect, useState } from "react";
import styles from "./ThemeToggle.module.scss";

type Theme = "light" | "dark";

const STORAGE_KEY = "theme";

// サーバーで生成する HTML には localStorage の値を反映できないため、
// 初期値は必ず light 側の見た目に合わせておき、実際の値は useEffect の中で読む。
// useState(() => localStorage.getItem(...)) のように初期化子で読むと、
// サーバーが返した HTML（light 前提）とクライアントの初回レンダー結果（保存済みの dark）が
// 食い違い、ハイドレーションエラーになる。
export function ThemeToggle() {
  // サーバーで生成する HTML は必ず "light" として描画する。
  const [theme, setTheme] = useState<Theme>("light");

  // マウント後（＝ブラウザで実行されるとき）に一度だけ localStorage を読み、
  // 保存されていた値を document とステートに反映する。
  // 保存値が無い場合は、OS の配色設定（prefers-color-scheme）に従って初期テーマを決める。
  useEffect(() => {
    const stored = window.localStorage.getItem(STORAGE_KEY);
    const initial: Theme =
      stored === "light" || stored === "dark"
        ? stored
        : window.matchMedia("(prefers-color-scheme: dark)").matches
          ? "dark"
          : "light";
    // localStorage・matchMedia は React の外側にある状態なので、effect の中で読んで同期する必要がある。
    // eslint-disable-next-line react-hooks/set-state-in-effect -- 外部ストレージとの同期のため意図的
    setTheme(initial);
    document.documentElement.dataset.theme = initial;
  }, []);

  const toggleTheme = () => {
    const next: Theme = theme === "light" ? "dark" : "light";
    setTheme(next);
    document.documentElement.dataset.theme = next;
    window.localStorage.setItem(STORAGE_KEY, next);
  };

  return (
    <button
      type="button"
      className={styles.toggle}
      onClick={toggleTheme}
      aria-pressed={theme === "dark"}
    >
      {theme === "dark" ? "☀️ ライト" : "🌙 ダーク"}
    </button>
  );
}

なぜこのルールがあるのか、ほかの書き方は

useEffect の中で無条件に setState すると、「描画 → effect で状態を更新 → もう一度描画」と、描画が 1 回余分に起きます。 しかも多くの場合、その値は描画中に計算できる派生値です（ステップ 4 の filteredPosts のように）。このルールは、そうした「effect に押し込まなくてよい計算」に気づかせるためのものです。 eslint-disable-next-line で無効にするときは、-- のあとに理由を書き、ほかの人が意図を読み取れるようにしておきます。

React が推奨するのは、外部ストレージと同期するための専用フック useSyncExternalStore を使う書き方です。これを使えば、このルールを無効にせずに書けます。 ただし購読の仕組みの理解が必要になるため、入門の範囲に収めるために、ここでは理由をコメントに書いたうえでルールを抑止する妥協をしています。

useReducer 版と比べる

状態を扱うフックには、useState のほかに useReducer があります。 ステップ 2 の LikeButton を useReducer で書き直した比較用のファイルを、同じフォルダに作ります。 見た目と動きは LikeButton と同じで、LikeButton.module.scss もそのまま使います。

TypeScript src/components/LikeButton/LikeButtonReducer.tsx 
"use client";

import { useReducer } from "react";
import styles from "./LikeButton.module.scss";

type LikeButtonProps = {
  postId: number;
  initialCount: number;
};

type State = { count: number };
type Action = { type: "increment" };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };
    default:
      return state;
  }
}

// LikeButton（useState 版）と同じ見た目・同じ振る舞いを useReducer で書き直したもの。
// このレッスンでは状態が「カウンター 1 個」しかないため useState で十分だが、
// 状態の更新パターンが増えたときに useReducer へ移行する感覚を掴むための比較用コンポーネント。
// 詳細ページ（[slug]/page.tsx）では引き続き LikeButton（useState 版）を使う。
export function LikeButtonReducer({ postId, initialCount }: LikeButtonProps) {
  const [state, dispatch] = useReducer(reducer, { count: initialCount });

  return (
    <button
      type="button"
      className={styles.button}
      onClick={() => dispatch({ type: "increment" })}
      aria-label={`記事 ${postId} にいいねする`}
    >
      👍 いいね {state.count}
    </button>
  );
}

2 つの書き方を並べると、状態を更新する処理の置き場所が違います。

観点useState（LikeButton）useReducer（LikeButtonReducer）
状態の初期化useState(initialCount)useReducer(reducer, { count: initialCount })
更新の書き方setCount((current) => current + 1)dispatch({ type: "increment" })
「次の状態」を決める処理の場所イベントハンドラーの中コンポーネントの外の reducer 関数に集約
向いている場面更新の種類が 1〜2 個の単純な状態更新の種類が多い、または複数の値をまとめて更新する状態

今の「いいね」は「1 増やす」だけなので、useState のほうが短く読みやすく書けます。 ところが、「いいねを取り消す」「リセットする」のように更新の種類が増えると、useState ではイベントハンドラーごとに更新の処理が散らばります。 useReducer なら、「現在の状態」と「何が起きたか（action）」から次の状態を決める処理を、reducer の switch 1 か所に集められます。 reducer は React に依存しない普通の関数なので、単独でテストしやすいという利点もあります。

このファイルは比較のためのもので、詳細ページ（[slug]/page.tsx）では引き続き LikeButton を使います。 index.ts にも追加しません。
