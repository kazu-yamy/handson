DataStore で設定を保存

  • ⏱ 所要時間: 60分（任意の実験を除く）
  • 📊 難易度: 入門
  • 👤 対象: 11 で Room 3 のローカル保存まで作った人
  • 📋 前提: 11 で作ったプロジェクトがビルドでき、エミュレータ（Handson_Android36）を起動できること。エミュレータからインターネットに接続できること（最初の一覧の取得と、release の確認で使います）
  • 🔗 前提となる項目: 11: Room 3 でローカル保存
  • 🧩 版: Kotlin 2.4.20 / AGP 9.4.1 / Compose BOM 2026.09.00 / DataStore 1.2.1（androidx.datastore:datastore-preferences）/ Room 3.0.3 / Ktor 3.6.0
  • 🌿 完成コード: ブランチ android/12-datastore

🎯 このレッスンで学ぶこと

  • Preferences DataStore をアプリで 1 つだけ作り、キーと値の組で設定を保存・読み出しできる
  • 「最初の一覧を取得済み」の印を DataStore に保存し、全件削除して起動し直しても API から取り直さないようにできる
  • 一覧の絞り込みを SavedStateHandle から DataStore に移し、アプリを終了して起動し直しても保たれるようにできる
  • DataStore<Preferences> の偽物を使い、設定の入口（SettingsRepository）を本物のまま、ファイルを作らずにテストできる

概要

11 では、Todo の一覧を Room の DB に保存しました。API に行くかどうかは、DB が空かどうかだけで決めていました。そのため、一覧を全件削除してから起動し直すと、API から最初の 20 件を取り直していました（11 の「この設計の限界」）。

この項目では、Jetpack の DataStore を使い、2 つの値を端末に保存します。

  • 「最初の一覧を取得済み」の印: API から最初の一覧を取得して DB に保存できたら、印を付けます。次の起動からは、DB が空でも、印があれば API に行きません。
  • 一覧の絞り込み（すべて・未完了・完了）: 11 までは SavedStateHandle に置いていました。DataStore に移し、アプリを終了して起動し直しても、前回選んだ絞り込みで一覧が出るようにします。

前提知識として、07 の ViewModel と StateFlow を使います。10 の偽のサーバー（FakeTodoServer）と、11 の TodoRepository・AppContainer・偽の DAO（FakeTodoDao）も使います。

Room と DataStore の使い分け

どちらも、アプリを終了しても残るデータの保存先です。この教材では、次のように使い分けます。

Room（11）DataStore（この項目）
保存するものTodo の一覧のような「行の集まり」少数の設定やフラグ（取得済みの印・絞り込み）
形テーブル。SQL で、条件に合う行だけを読み書きできるキーと値の組。1 つのファイルにまとめて保存する
読み書きの APIDAO に並べた関数（@Query・@Insert など）data（全体の Flow）と updateData（全体を変換して書き込む）の 2 つだけ
この教材のファイルdatabases/todos.dbfiles/datastore/settings.preferences_pb

DataStore の本体は、DataStore<T> という interface です。持っているのは val data: Flow<T> と suspend fun updateData(transform) の 2 つだけです（datastore-core 1.2.1 のソース）。読み書きで扱うのは、いつも保存した値の全体です。行を検索したり、一部の行だけを更新したりする仕組みはありません。数件の設定には十分ですが、件数が増えて検索や並べ替えが要るデータは Room に置きます。

DataStore には、キーと値の組を保存する Preferences DataStore と、自分で定義した型（protobuf）を保存する Proto DataStore があります。この項目では Preferences DataStore を使います。

設定の入口 SettingsRepository を作る

app/src/main/java/com/handson/android01/data/SettingsRepository.kt を作ります。アプリの設定は、このクラスだけを通して読み書きします。

Kotlin app/src/main/java/com/handson/android01/data/SettingsRepository.kt 
package com.handson.android01.data

import androidx.datastore.core.DataStore
import androidx.datastore.preferences.core.Preferences
import androidx.datastore.preferences.core.booleanPreferencesKey
import androidx.datastore.preferences.core.edit
import kotlinx.coroutines.flow.first

// アプリの設定の入口。保存先は Preferences DataStore（キーと値の組を、1 つのファイルに保存する）。
// DataStore<Preferences> は引数で受け取る（テストでは、メモリ上の偽物を渡すため）
class SettingsRepository(private val dataStore: DataStore<Preferences>) {

    // 「初回の取得が済んだか」。キーは型ごとの関数（booleanPreferencesKey）で作り、名前は保存されるキーそのもの
    suspend fun isInitialFetchDone(): Boolean = dataStore.data.first()[INITIAL_FETCH_DONE] ?: false

    // edit は、読み取り → 変更 → 書き込みを 1 つのトランザクションとして行う。保存が終わるまで中断する
    suspend fun markInitialFetchDone() {
        dataStore.edit { it[INITIAL_FETCH_DONE] = true }
    }

    private companion object {
        val INITIAL_FETCH_DONE = booleanPreferencesKey("initial_fetch_done")
    }
}
  • DataStore<Preferences> を、コンストラクタの引数で受け取ります。アプリでは本物の DataStore を、テストではメモリ上の偽物を渡します。
  • booleanPreferencesKey("initial_fetch_done") は、Boolean の値を入れるキーです。キーは型ごとの関数（stringPreferencesKey など）で作ります。"initial_fetch_done" が、ファイルに保存されるキーの名前そのものになります。
  • isInitialFetchDone() は、dataStore.data（保存した値の Flow）から first() で 1 回だけ読みます。キーがまだ無ければ null なので、?: false で「取得していない」とみなします。DataStore の KDoc でも、1 回だけ読むときは data.first() を使うように書かれています。
  • markInitialFetchDone() の edit は、読み取り → 変更 → 書き込みを 1 つのトランザクションとして行います。edit の中身は updateData で、KDoc には「データがディスクに保存されたときにコルーチンが完了する」とあります。edit から戻った時点で、ファイルへの保存は済んでいます。

印が無いのに DB に Todo がある場合

11 のアプリを使っていた端末に 12 を上書きで入れると、DB には Todo がありますが、印はまだありません。この場合は「取得せずに、印だけ付ける」ことにしました。理由は次の 3 つです。

  • API の一覧を取り込むと、insertAll（同じ id は置き換え）が、ユーザーが完了にした Todo や追加した Todo を API の値で上書きしてしまいます。
  • 11 までの端末では、最初の取得はもう済んでいます。印を付けるのが事実に合います。
  • 実装は if を 1 つ足すだけで済みます。
  • 取得後の保存と印の書き込みの間でプロセスが落ちた場合も、次の起動では取り直さずに印だけ付きます。

「印が無ければ必ず取得する」という書き方もできますが、上書きのおそれがあるので採りませんでした。この動きは、ステップ 3 のテスト existingTodosWithoutMark_areKeptAndMarked で確かめます。

SavedStateHandle を外した理由

絞り込みを DataStore と SavedStateHandle の両方に持つと、どちらが正しい値かを決める必要が出てきます。11 で一覧を DB だけに持つようにしたのと同じく、同じデータを 2 か所で持たないようにしました。

回転などで Activity が作り直されても、ViewModel は破棄されないので、絞り込みはそのまま残ります。既存の UI テストには、絞り込みが Activity の作り直しの後も残ることを確かめるものが 2 件あります。selectedFilter_survivesRecreation と filter_survivesActivityRecreation で、どちらも変更なしで通ります。ViewModel が作り直されないので、偽の DataStore も一緒に残るためです。

起動直後に「すべて」が一瞬見えないか

DataStore の最初の読み込みは非同期です。起動した直後、保存した絞り込み（たとえば「未完了」）が届くまでの間に、既定の「すべて」の一覧が一瞬見えないかが気になります。筆者は ViewModel に一時的にログ（Log.d）を入れて確かめました。保存した絞り込みが「未完了」（Active）の状態でアプリを強制終了して起動し、uiState の変化を記録しています（それぞれ 1 回の実測。ログのコードは完成コードに入っていません）。

// ViewModel の単体テスト（JVM 上。エミュレータは不要）。
// viewModelScope は Dispatchers.Main.immediate を使うが、JVM には Main が無いので、setMain でテスト用のディスパッチャーに差し替える
@OptIn(ExperimentalCoroutinesApi::class)
class TodoListViewModelTest {

    private val todos = listOf(
        Todo(1, "write"),
        Todo(2, "test", done = true),
        Todo(3, "ship"),
    )

    // setMain したら、テストのあとで必ず resetMain する（他のテストに差し替えが残らないように）
    @After
    fun tearDown() {
        Dispatchers.resetMain()
    }

    // 偽のサーバーは、渡されたディスパッチャーで動く。テスト用のディスパッチャーなら、応答までの待ち時間（delayMillis）は仮想時間になる
    private fun viewModel(
        settings: SettingsRepository = SettingsRepository(FakeDataStore()),
        dao: FakeTodoDao = FakeTodoDao(),
        responseDelayMillis: Long = 1_000L,
        dispatcher: CoroutineDispatcher,
    ) = TodoListViewModel(TodoRepository(dao, FakeTodoServer(todos, delayMillis = responseDelayMillis, dispatcher = dispatcher).api, settings), settings)

    // StandardTestDispatcher: launch した処理はキューに入るだけで、テスト側が進める（runCurrent / advanceTimeBy / advanceUntilIdle）まで動かない。
    // delay は仮想時間なので、待たずに時間だけ進められる
    @Test
    fun standardDispatcher_loadingFinishesWhenVirtualTimeAdvances() = runTest(StandardTestDispatcher()) {
        val dispatcher = StandardTestDispatcher(testScheduler)
        Dispatchers.setMain(dispatcher)
        val vm = viewModel(responseDelayMillis = 1_000L, dispatcher = dispatcher)

        // 作った直後: 読み込み中で、一覧は空
        assertTrue(vm.uiState.value.isLoading)
        assertEquals(emptyList<Todo>(), vm.uiState.value.todos)

        advanceTimeBy(999)
        runCurrent()
        assertTrue(vm.uiState.value.isLoading)

        advanceTimeBy(1)
        runCurrent()
        assertFalse(vm.uiState.value.isLoading)
        assertEquals(todos, vm.uiState.value.todos)
    }

    // 待ち時間が 0 でも、Standard では launch の中身は runCurrent するまで動かない
    @Test
    fun standardDispatcher_doesNotRunLaunchedWorkUntilTold() = runTest(StandardTestDispatcher()) {
        val dispatcher = StandardTestDispatcher(testScheduler)
        Dispatchers.setMain(dispatcher)
        val vm = viewModel(responseDelayMillis = 0L, dispatcher = dispatcher)

        assertTrue(vm.uiState.value.isLoading)

        runCurrent()
        assertFalse(vm.uiState.value.isLoading)
    }

    // UnconfinedTestDispatcher: launch した処理は、最初の中断点（delay など）まで、呼び出した場所でそのまま実行される
    @Test
    fun unconfinedDispatcher_runsLaunchedWorkEagerly() = runTest {
        val dispatcher = UnconfinedTestDispatcher(testScheduler)
        Dispatchers.setMain(dispatcher)
        val vm = viewModel(responseDelayMillis = 0L, dispatcher = dispatcher)

        // runCurrent なしで、もう読み込みが終わっている
        assertFalse(vm.uiState.value.isLoading)
        assertEquals(todos, vm.uiState.value.todos)
    }

    // StateFlow の値の変化を順に集める。collect は終わらないので backgroundScope で起動する（テストの最後に自動でキャンセルされる）。
    // StateFlow は値が変わったときだけ通知し、collect が追いつく前の途中の値は飛ばされる（conflation）。
    // 一覧が届いてから読み込み済みにするので、「一覧は入ったが、まだ読み込み中」の状態が途中に 1 つ入る（ViewModel の load を参照）
    @Test
    fun uiState_emitsLoadingThenLoadedThenToggled() = runTest {
        val dispatcher = StandardTestDispatcher(testScheduler)
        Dispatchers.setMain(dispatcher)
        val vm = viewModel(responseDelayMillis = 1_000L, dispatcher = dispatcher)
        val states = mutableListOf<TodoListUiState>()
        backgroundScope.launch(UnconfinedTestDispatcher(testScheduler)) { vm.uiState.toList(states) }

        advanceTimeBy(1_000)
        runCurrent()
        vm.toggleTodo(1, done = true)
        runCurrent()

        assertEquals(4, states.size)
        assertTrue(states[0].isLoading)
        assertEquals(emptyList<Todo>(), states[0].todos)
        assertTrue(states[1].isLoading)
        assertEquals(todos, states[1].todos)
        assertFalse(states[2].isLoading)
        assertFalse(states[2].todos.first { it.id == 1 }.done)
        assertTrue(states[3].todos.first { it.id == 1 }.done)
    }

    // 以降のテストは、読み込み済み（待ち時間 0 + Unconfined）の状態から始める
    private fun loadedViewModel(
        settings: SettingsRepository = SettingsRepository(FakeDataStore()),
        dao: FakeTodoDao = FakeTodoDao(),
    ): TodoListViewModel {
        val dispatcher = UnconfinedTestDispatcher()
        Dispatchers.setMain(dispatcher)
        return viewModel(settings, dao, responseDelayMillis = 0L, dispatcher = dispatcher)
    }

    @Test
    fun toggleTodo_changesOnlyThatTodo() {
        val vm = loadedViewModel()

        vm.toggleTodo(1, done = true)

        assertEquals(listOf(true, true, false), vm.uiState.value.todos.map { it.done })
    }

    @Test
    fun addTodo_appendsWithNextIdAndIgnoresBlank() {
        val vm = loadedViewModel()

        vm.addTodo("  buy milk  ")
        vm.addTodo("   ")

        assertEquals(4, vm.uiState.value.todos.size)
        assertEquals(Todo(4, "buy milk"), vm.uiState.value.todos.last())
    }

    @Test
    fun deleteTodo_thenRestoreTodo_putsItBackAtTheSameIndex() {
        val vm = loadedViewModel()
        val target = todos[1]

        vm.deleteTodo(target.id)
        assertEquals(listOf(1, 3), vm.uiState.value.todos.map { it.id })

        vm.restoreTodo(target)
        assertEquals(listOf(1, 2, 3), vm.uiState.value.todos.map { it.id })
    }

    @Test
    fun deleteDone_removesDoneTodos() {
        val vm = loadedViewModel()

        vm.deleteDone()

        assertEquals(listOf(1, 3), vm.uiState.value.todos.map { it.id })
    }

    @Test
    fun setFilter_changesFilterOnly() {
        val vm = loadedViewModel()

        vm.setFilter(TodoFilter.Done)

        assertEquals(TodoFilter.Done, vm.uiState.value.filter)
        assertEquals(todos, vm.uiState.value.todos)
    }

    // DB にすでに一覧があり、前回の絞り込みも保存されていれば、それをそのまま表示し、読み込み中にならない
    // （アプリの再起動を、中身のある DAO と、絞り込みを保存した設定を渡して再現する）
    @Test
    fun dbHasTodos_isShownWithoutLoading() = runTest {
        val settings = SettingsRepository(FakeDataStore())
        settings.setFilter(TodoFilter.Done)

        val vm = loadedViewModel(settings, FakeTodoDao(listOf(Todo(9, "saved", done = true))))

        assertFalse(vm.uiState.value.isLoading)
        assertEquals(listOf(Todo(9, "saved", done = true)), vm.uiState.value.todos)
        assertEquals(TodoFilter.Done, vm.uiState.value.filter)
    }

    // 一覧の変更は DAO に書かれ、設定（DataStore）に書かれるのは絞り込みだけ
    @Test
    fun updates_areWrittenToDao() = runTest {
        val settings = SettingsRepository(FakeDataStore())
        val dao = FakeTodoDao()
        val vm = loadedViewModel(settings, dao)

        vm.toggleTodo(1, done = true)
        vm.setFilter(TodoFilter.Active)

        assertEquals(3, dao.count())
        assertEquals(vm.uiState.value.todos, dao.observeAll().first().map { Todo(it.id, it.title, it.done) })
        assertTrue(vm.uiState.value.todos.first { it.id == 1 }.done)
        assertEquals(TodoFilter.Active, settings.filter.first())
    }

    // ---- 読み込みの失敗と再試行（偽のサーバーが失敗を返す） ----

    // 偽のサーバーと、それにつないだ ViewModel を作る。ディスパッチャーは Unconfined なので、応答は呼んだ場所でそのまま処理される
    private fun failingViewModel(
        dao: FakeTodoDao = FakeTodoDao(),
        configure: FakeTodoServer.() -> Unit,
    ): Pair<FakeTodoServer, TodoListViewModel> {
        val dispatcher = UnconfinedTestDispatcher()
        Dispatchers.setMain(dispatcher)
        val server = FakeTodoServer(todos, dispatcher = dispatcher).apply(configure)
        val settings = SettingsRepository(FakeDataStore())
        return server to TodoListViewModel(TodoRepository(dao, server.api, settings), settings)
    }

    @Test
    fun loadFailure_showsErrorAndStopsLoading() {
        val (_, vm) = failingViewModel { status = HttpStatusCode.NotFound }

        val state = vm.uiState.value
        assertFalse(state.isLoading)
        assertEquals("サーバーがエラーを返しました（HTTP 404）", state.errorMessage)
        assertEquals(emptyList<Todo>(), state.todos)
    }

    @Test
    fun loadFailure_messageDependsOnTheKindOfException() {
        val (_, network) = failingViewModel { error = IOException("boom") }
        assertEquals("ネットワークに接続できません", network.uiState.value.errorMessage)

        val (_, broken) = failingViewModel { rawBody = "[{" }
        assertEquals("データの形式が正しくありません", broken.uiState.value.errorMessage)

        val (_, unexpected) = failingViewModel { error = IllegalStateException("bug") }
        assertEquals("予期しないエラーが発生しました", unexpected.uiState.value.errorMessage)
    }

    // 例外の message（レスポンスの本文が入ることがある）は、画面に出す文言に混ぜない
    @Test
    fun loadFailure_doesNotLeakExceptionMessage() {
        val (_, vm) = failingViewModel { rawBody = "[{\"secret\": 1}]" }

        assertEquals("データの形式が正しくありません", vm.uiState.value.errorMessage)
    }

    // 失敗したときは、DB に何も書かない（印も付かないので、次の起動でも取得し直される）
    @Test
    fun loadFailure_leavesDaoEmpty() = runTest {
        val dao = FakeTodoDao()

        failingViewModel(dao = dao) { status = HttpStatusCode.InternalServerError }

        assertEquals(0, dao.count())
    }

    @Test
    fun retry_afterFailure_loadsTodos() {
        val (server, vm) = failingViewModel { status = HttpStatusCode.InternalServerError }
        assertEquals("サーバーがエラーを返しました（HTTP 500）", vm.uiState.value.errorMessage)

        server.status = HttpStatusCode.OK
        vm.retry()

        val state = vm.uiState.value
        assertFalse(state.isLoading)
        assertEquals(null, state.errorMessage)
        assertEquals(todos, state.todos)
        assertEquals(2, server.requestCount)
    }

    // 再試行は、失敗中にだけ効く。読み込み済みのときに呼んでも、取得し直さない
    @Test
    fun retry_whenNotFailed_doesNothing() {
        val (server, vm) = failingViewModel { }

        vm.retry()

        assertEquals(todos, vm.uiState.value.todos)
        assertEquals(1, server.requestCount)
    }

    // 再試行の途中（読み込み中）に、もう一度押されても、取得は 1 回だけ
    @Test
    fun retry_whileLoading_doesNotStartSecondRequest() = runTest {
        val dispatcher = StandardTestDispatcher(testScheduler)
        Dispatchers.setMain(dispatcher)
        val server = FakeTodoServer(todos, status = HttpStatusCode.InternalServerError, delayMillis = 1_000L, dispatcher = dispatcher)
        val settings = SettingsRepository(FakeDataStore())
        val vm = TodoListViewModel(TodoRepository(FakeTodoDao(), server.api, settings), settings)
        advanceTimeBy(1_000)
        runCurrent()
        assertEquals("サーバーがエラーを返しました（HTTP 500）", vm.uiState.value.errorMessage)

        server.status = HttpStatusCode.OK
        vm.retry()
        vm.retry()
        // loadState の変更が uiState に届くのは、combine がテスト用のディスパッチャーで動いてから
        runCurrent()
        assertTrue(vm.uiState.value.isLoading)
        advanceTimeBy(1_000)
        runCurrent()

        assertEquals(todos, vm.uiState.value.todos)
        assertEquals(2, server.requestCount)
    }

    // 取得の途中で ViewModel が破棄されると、viewModelScope がキャンセルされ、取得中のコルーチンも止まる。
    // これは失敗ではないので、失敗の表示（errorMessage）にしてはいけない（catch (e: Exception) で握りつぶさず、CancellationException は投げ直す）
    @Test
    fun cancellationDuringLoad_isNotTreatedAsFailure() = runTest(StandardTestDispatcher()) {
        val dispatcher = StandardTestDispatcher(testScheduler)
        Dispatchers.setMain(dispatcher)
        val vm = viewModel(responseDelayMillis = 1_000L, dispatcher = dispatcher)

        // 応答を待っている途中（1 秒のうち 0.5 秒）で、ViewModel の破棄と同じく viewModelScope をキャンセルする
        advanceTimeBy(500)
        runCurrent()
        vm.viewModelScope.cancel()
        advanceUntilIdle()

        assertEquals(null, vm.uiState.value.errorMessage)
    }

    // 印が無くても、DB に一覧があれば取得しない（11 から上書きで入れた場合）。通信の回数で確かめる
    @Test
    fun dbHasTodos_doesNotCallApi() {
        val (server, vm) = failingViewModel(dao = FakeTodoDao(listOf(Todo(9, "saved")))) { }

        assertEquals(0, server.requestCount)
        assertEquals(listOf(Todo(9, "saved")), vm.uiState.value.todos)
    }
}

// 「取得済み」の印（DataStore）で、初回の取得を 1 回だけにする判断のテスト。偽の DAO・偽のサーバー・偽の DataStore だけで動く
class TodoRepositoryTest {

    private val todos = listOf(Todo(1, "write"), Todo(2, "test", done = true))

    private val settings = SettingsRepository(FakeDataStore())
    private val server = FakeTodoServer(todos)

    // 取得済みの印があれば、DB が空でも取得しない（全件削除して再起動した場合）
    @Test
    fun fetchedMark_skipsFetchEvenWhenDbIsEmpty() = runTest {
        settings.markInitialFetchDone()
        val repository = TodoRepository(FakeTodoDao(), server.api, settings)

        assertEquals(0, repository.fetchInitialTodosIfNeeded())

        assertEquals(0, server.requestCount)
    }

    // 取得に成功したら保存して、印を付ける。2 回目は取得しない
    @Test
    fun successfulFetch_savesTodosAndMarksAsFetched() = runTest {
        val repository = TodoRepository(FakeTodoDao(), server.api, settings)

        assertEquals(2, repository.fetchInitialTodosIfNeeded())
        assertEquals(0, repository.fetchInitialTodosIfNeeded())

        assertTrue(settings.isInitialFetchDone())
        assertEquals(1, server.requestCount)
    }

    // 取得に失敗したら、印を付けない（再試行でもう一度取得できる）
    @Test
    fun failedFetch_doesNotMarkAsFetched() = runTest {
        server.status = HttpStatusCode.InternalServerError
        val repository = TodoRepository(FakeTodoDao(), server.api, settings)

        try {
            repository.fetchInitialTodosIfNeeded()
            fail("取得の失敗が例外で投げられるはず")
        } catch (_: Exception) {
            // 失敗は例外のまま投げられる（表示は ViewModel の仕事）
        }

        assertFalse(settings.isInitialFetchDone())
    }

    // 印が無くても DB に Todo があれば（印を付ける前の版で使っていた端末）、取得せずに印だけ付ける。API の一覧で上書きしないため
    @Test
    fun existingTodosWithoutMark_areKeptAndMarked() = runTest {
        val repository = TodoRepository(FakeTodoDao(listOf(Todo(9, "mine", done = true))), server.api, settings)

        assertEquals(0, repository.fetchInitialTodosIfNeeded())

        assertEquals(0, server.requestCount)
        assertTrue(settings.isInitialFetchDone())
    }
}
  • fetchedMark_skipsFetchEvenWhenDbIsEmpty: 印があれば、DB が空でも API を呼ばない（全件削除して起動し直した場合）。FakeTodoServer の requestCount で、API が呼ばれた回数を確かめます。
  • successfulFetch_savesTodosAndMarksAsFetched: 取得に成功したら 2 件を保存して印を付け、2 回目は取得しない。
  • failedFetch_doesNotMarkAsFetched: 取得に失敗したら（HTTP 500）、例外が投げられ、印は付かない。
  • existingTodosWithoutMark_areKeptAndMarked: 印が無くても DB に Todo があれば、取得せずに印だけ付ける（ステップ 1 の「印が無いのに DB に Todo がある場合」）。
  • どのテストも、偽の DAO・偽のサーバー・偽の DataStore だけで動きます。SettingsRepository は本物です。
💡

fail() は catch (_: Exception) に捕まらない

failedFetch_doesNotMarkAsFetched では、try の中で例外が出なければ fail(...) でテストを失敗させます。fail が投げるのは AssertionError で、Exception ではありません。そのため、catch (_: Exception) に飲み込まれず、テストはきちんと失敗します。

ViewModel の単体テストに、絞り込みの保存と復元のテストを 1 件足します。同じ設定（偽の DataStore）をつないだ新しい ViewModel を作ることで、アプリの再起動を再現します。

つまずきポイント

⚠️

There are multiple DataStores active for the same file で失敗する

同じファイル名の DataStore が 2 つ作られています。preferencesDataStore(name = "settings") を、クラスの中や複数のファイルに書いていないか確かめます。この項目では、AppContainer.kt のトップレベルに 1 回だけ書きます。

⚠️

ViewModel を作るところでアプリが落ちる

viewModel() の既定のファクトリは、引数なしのコンストラクタ（または SavedStateHandle だけを受け取るコンストラクタ）を探します。SavedStateHandle の引数を外したら、2 次コンストラクタも constructor() に変えます。

⚠️

保存した絞り込みを読むところで例外になる

TodoFilter.valueOf(保存した値) は、知らない名前で例外を投げます。保存した値は外から来るデータとして扱い、TodoFilter.entries.firstOrNull { it.name == 保存した値 } ?: TodoFilter.All で受けます。

⚠️

files/datastore が無い

DataStore のファイルは、最初の書き込み（edit）まで作られません。取得に失敗して印をまだ付けていない場合や、絞り込みを一度も変えていない場合は、ファイルが無くても正常です。

⚠️

全件削除して起動し直したのに、API の 20 件に戻らない

この項目の意図した動きです。「取得済み」の印があるので、DB が空でも API には行きません。最初の状態に戻したいときは、adb shell pm clear com.handson.android01 でアプリのデータ（DB と設定）を消します。

まとめ

Preferences DataStore を AppContainer のトップレベルに 1 つだけ作り、設定の読み書きを SettingsRepository にまとめました。 「最初の一覧を取得済み」の印を保存し、API に行くかどうかを DB の中身ではなく印で決めるようにしたので、全件削除して起動し直しても API から取り直しません。取得に失敗したときは印を付けず、再試行で取得できます。 絞り込みは SavedStateHandle から DataStore に移し、アプリを終了しても保たれるようにしました。起動直後は読み込み中の表示が出ているので、既定の「すべて」が見えることはありません。 テストでは DataStore<Preferences> の偽物を使い、SettingsRepository は本物のまま、設定ファイルを作らずに通ります。
