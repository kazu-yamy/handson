Room 3 でローカル保存

  • ⏱ 所要時間: 60分（任意の実験を除く）
  • 📊 難易度: 入門
  • 👤 対象: 10 で MockEngine のテストまで書いた人
  • 📋 前提: 10 で作ったプロジェクトがビルドでき、エミュレータ（Handson_Android36）を起動できること。エミュレータからインターネットに接続できること（最初の一覧の取得と、release の確認で使います）
  • 🔗 前提となる項目: 10: MockEngine でネットワークのテスト
  • 🧩 版: Kotlin 2.4.20 / AGP 9.4.1 / Compose BOM 2026.09.00 / Room 3.0.3（androidx.room3）/ KSP 2.3.12 / Ktor 3.6.0
  • 🌿 完成コード: ブランチ android/11-room

🎯 このレッスンで学ぶこと

  • Room 3 の Gradle プラグインと KSP を設定し、Entity・DAO・Database を書いて、DB のコードとスキーマ JSON を生成できる
  • DAO と API を束ねる Repository を作り、Room を唯一の情報源にして、DB が空のときだけ API から取得できる
  • ViewModel の状態を DB の Flow と combine・stateIn で組み立て、アプリを終了しても一覧の変更が残るようにできる
  • 偽の DAO を使い、既存の単体テストと UI テストを、本物の DB なしで通せる

概要

09 では、Web API から Todo の一覧を取得しました。10 では、その取得をテストしました。ただし、追加・完了の切り替え・削除は、ViewModel のメモリ上（と SavedStateHandle）で行っていただけです。アプリを終了すると変更は消え、次に起動したときは API の 20 件に戻っていました。

この項目では、Jetpack の DB ライブラリ Room 3 を使い、一覧を端末の SQLite のデータベース（DB）に保存します。アプリを終了しても、プロセスが強制終了されても、変更が残るようになります。

前提知識として、07 の ViewModel・StateFlow・SavedStateHandle を使います。09 の TodoApi・AppContainer と、10 の偽のサーバー（FakeTodoServer）も使います。SQL は SELECT・UPDATE・DELETE の 1 行の文を読める程度で十分です。

データの流れ

この項目では、Room を唯一の情報源にします。画面に出す一覧は、いつも DB から読みます。API は、DB が空のときに最初の一覧を取ってくるためだけに使います。

  1. 画面（TodoListPage）は、これまでどおり ViewModel の uiState を購読します。
  2. ViewModel は、次の 3 つを combine して uiState を作ります。DB の一覧（Flow）・絞り込み（SavedStateHandle）・読み込みの状態（ViewModel のメモリ）です。
  3. 起動したとき、DB が空なら、API から取得して DB に保存します。DB に一覧があれば、API には行きません。
  4. 追加・完了の切り替え・削除・元に戻す・完了済みの削除は、DB に書くだけです。DB が変わると、Room が新しい一覧を Flow に流し、2 の combine を通って画面に届きます。

Todo の一覧ViewModel のメモリと SavedStateHandle。起動のたびに API から取得DB（Room）。DB が空のときだけ API から取得して保存
追加・切り替え・削除ViewModel が一覧を書き換えるViewModel は DB に書くだけ。一覧は DB の Flow から届く

SavedStateHandle に残すのは絞り込みだけにします。一覧と完了の状態は DB が持つので、同じデータを 2 か所で持たないようにするためです。

ℹ️

この設計の限界（「DB が空のときだけ取得」）

API に行くかどうかは、DB が空かどうかだけで決めています。そのため、次の 2 つの限界があります。

  • 一覧を全件削除してから起動し直すと、DB が空なので、API から最初の 20 件を取り直します。ステップ 4 で実際に確かめます。
  • DB に一覧があれば API には行かないので、2 回目以降の起動では、サーバー側の変更は取り込まれません。

次の項目（12: DataStore で設定を保存）では、「最初の一覧を取得済み」という印を DataStore へ保存し、全件削除した後も取り直さないようにします。

Room 3 について

  • Room は、SQLite を使うための Jetpack のライブラリです。テーブルの 1 行を表すクラス（Entity）と、DB への操作を並べた interface（DAO）を書くと、実装のコードをビルド時に生成します。
  • Room 3 のパッケージと artifact は androidx.room3 です。Room 2 のパッケージは androidx.room で、名前が違います。Web の解説の多くは Room 2 の書き方なので、import を混ぜないように注意します。
  • コードの生成には KSP（Kotlin Symbol Processing）を使います。Room 3 では、kapt は使えず KSP だけです。
  • Room 3 の Gradle プラグインでは、スキーマ（テーブルの定義）を書き出す先 schemaDirectory の指定が必須です。

Kotlin app/src/main/java/com/handson/android01/data/TodoEntity.kt 
package com.handson.android01.data

import androidx.room3.Entity
import androidx.room3.PrimaryKey
import com.handson.android01.kotlin.Todo

// DB の 1 行（todos テーブルの 1 行）。画面で使う Todo とは別の型にして、DB の都合（autoGenerate など）を画面に持ち込まない。
// id = 0 のまま insert すると、Room が新しい id を振る
@Entity(tableName = "todos")
data class TodoEntity(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val title: String,
    val done: Boolean,
)

fun TodoEntity.toTodo(): Todo = Todo(id = id, title = title, done = done)

fun Todo.toEntity(): TodoEntity = TodoEntity(id = id, title = title, done = done)
  • @Entity(tableName = "todos") を付けたクラスが、todos テーブルになります。プロパティが列になります。
  • @PrimaryKey(autoGenerate = true) は、主キーの値を DB に振らせる指定です。id = 0 のまま挿入すると、新しい id が振られます。
  • 画面で使う Todo（02 で作り、07 で Parcelable にした型）とは別の型にします。autoGenerate のような DB の都合を画面の型に持ち込まないためです。toTodo() と toEntity() で相互に変換します。

2 つめは、DB への操作を並べた DAO です。interface を書くだけで、実装（TodoDao_Impl）は Room が KSP で生成します。

Kotlin app/src/main/java/com/handson/android01/data/TodoDao.kt 
package com.handson.android01.data

import androidx.room3.Dao
import androidx.room3.Insert
import androidx.room3.OnConflictStrategy
import androidx.room3.Query
import kotlinx.coroutines.flow.Flow

// DB への操作の一覧。interface を書くと、実装（TodoDao_Impl）を Room が KSP で生成する。
// Room 3 では、DAO の関数は suspend にする。変更を監視する関数だけは、Flow を返す（suspend は付けない）
@Dao
interface TodoDao {

    // テーブルが変わるたびに、最新の一覧を流し直す
    @Query("SELECT * FROM todos ORDER BY id")
    fun observeAll(): Flow<List<TodoEntity>>

    @Query("SELECT COUNT(*) FROM todos")
    suspend fun count(): Int

    // 同じ id の行があれば置き換える
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insert(todo: TodoEntity)

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(todos: List<TodoEntity>)

    @Query("UPDATE todos SET done = :done WHERE id = :id")
    suspend fun setDone(id: Int, done: Boolean)

    @Query("DELETE FROM todos WHERE id = :id")
    suspend fun deleteById(id: Int)

    @Query("DELETE FROM todos WHERE done = 1")
    suspend fun deleteDone()
}
  • observeAll() は Flow を返します。todos テーブルが変わるたびに、Room が SELECT をやり直し、最新の一覧を流します。ステップ 3 で、画面の一覧をこの Flow から作ります。Flow を返す関数には suspend を付けません。
  • それ以外の関数は suspend にします。DB の読み書きは時間がかかることがあるので、コルーチンの中から呼びます。
  • @Insert(onConflict = OnConflictStrategy.REPLACE) は、同じ主キーの行があれば置き換えます。削除の「元に戻す」で、同じ id の行を入れ直すのに使います。
  • @Query の中の :id や :done は、関数の引数が入る場所です。Boolean は SQLite では整数（0 / 1）で保存されるので、done = 1 は完了済みの行です。

3 つめは、DB 本体の定義です。

Kotlin app/src/main/java/com/handson/android01/data/AppDatabase.kt 
package com.handson.android01.data

import androidx.room3.Database
import androidx.room3.RoomDatabase

// DB 本体の定義。テーブルになる Entity の一覧と、スキーマの版（version）を書く。
// Entity を変えたら version を上げて、移行（Migration）を用意する
@Database(entities = [TodoEntity::class], version = 1)
abstract class AppDatabase : RoomDatabase() {
    abstract fun todoDao(): TodoDao
}

entities には、テーブルにする Entity を並べます。version はスキーマの版です。RoomDatabase を継承した抽象クラスにして、DAO を返す抽象関数を置きます。実装（AppDatabase_Impl）は、これも Room が生成します。

// Todo の入口。画面（ViewModel）は DAO と API を直接触らず、ここだけを使う。
// 唯一の情報源は Room。API は、DB が空のときに最初の一覧を取ってくるためだけに使う
class TodoRepository(
    private val dao: TodoDao,
    private val api: TodoApi,
) {
    // DB の一覧。変更のたびに最新の一覧が流れる
    val todos: Flow<List<Todo>> = dao.observeAll().map { list -> list.map { it.toTodo() } }

    // DB が空のときだけ、API から取得して保存する。失敗した場合は、例外をそのまま投げる（失敗の表示は ViewModel の仕事）
    suspend fun refreshIfEmpty() {
        if (dao.count() == 0) {
            dao.insertAll(api.fetchTodos().map { it.toEntity() })
        }
    }

    suspend fun add(title: String) = dao.insert(TodoEntity(title = title, done = false))

    suspend fun setDone(id: Int, done: Boolean) = dao.setDone(id, done)

    suspend fun delete(id: Int) = dao.deleteById(id)

    // 削除の「元に戻す」。同じ id で入れ直すので、一覧の同じ位置（id の順）に戻る
    suspend fun restore(todo: Todo) = dao.insert(todo.toEntity())

    suspend fun deleteDone() = dao.deleteDone()
}
  • todos は、DAO の observeAll() を、画面で使う Todo の一覧に変換した Flow です。
  • refreshIfEmpty() は、DB が空のときだけ API から取得して保存します。取得に失敗したときは、例外をそのまま投げます。失敗を画面にどう出すかは、これまでどおり ViewModel が決めます。
  • 「空なら取得して保存」の判断を ViewModel に入れないために、Repository を置きます。ViewModel から見ると、データの入口はここ 1 つです。
  • restore() は、削除した Todo を同じ id で入れ直します。一覧は id の順に並べて読むので、削除する前と同じ位置に戻ります。

// SavedStateHandle: プロセスが終了されても残したい値の入れ物。Activity の onSaveInstanceState の Bundle に保存され、

class TodoListViewModel(

    // 通信は Ktor のエンジンが別のスレッドで行うので、withContext は要らない

            try {
                val saved = repository.refreshIfEmpty()
                // DB に書いてから、Room が新しい一覧を Flow に流すまでには少し間がある（実測で約 50 ms）。

        }
    }

        if (loadState.value.errorMessage == null) return
        loadState.value = LoadState()
        load()
    }

    // 追加・切り替え・削除は、DAO に書くだけ。画面の一覧は、DB の変更が Flow で届いて更新される
    fun addTodo(title: String) {
        val trimmed = title.trim()
        if (trimmed.isEmpty()) return
        viewModelScope.launch { repository.add(trimmed) }
    }

    fun toggleTodo(id: Int, done: Boolean) {
        viewModelScope.launch { repository.setDone(id, done) }
    }

    fun deleteTodo(id: Int) {
        viewModelScope.launch { repository.delete(id) }
    }

    // 削除の「元に戻す」。同じ id で入れ直すと、一覧の並び（id の順）で、削除前の位置に戻る
    fun restoreTodo(todo: Todo) {
        viewModelScope.launch { repository.restore(todo) }
    }

    fun deleteDone() {
        viewModelScope.launch { repository.deleteDone() }
    }

    // 絞り込みだけは SavedStateHandle に残す（プロセスが終了されても残る）。書き込むと、上の getStateFlow を通って画面に届く
    fun setFilter(filter: TodoFilter) {
        savedStateHandle[KEY_FILTER] = filter
    }

    // 例外を、画面に出す文言にする。e.message はそのまま出さない（レスポンスの本文が入ることがある）
    private fun Exception.toUserMessage(): String = when (this) {
        // タイムアウトは IOException のサブクラスもあるので、IOException より先に調べる
        is HttpRequestTimeoutException, is ConnectTimeoutException, is SocketTimeoutException -> "通信がタイムアウトしました"
        is ResponseException -> "サーバーがエラーを返しました（HTTP ${response.status.value}）"
        is IOException -> "ネットワークに接続できません"
        is ContentConvertException, is SerializationException, is NoTransformationFoundException -> "データの形式が正しくありません"
        else -> "予期しないエラーが発生しました"
    }

    private companion object {
        const val KEY_FILTER = "filter"
    }
}

  • LoadState は、読み込み中かどうかと失敗の文言です。DB には入らない画面だけの状態なので、ViewModel のメモリだけに持ちます。
  • uiState は、3 つの Flow を combine して作ります。DB の一覧（repository.todos）・絞り込み（savedStateHandle.getStateFlow）・loadState です。どれかが変わるたびに TodoListUiState が作り直されます。

WhileSubscribed にしない理由

stateIn の開始には、画面が購読している間だけ動かす SharingStarted.WhileSubscribed(5_000) もよく使われます。ただし、購読者がいないと .value が初期値のままになります。この項目の単体テストは vm.uiState.value を直接読むので、既存のテストを変えずに済む Eagerly を選びました。

初回取得の直後に空の一覧が見える問題

load() の中に、次の 1 行があります。

テストを偽の DAO に合わせる

既存のテストは、本物の Room を使わず、偽の DAO で動かします。本物の Room は、書き込みと、その後のクエリのやり直しを Dispatchers.IO のスレッドで行います。このスレッドは、Compose の UI テストが待ってくれる対象に入りません。操作の直後に表示を確かめている既存の UI テストの多くで、待ち合わせが必要になり、不安定になります。DAO は interface なので、09 で TodoApi にエンジンを渡せるようにしたのと同じように、偽物を手で書けます。

    override fun observeAll(): Flow<List<TodoEntity>> = rows.map { list -> list.sortedBy { it.id } }

    // id が 0 なら、今の最大値 + 1 を振る。同じ id があれば置き換える（REPLACE）
    override suspend fun insert(todo: TodoEntity) {
        rows.update { list ->
            val saved = if (todo.id == 0) todo.copy(id = (list.maxOfOrNull { it.id } ?: 0) + 1) else todo
            list.filterNot { it.id == saved.id } + saved
        }
    }

    override suspend fun insertAll(todos: List<TodoEntity>) = todos.forEach { insert(it) }

    override suspend fun setDone(id: Int, done: Boolean) {
        rows.update { list -> list.map { if (it.id == id) it.copy(done = done) else it } }
    }

    override suspend fun deleteById(id: Int) {
        rows.update { list -> list.filterNot { it.id == id } }
    }

    override suspend fun deleteDone() {
        rows.update { list -> list.filterNot { it.done } }
    }
}
  • メモリ上の行の一覧を MutableStateFlow に入れて、本物の DAO と同じ関数を実装します。observeAll() は、その Flow を id の順に並べて返します。
  • どの関数も中断せずに値を書き換えます。そのため、テストで書き込んだ直後に結果を確かめられます。
  • initial で、「DB にすでに入っている」状態から始められます。アプリの再起動を再現するのに使います。
  • insert は、id が 0 なら「今の最大値 + 1」を振ります。本物の DB（AUTOINCREMENT）は、削除した最大の id を再利用しない点が違いますが、既存のテストの期待値には影響しません。

まとめ

Room 3 の Gradle プラグインと KSP を設定し、Entity・DAO・Database を書きました。DAO と Database の実装は、Room が KSP で生成します。スキーマは JSON に書き出し、コミットしておきます。 TodoRepository を置いて Room を唯一の情報源にし、API は DB が空のときにだけ使うようにしました。ViewModel は DB の Flow・絞り込み・読み込みの状態を combine して uiState を作ります。追加や削除は DAO に書くだけで、画面は Flow で更新されます。アプリを強制終了しても変更が残り、2 回目以降は機内モードでも一覧が出ます。ただし、全件削除すると次の起動で API の一覧を取り直し、サーバー側の変更は取り込みません。テストは偽の DAO を使い、本物の DB とネットワークを使わずに通ります。

次の項目（12: DataStore で設定を保存）では、絞り込みなどの設定を DataStore に保存し、アプリを再起動しても保たれるようにします。「最初の一覧を取得済み」の印も DataStore へ保存し、全件削除した後も API から取り直さないようにします。
