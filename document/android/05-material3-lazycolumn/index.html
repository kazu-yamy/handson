Material3 と LazyColumn

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: 04 で状態と State hoisting を実装した人
  • 📋 前提: 04 で作ったプロジェクトがビルドでき、エミュレータ（Handson_Android36）を起動できること
  • 🔗 前提となる項目: 04: 状態と State hoisting

🎯 このレッスンで学ぶこと

  • Column を LazyColumn に置き換え、画面に見えている行だけが compose されることを確かめられる
  • rememberLazyListState と derivedStateOf で、スクロール位置に応じてボタンを出し分けられる
  • Scaffold のスロット（FAB・Snackbar）を使い、削除と「元に戻す」を実装できる
  • Snackbar をイベントから scope.launch で出す理由を、LaunchedEffect との違いで説明できる

概要

04 の Todo 一覧は、Column の中で forEachIndexed を回して全件の行を並べていました。3 件なら問題ありませんが、件数が増えると、画面に入らない行まで全部 compose されます。 この項目では一覧を LazyColumn に置き換えます。さらに Material3 の Scaffold のスロットを使って、スクロール位置に応じて出す「先頭へ」ボタンと、削除と取り消しを付けます。 スワイプ削除・セクション分けと絞り込み・追加用のボトムシートと確認ダイアログは、次の項目（06）で扱います。

Column と LazyColumn の違い

ColumnLazyColumn
子の書き方Composable を並べて書く（ループも普通の Kotlin）item { } / items(リスト) { } の DSL で書く
compose される範囲全部の子（画面に入らない分も）画面に見えている行だけ。スクロールで見えた行が新しく compose される
スクロールModifier.verticalScroll を付けたときだけ最初からスクロールできる。位置は LazyListState で読み書きする
行と状態の対応書いた順（呼び出し位置）既定は位置。key を渡すと、その値（ここでは Todo の id）で対応付ける

ステップ 1 で、1000 件のデータに対して実際に何行が compose されるかを数えて確かめます。

この項目で使う Material3 のコンポーネント

Material3 には、Material Design 3 に沿った部品がまとまっています。この項目で使う部品と、@OptIn(ExperimentalMaterial3Api::class) が必要かどうかを示します。opt-in の要否は、@OptIn を外してビルドしたときのエラーで確かめました（Material3 1.4.0）。

  • LazyColumn { ... }: 中括弧の中は Composable ではなく、行の並びを指定する DSL です。items(todos) { todo -> ... } で、リストの要素ごとに行の UI を書きます。

  • contentPadding = PaddingValues(16.dp): リストの内側（先頭の上・末尾の下・左右）に余白を付けます。
  • verticalArrangement = Arrangement.spacedBy(8.dp): 行と行の間を 8dp 空けます。区切り線の代わりに、行ごとの Card と間隔で区切ります。
  • Modifier.weight(1f): 外側の Column の中で、ほかの部品が使った残りの高さを全部使います。LazyColumn には、このように高さの上限を決めて渡す必要があります（後の実験 2）。
  • testTag("todo_list"): UI テストで一覧をスクロールさせるための目印です。
⚠️

入力欄をリストの下に置くと、キーボードで画面が押し上げられる

最初は 04 と同じ「サマリ → 一覧 → 入力欄」の順のまま LazyColumn にしました。一覧が weight(1f) で残りの高さを使い切るので、入力欄は画面の一番下に来ます。この状態で UI テストの performTextInput を行うと、キーボードが出てウィンドウ全体が上に押し上げられました。その結果、画面上部のサマリが表示範囲から外れました。04 の TodoListPageTest のうち 2 件が、次のメッセージで失敗しました。

Assert failed: The component with Text + InputText + EditableText contains '4 件中 2 件完了' (ignoreCase: false) is not displayed!

そこで入力欄とボタンをリストより上に移し、リストを最後に置きました。テストコードは変えていません。入力欄は、次の項目（06）で画面からボトムシートの中へ移します。

実験 1: 1000 件のうち、何行が compose されるか

LazyColumn が見えている行だけを compose することを確かめます。一時的に、MainActivity のデータを demoTodos(1000) にします。items の中には SideEffect { Log.d("LazyDemo", "compose todo ${todo.id}") } を入れ、行が compose されるたびに Logcat へ出します（android.util.Log と androidx.compose.runtime.SideEffect の import も足します）。インストールして起動し、ログを数えます。

一覧の作り方起動直後に compose された行
LazyColumn + items8 件
Column + verticalScroll + forEach1000 件（全件）

確かめたら、SideEffect のログを外し、データを demoTodos(20) に戻します。

実験 2: verticalScroll の Column に入れるとクラッシュする

外側の Column に .verticalScroll(rememberScrollState()) を足し、LazyColumn の weight(1f) を外して起動します。アプリは起動直後に落ちます。

Terminal 
$ adb logcat -d -b crash | grep IllegalStateE AndroidRuntime: java.lang.IllegalStateException: Vertically scrollable component was measured with an infinity maximum height constraints, which is disallowed. One of the common reasons is nesting layouts like LazyColumn and Column(Modifier.verticalScroll()). If you want to add a header before the list of items please add a header as a separate item() before the main items() inside the LazyColumn scope. There could be other reasons for this to happen: your ComposeView was added into a LinearLayout with some weight, you applied Modifier.wrapContentSize(unbounded = true) or wrote a custom layout. Please try to remove the source of infinite constraints in the hierarchy above the scrolling container.

スクロールする Column の中では、子の高さの上限が無限になります。LazyColumn は「画面にどこまで入るか」を決められず、例外を投げます。メッセージにあるとおり、一覧の上に置く見出しなども一緒にスクロールさせたいときは、外側をスクロールさせずに item { ... } で LazyColumn の中に入れます。確かめたら元に戻してください。

        setScreen(1000)

        val count = composeTestRule.onAllNodesWithTag("todo_row").fetchSemanticsNodes().size
        assertTrue("compose された行数: $count", count in 1..50)
    }

    @Test
    fun offscreenItem_isNotFoundUntilScrolled() {
        setScreen(1000)

        // 画面外の行はセマンティクスツリーに無い
        composeTestRule.onAllNodesWithText("Task 500").assertCountEquals(0)
    }

    @Test
    fun performScrollToIndex_showsTheItem() {
        setScreen(1000)

        composeTestRule.onNodeWithTag("todo_list").performScrollToIndex(500)

        composeTestRule.onNodeWithText("Task 501").assertIsDisplayed()
    }

    @Test
    fun performScrollToNode_showsTheItemMatchingTheCondition() {
        setScreen(1000)

        composeTestRule.onNodeWithTag("todo_list").performScrollToNode(hasText("Task 900"))

        composeTestRule.onNodeWithText("Task 900").assertIsDisplayed()
    }

実験: derivedStateOf が効く場面

04 のステップ 5 では、完了件数のように「元の State が変わるたびに結果も変わる」値には、derivedStateOf の効果が無いことを見ました。スクロール位置は、その反対の例です。

一時的に、FAB スロットの先頭に SideEffect { Log.d("ToTop", ...) } を入れ、スロットが compose された回数を Logcat に出しました。1000 件のデータで起動し、adb shell input swipe 540 1800 540 600 300 で 1 秒おきに 3 回スクロールして数えた結果です。

書き方スロットが compose された回数
A: val showToTop by remember { derivedStateOf { listState.firstVisibleItemIndex > 0 } } を読む1 回
B: スロットの中で listState.firstVisibleItemIndex > 0 を直接読む数十回（実測 7〜35 回。端末の描画速度で変わる）
A の場合 
$ adb logcat -d -s ToTopD ToTop   : fab slot composed, showToTop=true

A では、最初のスクロールで結果が false から true に変わったときの 1 回だけです。B の回数は、スクロール中に何フレーム描画されたかで変わり、同じ手順でも 7 回のときと 35 回のときがありました。B では、結果は true のまま変わらないのに、firstVisibleItemIndex が変わるたびにスロットが compose し直されました。「頻繁に変わる値から、たまにしか変わらない結果を作る」場面が、derivedStateOf の使いどころです。確かめたら、ログとデータを元に戻します。

実験: Snackbar を LaunchedEffect で出すと

LaunchedEffect(キー) は、コンポジションに入ったときと、キーの値が変わったときに、中の処理を実行する仕組みです。削除した題名を State に入れ、それをキーにして Snackbar を出す、次のような書き方を一時的なテストで試しました（抜粋）。

Kotlin 悪い例（実験用。完成コードには含まれません） 
var deleted by rememberSaveable { mutableStateOf<String?>(null) }
LaunchedEffect(deleted) { deleted?.let { host.showSnackbar("deleted $it") } }

ボタンを押して deleted = "a" にし、"deleted a" の Snackbar の数を Logcat に出しました。最後の 2 行は、StateRestorationTester で画面回転と同じ作り直しをした前後です。

Logcat 
D DBG : after 1st click: 1D DBG : after 10s: 0D DBG : after 2nd click: 0D DBG : before restore: 0D DBG : after restore: 1
操作Snackbar の数起きたこと
1 回目のクリック1表示される
10 秒進める0時間で消える
同じ題名でもう一度クリック0キーの値が "a" のまま変わらないので、LaunchedEffect が動かない
画面の作り直し（回転）0 → 1作り直しでコンポジションに入り直すので、保存されたキーのまま LaunchedEffect が動き直し、消えたはずの Snackbar がもう一度出る

状態をキーにすると、「同じ操作の 2 回目が出ない」「回転で二重に出る」という不具合になります。イベントのコールバックから scope.launch で出せば、どちらも起きません。

以下のチェックリストを使って、このレッスンの内容を振り返りましょう。

つまずきポイント

⚠️

LazyColumn をスクロールする Column に入れる

Column(Modifier.verticalScroll(...)) の中に LazyColumn を置くと、IllegalStateException でクラッシュします。メッセージは Vertically scrollable component was measured with an infinity maximum height constraints で始まります。外側のスクロールを外して LazyColumn に weight(1f) などで高さを渡し、一緒にスクロールさせたい部品は item { } で LazyColumn の中に入れます。

⚠️

UI テストで画面外の行が見つからない

LazyColumn は画面外の行を compose しないので、onNodeWithText("Task 500") のような検索は、スクロールするまで見つかりません。onNodeWithTag("todo_list") に performScrollToIndex(n) か performScrollToNode(hasText(...)) を呼んでから探します。

⚠️

Snackbar を LaunchedEffect で出す

削除した題名などの State をキーにして LaunchedEffect で Snackbar を出すと、同じ値での 2 回目の操作では出ず、画面回転の後には二重に出ました（ステップ 3 の実験）。ボタンが押されたときのようなイベントには、rememberCoroutineScope() のスコープで launch して showSnackbar を呼びます。

⚠️

入力欄を画面の下に置くと、キーボードで画面が押し上げられる

weight(1f) の一覧の下に入力欄を置くと、入力欄へフォーカスしたときにキーボードがウィンドウ全体を押し上げます。上部の部品は画面から外れます（ステップ 1）。この項目では、入力欄を一覧より上に置いて避けました。

⚠️

testTag を付けたノードに assertTextContains が効かない

Modifier.testTag を付けた Row などは、子のテキストをまとめていないので、自身にはテキストがありません。行の中の文字は assert(hasAnyDescendant(hasText(...))) で確かめます（ステップ 3）。

まとめ

04 の Column の一覧を LazyColumn に置き換え、1000 件のうち画面に見えている 8 件だけが compose されることを確かめました。 rememberLazyListState と derivedStateOf でスクロール位置から「先頭へ」ボタンを出し分けました。スロットの再コンポーズが、derivedStateOf 無しの数十回（実測 7〜35 回）から 1 回に減ることも実測しました。 Scaffold のスロットに FAB と SnackbarHost を置き、削除と「元に戻す」をイベントから scope.launch で実装しました。 次の項目（06: Material3 の画面部品）では、この一覧にスワイプでの削除、スクロールしても上端に残るセクション見出しと絞り込み、追加用のボトムシートと確認ダイアログを足します。
