概要

13 までのアプリの処理は、画面を開いている間だけ動きます。この項目では、アプリを閉じていても動くバックグラウンドの処理を、WorkManager で作ります。

WorkManager に作業を予約すると、WorkManager は予約を自分の DB に記録し、OS の JobScheduler にジョブとして登録します。条件がそろうと、OS がアプリのプロセスを起動して（終了していても）、Worker を動かします。作業の本体は Worker というクラスに書きます。

WorkManager が向いている処理

例この項目では
向いているアプリを閉じても、条件（ネットワーク・電池など）がそろったときに確実に実行したい作業。失敗したら時間をおいてやり直したい作業（サーバーへのデータ送信など）Todo 一覧のバックアップに使う
向いているすぐに始めて、すぐに終えたい作業（ユーザーの操作をきっかけにした送信など）。expedited work（優先して実行する作業）として依頼します扱わない（API 31 未満では通知が必要なため）
向いていない決まった時刻に実行したい処理（「毎日 9 時」など）。時刻が要るなら AlarmManager の領分です扱わない
向いていない画面が出ている間だけ動けばよい処理（一覧の読み込みなど）。画面を離れたら止めてよいので、コルーチン（viewModelScope）で書きますTodoListViewModel で使っている

1 日周期の作業は、「毎日決まった時刻」ではなく「1 日に 1 回くらい、条件がそろったとき」に動きます。端末が省電力の状態（Doze）にある間や、アプリの使用頻度による制限（App Standby）によっては、さらに後ろへずれます。

この項目の題材: Todo 一覧の定期バックアップ

端末の Todo 一覧を、1 日に 1 回サーバーへ送ってバックアップします。09〜13 では「最初の一覧だけを API から取得し、以後は端末の DB（Room）が正」という方針で作ってきました。バックアップは端末から送るだけで、サーバーからは何も取り込まないので、この方針と矛盾しません。

  • 送信先は、09 から使っている練習用の API（JSONPlaceholder）の POST https://jsonplaceholder.typicode.com/todos です。Todo の配列を送ると 201 Created を返しますが、実際には保存されません。送信と応答までは本物の API と同じです。
  • 送るのは Todo の一覧（番号・タイトル・完了したかどうか）だけです。API の形に合わせて userId を 1 に固定して付けます。
  • 条件は「ネットワークにつながっている」と「電池残量が少なくない」の 2 つです。通信の失敗やサーバーのエラー（5xx）では、時間をおいてやり直します。
  • 最後に送った時刻は DataStore に残し、一覧の上部に「最終バックアップ: 10/4 12:00」の形で出します。
  • バックアップから復元する機能は作りません。
⚠️

公開 API へ 1 日 1 回送信される

この項目のアプリ（debug 版も含む）を入れた端末は、1 日に 1 回、JSONPlaceholder へ Todo の一覧を送ります。ハンズオンが終わったら、最後のステップでアプリをアンインストールします。

既定の初期化を外す

Worker を書く

Kotlin app/src/main/java/com/handson/android01/work/TodoBackupWorker.kt 
package com.handson.android01.work

import android.content.Context
import androidx.hilt.work.HiltWorker
import androidx.work.CoroutineWorker
import androidx.work.WorkerParameters
import com.handson.android01.data.TodoRepository
import dagger.assisted.Assisted
import dagger.assisted.AssistedInject
import kotlin.coroutines.cancellation.CancellationException

// バックグラウンドで 1 回分のバックアップを行う Worker。
// @HiltWorker + @AssistedInject: Context と WorkerParameters は WorkManager が実行のたびに渡し（@Assisted）、
// それ以外（TodoRepository）は Hilt が組み立てて渡す。作るのは TodoApplication で設定した HiltWorkerFactory
@HiltWorker
class TodoBackupWorker @AssistedInject constructor(
    @Assisted appContext: Context,
    @Assisted params: WorkerParameters,
    private val repository: TodoRepository,
) : CoroutineWorker(appContext, params) {

    // CoroutineWorker の doWork はメインスレッドの外（既定では Dispatchers.Default）で動く。
    // 戻り値で、WorkManager に結果を伝える（success / failure / retry）
    override suspend fun doWork(): Result = try {
        repository.backupTodos()
        Result.success()
    } catch (e: CancellationException) {
        // 条件を満たさなくなったときなど、WorkManager に止められると、コルーチンがキャンセルされる。握りつぶさない
        throw e
    } catch (e: Exception) {
        Result.failure()
    }
}
  • Worker は CoroutineWorker を継承し、suspend fun doWork() に作業を書きます。suspend の Repository をそのまま呼べます。
  • doWork の戻り値で、WorkManager に結果を伝えます。Result.success()（成功）・Result.failure()（失敗。やり直さない）・Result.retry()（時間をおいてやり直す。ステップ 3 で使う）の 3 種類です。
  • @HiltWorker と @AssistedInject で、Hilt から部品を受け取ります。@Assisted を付けた Context と WorkerParameters は、WorkManager が実行のたびに渡します。それ以外の引数（TodoRepository）は、Hilt が組み立てて渡します。
  • CancellationException は握りつぶさずに投げ直します。条件を満たさなくなったときなどに WorkManager が作業を止めると、コルーチンのキャンセルとして届くためです。

予約の窓口を書く

Kotlin app/src/main/java/com/handson/android01/work/TodoBackupScheduler.kt 
package com.handson.android01.work

import android.content.Context
import androidx.work.ExistingWorkPolicy
import androidx.work.OneTimeWorkRequestBuilder
import androidx.work.WorkManager
import dagger.hilt.android.qualifiers.ApplicationContext
import javax.inject.Inject

// バックアップの予約の窓口。WorkManager への登録をここにまとめる
class TodoBackupScheduler @Inject constructor(@ApplicationContext private val context: Context) {

    // WorkManager.getInstance は、初回に TodoApplication.workManagerConfiguration を読んで初期化する。
    // コンストラクタで取ると、TodoApplication への注入の途中で読まれる。今は workerFactory が先に注入されるので問題ないが、
    // フィールドの宣言の順に頼ることになるので、使うときに取る
    private val workManager: WorkManager get() = WorkManager.getInstance(context)

    // 1 回だけのバックアップ。同じ名前の作業が待ち・実行中なら、新しく入れない（KEEP）。
    // 終わった作業は数えないので、起動のたびに 1 回動く
    fun backupOnce() {
        val request = OneTimeWorkRequestBuilder<TodoBackupWorker>().build()
        workManager.enqueueUniqueWork(UNIQUE_NAME, ExistingWorkPolicy.KEEP, request)
    }

    companion object {
        const val UNIQUE_NAME = "todo-backup"
    }
}
  • OneTimeWorkRequestBuilder で、1 回だけの作業の依頼を作ります。
  • enqueueUniqueWork は、名前（todo-backup）を付けて予約します。ExistingWorkPolicy.KEEP は、同じ名前の作業が待ちか実行中なら、新しく入れません。終わった作業は数えないので、このステップでは起動のたびに 1 回動きます。
ℹ️

WorkManager をコンストラクタで取らない理由

WorkManager.getInstance は、初回に TodoApplication の workManagerConfiguration を読んで初期化します。Hilt は super.onCreate() の中で、TodoApplication のフィールドを宣言の順（workerFactory → backupScheduler）に注入します。TodoBackupScheduler のコンストラクタで getInstance を呼ぶと、backupScheduler の注入中に設定が読まれます。このコードでは workerFactory が先に注入されているので、問題は起きません。ただし、これはフィールドの宣言の順に頼った書き方です。順を入れ替えると、まだ注入されていない workerFactory を読み、lateinit のプロパティが初期化されていないという例外になりえます。そこで、使うたびに取る get() の形にしました。筆者は逆の書き方での失敗は試していません。

同じ理由で、WorkManager を @Provides で提供することもしていません。

ℹ️

最初の 1 回は、登録の直後に動く

1 日周期でも、最初の 1 回目は、条件がそろえば登録の直後に動きました（1 日後ではありません）。2 回目以降は、前の実行から約 1 日後です。Result.failure() を返しても、Periodic の作業は次の周期にまた動きます。retry() は、同じ周期の中でのやり直しです。

am force-stop すると予約が消える

am force-stop（強制停止）すると、アプリは停止状態になり、JobScheduler のジョブも消えます。筆者の環境では、adb shell am force-stop com.handson.android01 の後、dumpsys jobscheduler にこのアプリのジョブがありませんでした。次にアプリを起動すると、約 24 時間後の TIMING_DELAY 付きのジョブが戻りました。WorkManager の記録は残っているので、起動したときに登録し直されます。端末を再起動した場合は、WorkManager の RescheduleReceiver が起動完了の通知（BOOT_COMPLETED）を受けて登録し直します。アプリを開かなくても予約が戻ります（筆者は再起動では試していません）。「アプリを終了しても動くか」は、am force-stop ではなく am kill で確かめます。

まとめ

Todo 一覧を 1 日 1 回サーバーへ送るバックアップを、WorkManager で作りました。 WorkManager の既定の初期化を外し、TodoApplication の Configuration.Provider で HiltWorkerFactory を渡しました。これで、@HiltWorker の Worker が Hilt の TodoRepository を受け取れます。 予約には「ネットワークにつながっている」「電池が少なくない」の条件と、30 秒から倍になるバックオフを付けました。4xx はあきらめ、通信の失敗と 5xx は 3 回までやり直します。 enqueueUniquePeriodicWork と KEEP で、起動のたびに呼んでも予約は 1 つのままです。アプリのプロセスを終了していても、条件がそろうと OS がアプリを起動して Worker を実行しました。 送った時刻は DataStore に残し、ViewModel の combine を通して一覧の上部に出しています。

次の項目（15: テストの仕上げ）では、13 から持ち越した Hilt のテストの書き方（@UninstallModules・@BindValue・hiltRule.inject()）を使います。この項目の Worker も、hiltRule.inject() で注入した HiltWorkerFactory で、Hilt の組み立てごとテストします。あわせて、本物の Room と DataStore のファイルを使うテストと、カバレッジの測り方を扱います。リリースビルドと署名は 16 で扱います。
