MockEngine でネットワークのテスト

  • ⏱ 所要時間: 60分
  • 📊 難易度: 入門
  • 👤 対象: 09 で API からの取得と失敗表示を作った人
  • 📋 前提: 09 で作ったプロジェクトがビルドでき、エミュレータ（Handson_Android36）を起動できること。インターネットへの接続は、最後の release の確認でだけ使います
  • 🔗 前提となる項目: 09: Ktor と serialization で API 取得
  • 🧩 版: Kotlin 2.4.20 / AGP 9.4.1 / Compose BOM 2026.09.00 / Ktor 3.6.0（ktor-client-mock）/ kotlinx-coroutines-test 1.11.0
  • 🌿 完成コード: ブランチ android/10-mockengine-testing

🎯 このレッスンで学ぶこと

  • MockEngine に応答を登録し、アプリと同じ設定の HttpClient で TodoApi の成功・HTTP エラー・壊れた JSON・タイムアウトをテストできる
  • MockEngine のハンドラーで、送られたリクエスト（メソッドと URL）を確かめられる
  • テスト用のディスパッチャーを MockEngine に渡し、ViewModel の失敗・再試行・キャンセルを仮想時間でテストできる
  • 失敗表示と「再試行」の流れを、ネットワークに出ない UI テストで確かめられる

概要

09 では、Ktor Client で Web API から Todo の一覧を取得し、失敗したときにエラーの文言と「再試行」を出しました。既存のテストは、Ktor のテスト用エンジン MockEngine を使った偽のサーバー（FakeTodoServer）につなぎ替えました。ただし、新しいテストはまだ足していません。この項目では、その偽のサーバーと MockEngine を使って、取得の成功と失敗のテストを書きます。

前提知識として、07 のテスト用ディスパッチャー（runTest・StandardTestDispatcher・UnconfinedTestDispatcher）を使います。09 で作った TodoApi・createTodoHttpClient・TodoListViewModel の retry() も使います。

本物の API に対してテストしない理由

09 のアプリは、外部の練習用 API（JSONPlaceholder）から取得します。テストでこの API を直接呼ぶと、次の問題があります。

  • 結果が、外部のサービスの状態とネットワークに左右されます。テストのコードが正しくても、相手の都合で落ちることがあります。
  • 失敗の場合を再現できません。404・500・壊れた JSON・応答が返ってこない、といった場合を、本物の API に好きなときに起こさせることはできません。
  • 通信を待つぶん遅くなります。たとえば応答が来ない場合のテストを本物で書くと、09 で設定した 15 秒の上限まで待つことになります。

そこで、通信そのものを偽物に置き換えます。Ktor Client は、実際に通信する部分を「エンジン」として差し替えられます（09 の「エンジンに Android エンジンを選んだ理由」）。MockEngine は、ネットワークへ出ずに、テストで決めたレスポンスを返すエンジンです。

09 の createTodoHttpClient(engine, requestTimeoutMillis) は、エンジンを引数で受け取る形にしてあります。アプリは Android エンジンを渡し、テストは MockEngine を渡します。違うのはエンジンだけです。ContentNegotiation（JSON の変換）・expectSuccess（ステータスの検査）・HttpTimeout の設定は、アプリと同じものがテストでも効きます。テスト用に別の設定を作ると、アプリの設定が壊れてもテストでは気づけません。同じ関数を通すことで、それを防ぎます。

TodoApi を MockEngine でテストする

MockEngine に応答を登録し、その HttpClient を使う TodoApi の単体テストを書きます。JVM 上で動き、エミュレータとネットワークは使いません。app/src/test/java/com/handson/android01/ の下に data フォルダを作り、TodoApiTest.kt を新しく作ります。このステップのコードは、5 つのブロックを上から順に、空行を 1 行ずつ挟んでつなげると 1 つのファイルになります。最初のブロックは、テストの準備と、成功時のテスト 2 件です。

// TodoApi の単体テスト（JVM 上。ネットワークには出ない）。MockEngine が、決めたレスポンスを返す。
// createTodoHttpClient を通すので、本番と同じ JSON の設定・ステータスの検査・タイムアウトが効く
class TodoApiTest {

    private val json = headersOf(HttpHeaders.ContentType, ContentType.Application.Json.toString())

    private val body = """
        [
          {"userId": 1, "id": 1, "title": "delectus aut autem", "completed": false},
          {"userId": 1, "id": 2, "title": "quis ut nam", "completed": true}
        ]
    """.trimIndent()

    private fun api(
        requestTimeoutMillis: Long = 15_000L,
        handler: suspend MockRequestHandleScope.(HttpRequestData) -> HttpResponseData,
    ) = TodoApi(createTodoHttpClient(MockEngine(handler), requestTimeoutMillis))

    @Test
    fun fetchTodos_decodesJsonIntoTodos() = runTest {
        val api = api { respond(body, HttpStatusCode.OK, json) }

        val todos = api.fetchTodos()

        assertEquals(listOf(Todo(1, "delectus aut autem", done = false), Todo(2, "quis ut nam", done = true)), todos)
    }

    // 送ったリクエストは、MockEngine の中で確かめられる
    @Test
    fun fetchTodos_sendsGetToTodosWithLimit() = runTest {
        var request: HttpRequestData? = null
        val api = api {
            request = it
            respond("[]", HttpStatusCode.OK, json)
        }

        api.fetchTodos(limit = 5)

        assertEquals(HttpMethod.Get, request?.method)
        assertEquals("https://jsonplaceholder.typicode.com/todos?_limit=5", request?.url.toString())
    }
  • MockEngine(handler) の handler は、リクエストが来るたびに呼ばれる関数です。受け取ったリクエスト（HttpRequestData）から、返すレスポンス（HttpResponseData）を作ります。テストごとに違う応答を返したいので、api { ... } の引数で受け取ります。
  • api() は、その MockEngine を 09 の createTodoHttpClient に渡して TodoApi を作ります。アプリと違うのはエンジンだけです。
  • respond(本文, ステータス, ヘッダー) で、返すレスポンスを作ります。ヘッダーには Content-Type: application/json（json）を付けます。付けない場合は、このステップの最後のブロックのテストで確かめます。
  • fetchTodos_sendsGetToTodosWithLimit では、ハンドラーが受け取ったリクエストを変数に取っておきます。送ったリクエストが GET https://jsonplaceholder.typicode.com/todos?_limit=5 であることを、通信せずに確かめられます。

Kotlin app/src/test/java/com/handson/android01/data/TodoApiTest.kt（続き） 
    // expectSuccess = true なので、2xx 以外は本文のデコードに進まず、ステータスの例外になる
    @Test
    fun fetchTodos_whenNotFound_throwsClientRequestException() = runTest {
        val api = api { respond("""{"error": "not found"}""", HttpStatusCode.NotFound, json) }

        val e = failureOf<ClientRequestException> { api.fetchTodos() }

        assertEquals(404, e.response.status.value)
    }
  • 09 で expectSuccess = true にしたので、2xx 以外のステータスは、本文のデコードに進まずに例外になります。404 は ClientRequestException です。例外の response.status で、どのステータスだったかがわかります。
  • failureOf<E> は、このファイルの最後に置く補助関数です。処理が E の例外で失敗することを確かめ、その例外を返します。
4 つめのブロック（500・壊れた JSON・必須の項目の欠落・Content-Type の欠落・タイムアウト）を見る
Kotlin app/src/test/java/com/handson/android01/data/TodoApiTest.kt（続き） 
    @Test
    fun fetchTodos_whenServerError_throwsServerResponseException() = runTest {
        val api = api { respond("oops", HttpStatusCode.InternalServerError) }

        val e = failureOf<ServerResponseException> { api.fetchTodos() }

        assertEquals(500, e.response.status.value)
    }

    @Test
    fun fetchTodos_whenJsonIsBroken_throwsJsonConvertException() = runTest {
        val api = api { respond("""[{"userId": 1, "id": 1, "title":""", HttpStatusCode.OK, json) }

        failureOf<JsonConvertException> { api.fetchTodos() }
    }

    // 必須の項目（title）が無い JSON も、デコードの失敗になる
    @Test
    fun fetchTodos_whenRequiredFieldIsMissing_throwsJsonConvertException() = runTest {
        val api = api { respond("""[{"userId": 1, "id": 1, "completed": false}]""", HttpStatusCode.OK, json) }

        failureOf<JsonConvertException> { api.fetchTodos() }
    }

    // Content-Type が JSON でないレスポンスは、ContentNegotiation が変換できない
    @Test
    fun fetchTodos_whenContentTypeIsMissing_throwsNoTransformationFoundException() = runTest {
        val api = api { respond(body, HttpStatusCode.OK) }

        failureOf<NoTransformationFoundException> { api.fetchTodos() }
    }

    // 応答が来ないとき: requestTimeoutMillis を過ぎると HttpRequestTimeoutException。応答の遅れは実時間（MockEngine は別のスレッドで動く）
    @Test
    fun fetchTodos_whenNoResponse_throwsTimeoutException() = runTest {
        val api = api(requestTimeoutMillis = 100L) {
            delay(5_000)
            respond(body, HttpStatusCode.OK, json)
        }

        failureOf<HttpRequestTimeoutException> { api.fetchTodos() }
    }
  • 500 は ServerResponseException になります。
  • 途中で切れた JSON と、必須の項目（title）が無い JSON は、どちらも JsonConvertException になります。
  • respond に Content-Type を付けないと、ContentNegotiation が本文を JSON として読みません。結果は JsonConvertException ではなく NoTransformationFoundException になります。本物のサーバーは Content-Type を付けて返すので、偽の応答でも付けます。
  • タイムアウトのテストでは、requestTimeoutMillis を 100 ミリ秒にして、ハンドラーで 5 秒待ちます。上限を超えると HttpRequestTimeoutException になります。ここでは MockEngine にディスパッチャーを渡していません。そのため、ハンドラーは別のスレッドを使い、実時間で動きます。runTest の仮想時間では進みません。テストは約 0.1 秒で終わります。

最後のブロックは、補助関数 failureOf とクラスの閉じ括弧です。

Kotlin app/src/test/java/com/handson/android01/data/TodoApiTest.kt（続き） 
    // block が E の例外で失敗することを確かめて、その例外を返す
    private inline fun <reified E : Throwable> failureOf(block: () -> Unit): E {
        val e = runCatching(block).exceptionOrNull()
        assertTrue("期待した例外: ${E::class.simpleName}、実際: $e", e is E)
        return e as E
    }
}

ViewModel の失敗・再試行・キャンセルをテストする

09 の ViewModel は、取得に失敗すると errorMessage に文言を入れ、retry() で取得し直します。この流れを、単体テストで確かめます。まず、単体テスト側の偽のサーバー（FakeTodoServer）に、失敗を作る入口を足します。

つまずきポイント

⚠️

NoTransformationFoundException でテストが失敗する

respond に Content-Type: application/json を付け忘れています。headersOf(HttpHeaders.ContentType, ContentType.Application.Json.toString()) を渡します。JSON の中身が正しくても、JsonConvertException ではなくこの例外になります。

⚠️

ViewModel の単体テストで、応答が届く前にアサートしてしまう

MockEngine は、ディスパッチャーを渡さないと、別のスレッドを使い、実時間で動きます。runTest の中で advanceUntilIdle を呼んでも、応答は待てません。FakeTodoServer に、setMain したものと同じテスト用ディスパッチャーを渡します。

⚠️

「1 回目は失敗、2 回目は成功」をどう書くか迷う

MockEngine のハンドラーは、既定で何度でも使い回されます（reuseHandlers = true）。ハンドラーを順番に登録するより、この項目のように偽のサーバーの状態（status）をテストの途中で書き換えるほうが、読みやすく書けます。

⚠️

機内モードで、MainActivity を起動する UI テストだけが失敗する

そのテストがネットワークに出ています。FakeTodoApiRule が無いか、RuleChain の内側に置いています。09 と同じく、Activity を起動するルールより外側に置きます。

⚠️

アプリが「ネットワークに接続できません」になる

機内モードのままになっていないか確かめます。解除するコマンドは次のとおりです。

Terminal 
$ adb shell cmd connectivity airplane-mode disable

まとめ

MockEngine を createTodoHttpClient に渡し、アプリと同じ設定の HttpClient で TodoApi をテストしました。respond でステータス・本文・Content-Type を決めると、本物の API では起こせない失敗を、ネットワークへ出ずに再現できます。 ViewModel のテストでは、MockEngine にテスト用のディスパッチャーを渡して、待ち時間を仮想時間にしました。失敗の文言・再試行・キャンセルを確かめました。UI テストでは、別のスレッドから届く応答を waitUntil で待ち、失敗表示から再試行で一覧に戻る流れを確かめました。機内モードのままでも UI テスト 66 件が通り、テストがネットワークに出ていないことも確かめました。
