リリースビルドと署名

  • ⏱ 所要時間: 60分（任意の確認を除く）
  • 📊 難易度: 入門
  • 👤 対象: 15 でテストを仕上げた人。Android トラックの最後の項目です
  • 📋 前提: 15 で作ったプロジェクトがビルドでき、エミュレータ（Handson_Android36）を起動できること。エミュレータからインターネットに接続できること（最初の一覧を API から取得します）。ターミナルでシェルの関数と環境変数を使えること
  • 🔗 前提となる項目: 15: テストの仕上げ
  • 🧩 版: 依存の追加はありません。AGP 9.4.1（R8 9.4.24）/ Gradle 9.6.0 / Android SDK Build-Tools 37.0.0（aapt2・zipalign・apksigner）/ Command-line Tools の apkanalyzer と retrace 9.0.32 / Android Studio 同梱の JBR の keytool・jarsigner / Kotlin 2.4.20 / Compose BOM 2026.09.00
  • 🌿 完成コード: ブランチ android/16-release

🎯 このレッスンで学ぶこと

  • debug と release の APK の違い（デバッグ可能かどうか・サイズ・クラスの名前）を、aapt2 と apkanalyzer で確かめられる
  • R8 の出力（usage.txt・seeds.txt・configuration.txt・resources.txt・mapping.txt）から、消えたコードと残ったコードの理由を読み取れる
  • release でわざと落としたスタックトレースを、retrace と mapping.txt で元のクラス・ファイル・行に戻せる
  • keytool で作った自分の鍵で APK に署名し、versionCode を上げた APK でデータを残したまま更新できる。ダウングレードと署名違いが拒否されることを確かめられる
  • AAB（bundleRelease）の中身を確かめ、jarsigner で署名できる。鍵とパスワードをリポジトリに入れない理由を説明できる

概要

15 までで、Todo アプリの機能とテストがそろいました。この項目では、アプリを配る形にします。新しい機能は作りません。コードの変更は 2 ファイル・10 行だけで、ほとんどはコマンドの実習です。

これまでの項目では、release の APK を debug 用の鍵で一時的に署名し、起動の確認だけをしてきました。この項目では、release の APK の中身を debug と比べ、R8 が何を消して何を残したかを、R8 自身の出力で確かめます。続けて、release で起きたクラッシュを読めるように戻す方法と、自分の鍵での署名・更新・AAB を扱います。

⚠️

鍵とパスワードはリポジトリに入れない

この項目では、署名の鍵を自分で作ります。鍵はプロジェクトの外の作業用ディレクトリに作り、最後に削除します。パスワードは、コマンドが聞いてきたときに入力します。コマンドの引数やファイルに書きません。app/build.gradle.kts にも、鍵の場所やパスワードを読む設定（signingConfigs）を入れません。理由はステップ 4 で説明します。

デバッグ可能かどうか

aapt2 dump badging は、APK のマニフェストの要点を表示します。パッケージ名の行と、デバッグ可能を表す application-debuggable の行だけを取り出します。

Terminal

application-debuggable は debug にだけ出ます。デバッグ可能なアプリは、中のデータを adb shell run-as で読めます。筆者が debug の APK を入れて run-as com.handson.android01 ls を実行すると、databases や files などのディレクトリの一覧が出ました。release の APK では run-as: package not debuggable: com.handson.android01 と拒否されました。配るのは release です。versionCode='1' versionName='1.0' は両方同じで、ステップ 5 で上げます。

ℹ️

鍵とパスワードをリポジトリに入れない。鍵を失くさない

  • Google Play では Play App Signing が標準です。利用者に配る APK の署名の鍵（アプリの署名鍵）は Google が持ち、開発者はアップロード鍵で署名した AAB を Play に送ります。アップロード鍵は、失くしてもリセットできます。この項目では説明だけにして、Play Console の操作はしません。

Gradle に署名させる場合は、app/build.gradle.kts に signingConfigs を書きます。このコードは app/build.gradle.kts に入れません。このトラックでは、毎回手で署名します。また、筆者はこのコードを動かして確かめていません。下の書き方も、動かして確かめていない参考です。

値を読むときは .get() ではなく .orNull を使い、4 つの値がそろっているときだけ signingConfigs を作ります。.get() は、値が無いとビルドの設定の段階で失敗します。そうなると、値を置いていない環境（CI や他の人の環境）では、debug のビルドやテストまで止まります。

Kotlin app/build.gradle.kts（参考。入れない） 
// app/build.gradle.kts に書く場合の例（このトラックのプロジェクトには入れない）
// 値は ~/.gradle/gradle.properties などリポジトリの外に置き、ここには書かない
val releaseStoreFile = providers.gradleProperty("handson.storeFile").orNull
val releaseStorePassword = providers.gradleProperty("handson.storePassword").orNull
val releaseKeyAlias = providers.gradleProperty("handson.keyAlias").orNull
val releaseKeyPassword = providers.gradleProperty("handson.keyPassword").orNull

android {
    signingConfigs {
        // 4 つの値がそろっているときだけ作る
        if (releaseStoreFile != null && releaseStorePassword != null &&
            releaseKeyAlias != null && releaseKeyPassword != null
        ) {
            create("release") {
                storeFile = file(releaseStoreFile)
                storePassword = releaseStorePassword
                keyAlias = releaseKeyAlias
                keyPassword = releaseKeyPassword
            }
        }
    }
    buildTypes {
        release {
            // 作ったときだけ割り当てる
            signingConfigs.findByName("release")?.let { signingConfig = it }
        }
    }
}

つまずきポイント

⚠️

command not found: aapt2（または apksigner・keytool など）になる

準備の export PATH=… を、今のターミナルで実行したかを確かめます。ターミナルを開き直すと消えます。build-tools の版も、自分の環境の版に合わせます。

⚠️

最初の adb uninstall が Failure [DELETE_FAILED_INTERNAL_ERROR] になる

アプリが入っていないときの失敗です。そのまま次の adb install に進んでかまいません。

⚠️

-whyareyoukeeping を足しても、理由が表示されない

./gradlew :app:minifyReleaseWithR8 --rerun のように --rerun を付けて、R8 のタスクを流し直します。

⚠️

retrace で名前が戻らない

スタックトレースを出したビルドと、mapping.txt のビルドが同じかを確かめます。release をビルドし直すと mapping.txt は書き直されます。

⚠️

署名した APK が apksigner verify で通らない

署名した後に、その APK を別のツールで書き換えていないかを確かめます。筆者が署名済みの APK に zip コマンドでファイルを 1 つ足すと、apksigner verify は DOES NOT VERIFY になりました。書き換える作業は署名の前に済ませ、署名は最後に行います。

⚠️

INSTALL_FAILED_VERSION_DOWNGRADE になる

入っているアプリより versionCode が小さい APK です。versionCode を上げてビルドし直すか、アンインストールしてから入れます。ステップ 5 のダウングレードの確認は、v1.apk を先に作っておかないとできません。

⚠️

INSTALL_FAILED_UPDATE_INCOMPATIBLE になる

入っているアプリと違う鍵で署名した APK です。同じ鍵で署名し直します。練習なら、アンインストールしてから入れます（アプリのデータは消えます）。

⚠️

grep -c の結果が 0 のとき、終了コードが 1 になる

grep -c は、1 件も見つからないと終了コード 1 を返します。表示された件数が 0 なら、コマンドの失敗ではありません。

まとめ

release の APK を読み解き、自分の鍵で署名して配る形にしました。 debug と release を比べ、R8 が名前を置き換え、使われないコードとリソースを消していることを確かめました。 R8 の出力からは、消えたもの（usage.txt）・残したもの（seeds.txt）・ライブラリが持ち込んだ keep ルール（configuration.txt）を読み取りました。 わざと落としたスタックトレースは、retrace と mapping.txt で元のファイルと行に戻せました。行番号の keep ルールは足さずに済みました。 versionCode を上げ、keytool が作った鍵で APK に署名し、データを残したまま更新しました。ダウングレードと署名違いは拒否されます。 最後に AAB を作り、mapping.txt が同梱されていることを確かめて、jarsigner で署名しました。
