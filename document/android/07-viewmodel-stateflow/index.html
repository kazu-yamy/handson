概要

06 までは、Todo の一覧・絞り込み・シートの表示を、stateful な TodoListPage が rememberSaveable で持っていました。 この項目では、そのうち「アプリのデータ」にあたる一覧と絞り込みを ViewModel に移します。画面は StateFlow を購読して表示するだけにします。 ViewModel は画面回転では残りますが、プロセスが終了されると消えます。その退行を実際に確かめてから、SavedStateHandle で補います。 最後に、viewModelScope で動く読み込み処理を足し、ViewModel を JVM 上の単体テストで検証します。

前提知識として、02 のコルーチン（suspend・launch・runTest）と、04 の rememberSaveable と State hoisting を使います。

状態をどこに置くか

公式ドキュメント（State holders and UI state）は、状態の置き場所を次のように示しています。「ビジネスロジックと画面の UI 状態は ViewModel、UI 要素の状態と UI ロジックは Composable」に置きます。06 の TodoListPage が持っていた状態を、この指針で ViewModel と Composable に分けます。

状態置き場所理由
Todo の一覧ViewModelアプリのデータ。追加・完了切替・削除・元に戻すという操作を伴う
絞り込み（TodoFilter）ViewModel一覧のうちどれを表示するかを決める、画面の UI 状態
追加シートの表示（showAddSheet）Composable（rememberSaveable）シートという UI 要素の状態
入力中の文字（TextFieldState）Composable（rememberTextFieldState）Compose の部品に依存する
Snackbar（SnackbarHostState）Composable（remember）表示とボタンの結果待ちは UI の仕事
スクロール位置・確認ダイアログの表示・スワイプの状態Composable見た目だけに関わり、Compose の部品に依存する
  • ViewModel に置く: アプリのデータとビジネスロジック（追加・完了切替・削除・元に戻す）、画面に何を表示するかを決める UI 状態（絞り込み）。
  • Composable に置く: UI 要素の状態と UI ロジック。シートやダイアログの表示、SnackbarHostState・TextFieldState・LazyListState・コルーチンスコープなど、Compose の部品に依存するもの。
  • 回転で残るかどうかでは分けない: シートの表示も rememberSaveable で回転の後に残ります。回転で残ることは、ViewModel に置く理由になりません。
  • 迷ったとき: 「単体テストで ViewModel を作ったとき、その状態を JVM だけで検証したいか」で決めます。Snackbar や TextFieldState は Compose に依存するので、ViewModel には入れません。

削除の「元に戻す」は、操作そのもの（一覧に戻す）は ViewModel のメソッドにします。Snackbar を出し、押されたボタンを待つ部分は UI の仕事なので、TodoListPage に残します。

プロパティが全部 val の data class にします。状態を変えるときは copy で新しい値を作って入れ替えます。StateFlow は、新しい値が前の値と equals で違うときだけ購読側に通知します。

次に、ViewModel を作ります。ui/screens/TodoListViewModel.kt を新しく作ります。

Kotlin app/src/main/java/com/handson/android01/ui/screens/TodoListViewModel.kt 
package com.handson.android01.ui.screens

import androidx.lifecycle.ViewModel
import com.handson.android01.kotlin.Todo
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update

// 画面状態を持つ ViewModel。画面回転（Activity の作り直し）では破棄されず、同じインスタンスが使われ続ける
class TodoListViewModel(initialTodos: List<Todo>) : ViewModel() {

    // viewModel() の既定のファクトリは、引数なしのコンストラクタを探して呼ぶ。引数付きのままだと実行時に失敗する
    constructor() : this(demoTodos(20))

    // 書き込めるのは ViewModel の中だけ。外には読み取り専用の StateFlow として公開する
    private val _uiState = MutableStateFlow(TodoListUiState(todos = initialTodos))
    val uiState: StateFlow<TodoListUiState> = _uiState.asStateFlow()

    // update: 今の値から新しい値を作って入れ替える（複数の更新が重なっても取りこぼさない）
    fun addTodo(title: String) {
        val trimmed = title.trim()
        if (trimmed.isEmpty()) return
        _uiState.update { state ->
            // id は今ある最大値 + 1
            val id = (state.todos.maxOfOrNull { it.id } ?: 0) + 1
            state.copy(todos = state.todos + Todo(id = id, title = trimmed))
        }
    }

    fun toggleTodo(id: Int, done: Boolean) {
        _uiState.update { state ->
            state.copy(todos = state.todos.map { if (it.id == id) it.copy(done = done) else it })
        }
    }

    fun deleteTodo(id: Int) {
        _uiState.update { state -> state.copy(todos = state.todos.filterNot { it.id == id }) }
    }

    // 削除の「元に戻す」。削除前の位置に戻す（その間に件数が減っていても範囲内に収める）
    fun restoreTodo(todo: Todo, index: Int) {
        _uiState.update { state ->
            val todos = state.todos.toMutableList()
            todos.add(index.coerceIn(0, todos.size), todo)
            state.copy(todos = todos)
        }
    }

    fun deleteDone() {
        _uiState.update { state -> state.copy(todos = state.todos.filterNot { it.done }) }
    }

    fun setFilter(filter: TodoFilter) {
        _uiState.update { it.copy(filter = filter) }
    }
}
  • ViewModel() を継承したクラスは、画面回転（Activity の作り直し）では破棄されません。作り直した後の Activity でも、同じインスタンスが使われます。
  • _uiState（MutableStateFlow）は private にして、書き換えを ViewModel の中に閉じ込めます。外には asStateFlow() で読み取り専用にした uiState を公開します。
  • update { ... } は、今の値から新しい値を作って入れ替えます。複数の更新が重なっても、取りこぼしません。
  • 06 で TodoListPage に書いていた追加・完了切替・削除・元に戻す・完了済みの削除の処理を、メソッドとして移しました。restoreTodo は coerceIn(0, todos.size) で、戻す位置を範囲内に収めます。
  • constructor() : this(demoTodos(20)) は、引数なしで作るためのコンストラクタです。理由は後の注意で説明します。

collectAsState との違い

collectAsState() でも StateFlow を読めますが、画面がバックグラウンドにあるあいだも収集を続けます。collectAsStateWithLifecycle() は、画面が STARTED を下回ると収集を止めます。Android では collectAsStateWithLifecycle() を使います。

💡

am kill はバックグラウンドのプロセスだけを終了する

アプリが前面にあるまま am kill を実行しても、プロセスは終了しません。先にホームボタンを押すのはそのためです。開発者オプションの「アクティビティを保持しない」は Activity だけを破棄するので、プロセスが消える状況の再現にはなりません。

SavedStateHandle に、ViewModel の状態を保存します。SavedStateHandle は、プロセスが終了されても残したい値の入れ物です。中身は Activity の onSaveInstanceState の Bundle に保存され、プロセスが作り直されたときに、保存した値が入った状態で ViewModel に渡されます。

保存するのは、Todo の一覧と絞り込みです。06 の rememberSaveable が保存していたもの（一覧・絞り込み・シートの表示）のうち、ViewModel に移した 2 つです。同じ範囲を保存するので、06 の挙動から退行しません。シートの表示と入力中の文字は Composable に残したので、これまでどおり rememberSaveable と rememberTextFieldState が保存します。

⚠️

Todo の一覧を SavedStateHandle に入れるのは、教材上の簡略化

SavedStateHandle の中身は、Activity の保存状態と一緒にプロセス間通信（Binder）で渡されます。Binder のバッファは 1MB をプロセス全体の通信で共有するため、公式ドキュメント（Parcelables and bundles）は保存状態を 50KB 未満に抑えるよう推奨しています。超えると TransactionTooLargeException になります。大きなデータや本物のデータの置き場には向きません。この項目では、06 の挙動を保つために一覧ごと入れています。実際のアプリでは、一覧はデータベース（後の項目で扱う Room）に置き、SavedStateHandle には「選択中の ID」や「検索語」程度の小さな値を入れます。

追加の依存は要りません。SavedStateHandle だけを受け取るコンストラクタを用意すれば、viewModel() の既定のファクトリがそれを呼び、SavedStateHandle を渡します。必要な lifecycle-viewmodel-savedstate は、ステップ 1 で追加した lifecycle-viewmodel-compose が推移的に連れてきます。

viewModelScope の delay は、テスト用のクロックでは進まない

Compose の UI テストには、アニメーションなどを進めるテスト用のクロック（mainClock）があります。viewModelScope の delay は実時間で進むので、このクロックの対象外です。waitUntil を入れる前は、TodoListViewModelRecreationTest が失敗しました。20 件中 7 件完了 が見つからないという失敗です（... is not displayed!）。実時間の処理は、waitUntil(timeoutMillis) { 条件 } で条件が満たされるまで待ちます。

viewModelScope は Dispatchers.Main.immediate を使いますが、JVM には Main ディスパッチャーがありません。Dispatchers.setMain(...) でテスト用のディスパッチャーに差し替え、テストの後に @After の resetMain() で戻します。差し替えるディスパッチャーは 2 種類あり、動き方が違います。

ディスパッチャーlaunch した処理このテストでの確かめ方
StandardTestDispatcherキューに入るだけで、テストが runCurrent()・advanceTimeBy()・advanceUntilIdle() で進めるまで動かない。delay は仮想時間で、待たずに時間だけ進められる999 ミリ秒進めてもまだ isLoading = true、あと 1 ミリ秒進めると false。待ち時間 0 でも、runCurrent() するまで動かない
UnconfinedTestDispatcher最初の中断点（delay など）まで、呼び出した場所でそのまま実行される待ち時間 0 なら、ViewModel を作った時点で読み込みが終わっている
  • runTest { ... } の中で StandardTestDispatcher(testScheduler) を setMain すると、runTest と ViewModel が同じ testScheduler（仮想時間）を共有します。
  • uiState_emitsLoadingThenLoadedThenToggled は、StateFlow の値の変化を順に集めます。collect（toList）は終わらないので backgroundScope で起動し、テストの終わりに自動でキャンセルさせます。Unconfined で集めると、値が変わるたびにその場で集まり、「読み込み中 → 読み込み済み → 完了切替」の 3 件になります。
  • StateFlow は、同じ値は通知せず、集める側が追いつく前の途中の値は飛ばします（conflation）。値の数を数えるテストでは、この性質を意識します。
  • restoredState_isUsedWithoutLoading は、値を入れた SavedStateHandle を渡して、プロセスの再生成を再現します。
  • Turbine などのサードパーティのライブラリは使っていません。
⚠️

Dispatchers.setMain を忘れても、例外にならない

setMain を忘れても、ViewModel の生成は例外になりません。viewModelScope が別スレッドで動き、検証がタイミング次第になります。ViewModel のテストでは、setMain を毎回呼び、@After で resetMain します。

setMain を忘れた実験の記録を見る

setMain を呼ばずに、待ち時間 0 の ViewModel を作るだけの使い捨てのテストを書いて試しました。ViewModel の生成は例外にならず、テストも落ちません。生成の直後は isLoading=true のままで、300 ミリ秒待つと false になりました。

lifecycle の実装では、Dispatchers.Main が使えないと、viewModelScope は別のディスパッチャー（Default）で動きます。そのため、読み込みは別スレッドで非同期に実行され、検証がタイミング次第になります。直後に assertFalse(isLoading) すると、失敗することがあります（筆者の 1 回目の実行では失敗しました）。

テストの中で Dispatchers.Main に自分でアクセスした場合（withContext(Dispatchers.Main) {} で確かめました）は、次の分かりやすい例外になります。

例外のメッセージ 
java.lang.IllegalStateException: Dispatchers.Main was accessed when the platform dispatcher was absent and the test dispatcher was unset. Please make sure that Dispatchers.setMain() is called before accessing Dispatchers.Main and that Dispatchers.Main is not accessed after Dispatchers.resetMain().

つまずきポイント

⚠️

Cannot create an instance of class ... で起動直後に落ちる

viewModel() の既定のファクトリは、引数なし、または SavedStateHandle だけを受け取るコンストラクタしか呼べません。原因の行は Caused by: java.lang.NoSuchMethodException: ...<init> [] です。既定のファクトリ用のコンストラクタを用意するか、viewModel(factory = ...) でファクトリを渡します。

⚠️

回転すると状態が初期値に戻る

Composable の中で TodoListViewModel() のようにコンストラクタを直接呼ぶと、Activity が作り直されるたびに新しい ViewModel ができます。viewModel() で取り出します。

⚠️

ViewModel の回転のテストが、何をしても通る

StateRestorationTester は Activity を作り直さないので、ViewModel の状態は必ず残ります。Activity ごと作り直す createAndroidComposeRule<MainActivity>() と scenario.recreate() を使います。

⚠️

am kill してもプロセスが終了しない

am kill はバックグラウンドのプロセスだけを終了します。先にホームボタンでアプリをバックグラウンドに移します。

⚠️

Can't put value with type ... into saved state で落ちる

SavedStateHandle に、Bundle に入らない型を書きました。Parcelable・Serializable・プリミティブ・ArrayList などに変換してから書きます。List は実装クラスによっては受け付けられない（subList の結果など）ので、ArrayList(list) に詰め替えて型を確定させます。

⚠️

ViewModel の単体テストが、ときどき失敗する

Dispatchers.setMain を呼び忘れると、例外は出ないまま viewModelScope が別スレッドで動き、検証がタイミング次第になります。テストごとに setMain し、@After で resetMain します。

⚠️

UI テストが、読み込み前の画面を見て失敗する

viewModelScope の delay は実時間なので、Compose のテスト用クロックでは進みません。waitUntil で一覧が出るまで待つか、テスト用の ViewModel の待ち時間を 0 にします。

まとめ

Todo の一覧と絞り込みを TodoListViewModel に移し、MutableStateFlow を private にして StateFlow で公開しました。画面は viewModel() で ViewModel を取り出し、collectAsStateWithLifecycle() で購読します。 状態の置き場所は、アプリのデータは ViewModel、Compose の部品に依存する見た目だけの状態は Composable、と分けました。 ViewModel は回転では残りますが、プロセスの終了では消えます。その退行を確かめ、SavedStateHandle で一覧と絞り込みを復元しました。 最後に、viewModelScope の読み込み処理を足し、Dispatchers.setMain と 2 種類のテスト用ディスパッチャーで ViewModel を単体テストしました。
