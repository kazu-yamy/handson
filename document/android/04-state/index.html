状態と State hoisting

  • ⏱ 所要時間: 45分
  • 📊 難易度: 入門
  • 👤 対象: 03 で Composable 関数と Compose UI テストを書いた人
  • 📋 前提: 03 で作ったプロジェクトがビルドでき、エミュレータ（Handson_Android36）を起動できること
  • 🔗 前提となる項目: 03: Compose 入門

🎯 このレッスンで学ぶこと

  • remember と mutableStateOf で Composable に状態を持たせ、値の変化で再コンポーズが起きることを確かめられる
  • State hoisting で、状態を持つ画面（stateful）と状態を持たない部品（stateless）に分けられる
  • リストの状態を mutableStateListOf（toMutableStateList）で持ち、要素を置き換えて画面を更新できる
  • rememberSaveable と @Parcelize で、画面回転の後も状態を残せる
  • TextFieldState で入力欄の状態を扱い、入力に応じてボタンの有効・無効を切り替えられる
  • derivedStateOf が再コンポーズを減らす場面と、減らさない場面を説明できる
  • Compose UI テストで、クリックや文字入力の結果を検証できる

概要

03 の Todo 一覧画面は状態を持たず、チェックボックスを押しても「追加」を押しても画面は変わりませんでした。 この項目では、画面に状態を持たせて、チェックの切り替えと Todo の追加ができるようにします。 状態をどの Composable に置くかを決める State hoisting（状態の巻き上げ）のパターンを、カウンターと Todo 一覧の 2 つの題材で実装します。

Compose の状態モデル

03 で見たとおり、Compose は「データから UI を作る関数」を呼び直して画面を更新します（再コンポーズ）。 何が変わったら呼び直すのかを Compose に知らせるのが State です。 mutableStateOf で作った State の値を Composable が読むと、Compose はその読み取りを記録します。値が書き換わると、その State を読んでいる Composable だけが再コンポーズされます。 普通の変数（var count = 0）を書き換えても、Compose は変化に気づきません。

State hoisting では、状態をそれを使う部品から 1 段上の Composable に移します。状態を持つ側と持たない側の役割は次のとおりです。 この流れを単方向データフローと呼び、「状態は下へ、イベントは上へ」と覚えます。

役割この項目の例受け取るもの・渡すもの
状態を持つ（stateful）CounterScreen・TodoListPage状態を作って保持し、変更の処理を書く。子には値とイベントのラムダを渡す
状態を持たない（stateless）CounterDisplay・TodoListScreen・TodoRow・TodoInput値を引数で受け取って表示し、操作はラムダ（onIncrement・onToggle など）で親に知らせる

状態を持たない部品は、同じ引数を渡せばいつも同じ画面になります。03 と同じく Preview や UI テストでそのまま確かめられます。

状態の API の使い分け

この項目で使う API と、使い分けの目安です。各ステップで実際に書いて、動きの違いを確かめます。

API役割この項目で使う場面
mutableStateOf(値)読み書きを Compose が追跡する State を作る。値が変わると、読んでいる Composable が再コンポーズされるカウンターの count（ステップ 1）
remember { ... }初回のコンポーズで計算した値を、再コンポーズをまたいで覚えておく。画面回転などで Activity が作り直されると消えるmutableStateOf を包む（ステップ 1）
rememberSaveable { ... }remember と同じに覚えておくうえ、画面回転などの構成変更をまたいで値を保存して戻す。保存できる型（Bundle に入る型）か、保存方法（Saver）が必要カウンターと Todo 一覧（ステップ 3）
mutableStateListOf() / toMutableStateList()要素の追加・削除・置き換えを Compose が追跡するリスト（SnapshotStateList）を作るTodo の一覧（ステップ 2）
derivedStateOf { ... }ほかの State から計算した値を State にする。計算結果が変わったときだけ、読んでいる側が再コンポーズされる完了件数・全完了フラグ（ステップ 5）

入力欄の状態には、Compose Foundation の TextFieldState（rememberTextFieldState() で作る）を使います。詳しくはステップ 4 で扱います。

1

remember と mutableStateOf

最初に、ボタンを押すたびに数が増えるカウンターを作ります。状態（今の数）を Composable の中に持たせる、一番小さな例です。ui/components/Counter.kt を作ります。

Kotlin app/src/main/java/com/handson/android01/ui/components/Counter.kt 
package com.handson.android01.ui.components

import android.util.Log
import androidx.compose.foundation.layout.Column
import androidx.compose.foundation.layout.padding
import androidx.compose.material3.Button
import androidx.compose.material3.MaterialTheme
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable
import androidx.compose.runtime.SideEffect
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.remember
import androidx.compose.runtime.setValue
import androidx.compose.ui.Modifier
import androidx.compose.ui.platform.testTag
import androidx.compose.ui.tooling.preview.Preview
import androidx.compose.ui.unit.dp
import com.handson.android01.ui.theme.HandsonAndroid01Theme

// remember: 再コンポーズをまたいで値を保持する。remember の中の計算は初回コンポーズ時にだけ実行される
// mutableStateOf: 値が変わると、この値を読んでいる Composable だけが再コンポーズされる
// by: 委譲プロパティ。count の読み書きが state.value の読み書きになる（getValue / setValue の import が必要）
@Composable
fun Counter(modifier: Modifier = Modifier) {
    var count by remember { mutableStateOf(0) }

    // SideEffect: 再コンポーズが成功するたびに実行される。再コンポーズの回数を logcat に出すために使う
    SideEffect {
        Log.d("Recompose", "Counter: count=$count")
    }

    Column(modifier = modifier.padding(16.dp)) {
        Text(
            text = "count: $count",
            modifier = Modifier.testTag("count_text"),
            style = MaterialTheme.typography.titleLarge,
        )
        Button(
            onClick = { count++ },
            modifier = Modifier.testTag("increment_button"),
        ) {
            Text("増やす")
        }
    }
}

@Preview(showBackground = true)
@Composable
private fun CounterPreview() {
    HandsonAndroid01Theme {
        Counter()
    }
}
  • mutableStateOf(0): 初期値 0 の State を作ります。この State の値を読んだ Composable は、値が変わると再コンポーズされます。
  • remember { ... }: 中のラムダは初回のコンポーズでだけ実行され、作った State は再コンポーズをまたいで使い回されます。
  • var count by ...: by は Kotlin の委譲プロパティです。count を読むと State の value を読み、count++ は value への書き込みになります。by で State を使うには、androidx.compose.runtime.getValue と setValue の import が必要です。
  • SideEffect { ... }: コンポーズ（初回と再コンポーズ）が成功するたびに実行されるブロックです。ここでは、再コンポーズが何回起きたかを Logcat に出すために使っています。
  • testTag: UI テストから表示と押すボタンを見つけるための目印です（03 で使ったもの）。

ボタンを 2 回押しても count は 0 のままです。ボタンを押すと count++ で State の値は 1 になり、再コンポーズが起きます。ところが再コンポーズで Counter が呼び直されると、remember が無いので mutableStateOf(0) がもう一度実行され、新しい State（値は 0）が作られます。remember は「再コンポーズのたびに作り直さない」ための仕組みです。

⚠️

remember を外してもコンパイルエラーにならない

remember を付け忘れても、ビルドは成功します。誤りに気づけるのは、ボタンを押した後の値を確かめたときだけです。状態を持つ部品には、操作の後の表示を確かめる UI テストを書いておきます。

✅ 確認ポイント

CounterTest の 2 件が成功し、Logcat に count=0・count=1・count=2 が出れば OK です。remember を外すと count: 2 の検証が失敗することも確かめてください。

2

State hoisting

ステップ 1 の Counter は、状態（count）と表示（Text・Button）を 1 つの関数に持っています。これを、状態を持たない部品 CounterDisplay と、状態を持つ画面 CounterScreen に分けます。まず ui/components/CounterDisplay.kt を作ります。

Kotlin app/src/main/java/com/handson/android01/ui/components/CounterDisplay.kt 
package com.handson.android01.ui.components

import androidx.compose.foundation.layout.Column
import androidx.compose.foundation.layout.padding
import androidx.compose.material3.Button
import androidx.compose.material3.MaterialTheme
import androidx.compose.material3.Text
import androidx.compose.runtime.Composable
import androidx.compose.ui.Modifier
import androidx.compose.ui.platform.testTag
import androidx.compose.ui.tooling.preview.Preview
import androidx.compose.ui.unit.dp
import com.handson.android01.ui.theme.HandsonAndroid01Theme

// stateless（状態を持たない）な部品。表示する値は count で受け取り、操作は onIncrement で親に知らせる
// 値を持たないので、同じ引数を渡せば何度呼んでも同じ画面になる。テストや Preview で扱いやすい
@Composable
fun CounterDisplay(
    count: Int,
    onIncrement: () -> Unit,
    modifier: Modifier = Modifier,
) {
    Column(modifier = modifier.padding(16.dp)) {
        Text(
            text = "count: $count",
            modifier = Modifier.testTag("count_text"),
            style = MaterialTheme.typography.titleLarge,
        )
        // ボタンを押しても count は変わらない。onIncrement を呼ぶだけで、増やすかどうかは親が決める
        Button(
            onClick = onIncrement,
            modifier = Modifier.testTag("increment_button"),
        ) {
            Text("増やす")
        }
    }
}

CounterDisplay は count を引数で受け取って表示し、ボタンが押されたことを onIncrement で親に知らせるだけです。数を増やすかどうかは親が決めます。次に、状態を持つ ui/screens/CounterScreen.kt を作ります。

Kotlin app/src/main/java/com/handson/android01/ui/screens/CounterScreen.kt 
package com.handson.android01.ui.screens

import android.util.Log
import androidx.compose.runtime.Composable
import androidx.compose.runtime.SideEffect
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.remember
import androidx.compose.runtime.setValue
import androidx.compose.ui.Modifier
import com.handson.android01.ui.components.CounterDisplay

// stateful（状態を持つ）な画面。count の状態をここで持ち、部品には値とイベントだけを渡す
// 状態を持つ場所を 1 か所に決めると、部品の動きを状態に関係なくテストできる
@Composable
fun CounterScreen(modifier: Modifier = Modifier) {
    var count by remember { mutableStateOf(0) }

    SideEffect {
        Log.d("Recompose", "CounterScreen: count=$count")
    }

    CounterDisplay(
        count = count,
        onIncrement = { count++ },
        modifier = modifier,
    )
}

count の State は CounterScreen が持ち、CounterDisplay には値（count）とイベント（onIncrement = { count++ }）を渡します。これが State hoisting です。状態は下へ（count）、イベントは上へ（onIncrement）流れます。

@Composable
fun TodoListPage(

    modifier: Modifier = Modifier,
) {

    TodoListScreen(

        onToggle = { id, done ->

    )

実験: リストの状態の持ち方で何が変わるか

Todo の一覧を mutableStateOf<List<Todo>> に入れる方法もあります。一時的なテストを作り、「2 番目の Todo を完了にする」操作を 3 通りの持ち方で行って、表示と親の再コンポーズ回数（SideEffect で数えたもの）を比べました。

ケース操作親の再コンポーズ画面の表示
A1: mutableStateOf<List> で全体を置き換えるtodos = todos.map { ... }クリック 1 回で 1 回3 件中 3 件完了（更新される）
A2: 同じ List の中身だけ書き換えるraw[i] = ...（State の参照は変えない）0 回3 件中 2 件完了のまま（更新されない）
B: SnapshotStateList の要素を置き換えるtodos[i] = ...0 回3 件中 3 件完了（更新される）
Terminal 
$ adb logcat -d -s ExpD Exp     : A1 parent #1D Exp     : A1 parent #2D Exp     : A1 result: parent recompositions per click = 1D Exp     : A2 result: summary still '3 件中 2 件完了' after in-place mutationD Exp     : B parent #1D Exp     : B result: parent recompositions per click = 0
  • A1 は、新しいリストを State に代入するので、State を読んでいる親が再コンポーズされます。
  • A2 は、リストの中身を変えても State に入っているリストの参照は同じなので、Compose は変化に気づきません。List を mutableStateOf に入れて中身だけを書き換えるのは誤りです。
  • B は、表示が更新されるのに親は再コンポーズされていません。要素を置き換えたときに再コンポーズされるのは、そのリストを読んでいる側（件数や行を表示している TodoListScreen）だけだからです。

この項目では B の持ち方（TodoListPage の書き方）を採用しています。

「追加」ボタンで Todo を増やせるように、入力欄を付けます。Compose の入力欄には、状態の持ち方が違う 2 系統の API があります。

value / onValueChangeOutlinedTextField(value = text, onValueChange = { text = it })呼び出し側が String の State を持ち、入力のたびに書き換える

表示は 03 と同じ 3 件中 2 件完了 のままです。では、derivedStateOf で再コンポーズはどれだけ減るのでしょうか。

実験: derivedStateOf で再コンポーズは減るか

一時的なテストで、3 件の Todo に対して 3 つのラベルを置き、それぞれの再コンポーズ回数を SideEffect で数えました。ボタンで 1 件ずつ完了を切り替え、クリックごとに waitForIdle() で再コンポーズが終わるのを待ってから回数を記録しています。

ラベル書き方
直接Text("直接 ${todos.count { it.done }}")
件数を派生remember(todos) { derivedStateOf { todos.count { it.done } } }
全完了を派生remember(todos) { derivedStateOf { todos.all { it.done } } }
Terminal 
$ adb logcat -d -s Exp5D Exp5 : initial: direct=1 derivedCount=1 derivedAllDone=1D Exp5 : after t3: direct=2 derivedCount=2 derivedAllDone=1D Exp5 : after t2: direct=3 derivedCount=3 derivedAllDone=1D Exp5 : after t1: direct=4 derivedCount=4 derivedAllDone=1D Exp5 : after t3: direct=5 derivedCount=5 derivedAllDone=1D Exp5 : after t1: direct=6 derivedCount=6 derivedAllDone=2

初期状態は「完了 / 未完了 / 完了」で、t3 → t2 → t1 → t3 → t1 の順に切り替えています。

  • 件数は、切り替えのたびに変わります。そのため、派生させても再コンポーズの回数は直接計算と同じです（どちらも 1 → 6）。件数の表示に derivedStateOf を使っても、再コンポーズは減りません。
  • 全完了フラグは、最後の t1 で 3 件すべてが完了になったときだけ false → true に変わり、そのときだけ再コンポーズされました（1 → 2）。それまでの 4 回の切り替えでは、値が false のまま変わらないので再コンポーズされていません。

derivedStateOf が効くのは、「元の State は頻繁に変わるが、計算結果はあまり変わらない」場合です。件数のように毎回変わる値では効果がありません。この画面で件数に使っているのは、計算した値に doneCount という名前を付けて分けるためで、再コンポーズを減らす効果は無いことに注意してください。

つまずきポイント

⚠️

by で State を使うには getValue / setValue の import が必要

var count by remember { mutableStateOf(0) } と書くときは、androidx.compose.runtime.getValue と setValue の import が必要です。無いと、委譲プロパティの getValue / setValue が見つからずコンパイルエラーになります。mutableStateOf と remember の import と合わせて、4 つを一緒に入れます。読み取りだけの val ... by なら getValue だけで足ります（ステップ 5 の doneCount）。

⚠️

remember と rememberSaveable の使い分け

remember は再コンポーズのあいだだけ値を覚えておき、画面回転などで Activity が作り直されると消えます。rememberSaveable は構成変更をまたいで値を残します。どちらを使うかは「回転の後もユーザーに残っていてほしい値か」で決めます。rememberSaveable で保存する値は、Bundle へ入れられる型（Parcelable）にするか、Saver で保存の方法を決めます（ステップ 3）。

⚠️

List を mutableStateOf に入れて中身を書き換えない

mutableStateOf<List<Todo>> に入れたリストの中身を書き換えても、State の参照が同じなので画面が更新されません（ステップ 2 の実験 A2）。リスト全体を新しいリストに置き換えるか、mutableStateListOf / toMutableStateList() で作った SnapshotStateList の要素を置き換えます。

⚠️

derivedStateOf の使いすぎ

derivedStateOf が再コンポーズを減らすのは、計算結果が元の State ほど頻繁に変わらないときだけです。完了件数のように毎回変わる値に使っても、再コンポーズの回数は変わりません（ステップ 5 の実験）。

⚠️

TextField の API は 2 系統ある

OutlinedTextField には、value / onValueChange を渡す方式と、state（TextFieldState）を渡す方式があります。調べた記事やサンプルがどちらの方式かを確かめてから使います。TextFieldState の操作は edit { ... } の中で行います。clearText() は拡張関数なので、androidx.compose.foundation.text.input.clearText の import が無いと Unresolved reference のコンパイルエラーになります。

⚠️

空欄では追加ボタンが押せない

ステップ 4 から、追加ボタンは入力が空のとき無効です。03 の addButton_callsOnAddClick のように、いきなり「追加」を押すテストは失敗します。テストでは、先に performTextInput で文字を入れてから押します。

⚠️

adb shell input text は入力欄にフォーカスを移してから

入力欄にフォーカスが無い状態で adb shell input text "buy%smilk" を送ると、空白（%s）がフォーカス中のチェックボックスに届き、完了状態が切り替わってしまいました。文字を送る前に、入力欄をタップします。
